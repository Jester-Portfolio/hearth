# 스토리 월드 독립 진행 구조 비교

> 2026-10-25 정정: [ADR-0010](decisions/0010-coop-information-and-hud.md)에 따라 가입/탈퇴/관리자 구성원 변경은 현행 미정 기능이 아닙니다. 내부 식별 연결만 허용합니다. 아래 가입/파티 후보는 과거 검토 이력입니다. 투표/복귀/채집과 저장 최신 정책은 ADR-0011·0012를 따릅니다.

> 후속 정책: [ADR-0004](decisions/0004-community-quests-and-chapter-skip.md)가 코옵을 공동체로 정의했습니다. 아래 파티 가입·탈퇴·파티장·분할·병합은 당시 비교 후보이며 현재 구현 요구가 아닙니다. 당시에는 가입·관리자 변경도 미정이었으나 ADR-0010에서 가입/관리 기능 자체를 제외했습니다. B안 구조·기술 검토 이력은 보존합니다.

> 후속 결정 (2026-10-23): [ADR-0002](decisions/0002-stack-and-world-policies.md)로 Paper 26.2·Java 25·Gradle·PostgreSQL·단일 JAR·Docker Compose 및 월드 정책이 확정됐습니다. 아래 기술 미정·후보 표현과 API 근거는 2026-10-22 당시 검토 기록으로 보존합니다. 현재 결정은 ADR을 따르며 채택 버전에서의 실행·호환성 검증은 여전히 미완료입니다.


상태: B안 채택 후 보존하는 비교 문서. 사용자가 운영 구조 B안을 확정했으며 [ADR-0001](decisions/0001-story-world-multiworld.md)이 결정의 기준입니다. 구현 기술과 검증은 미정·미완료이며 이 문서는 설치·배포 승인을 의미하지 않습니다.
검토일: 2026-10-22.

## 요구사항과 검토 범위

[아키텍처](architecture.md), [스토리 월드 설계](../minecraft/story/README.md), [AGENTS.md](../AGENTS.md)를 기준으로 다음을 비교합니다.

- 싱글 플레이와 소규모 코옵을 지원합니다.
- 플레이어 또는 파티별로 스토리를 독립 진행하며 퀘스트, NPC 상태, 월드 변화가 다른 진행에 간섭하지 않도록 합니다.
- 현대인이 마법 없는 중세 세계에서 현대의 과학·기술 지식을 활용하며, 제작·건설 같은 실제 월드 변화도 고려합니다.
- 필수 AI 스마트폰 어시스턴트는 해당 진행의 퀘스트·NPC·게임 내 정보만 참조하도록 경계를 설계합니다.
- 경제 월드와 스토리 월드의 진행·경제 데이터는 계속 분리합니다.

이 문서의 성능 비교는 구조에 대한 추론입니다. 서버 구현체, 에디션, 버전, NPC·퀘스트 확장 기술, 데이터 저장소와 AI 런타임은 미정입니다. Java 기반 구현의 JVM 비용을 예로 들지만 Java Edition 또는 Paper 채택을 확정하지 않습니다.

## A. 플레이어·파티별 서버 또는 컨테이너 분리

하나의 스토리 진행에 전용 서버 프로세스와 월드 데이터를 배정합니다. 컨테이너를 쓰더라도 여러 진행이 같은 서버 프로세스를 사용한다면 여기서 말하는 A의 격리가 아닙니다.

장점은 실제 블록, 엔티티, 시간·날씨와 서버 내부 상태를 진행별로 관리하기 쉽다는 점입니다. 서버 프로세스 하나의 오류가 다른 서버 프로세스를 직접 종료시키지는 않으며, 진행별 백업·복구와 호스트 간 배치에도 유리합니다. 코옵은 해당 서버에 같은 진행의 플레이어를 모으는 방식입니다.

제약은 실행 중 서버마다 런타임과 확장 기능의 기본 메모리, 시작·저장 작업이 반복된다는 점입니다. 중지된 진행은 실행 자원을 줄일 수 있지만 재접속 시 시작 지연과 안전한 저장·종료 절차가 필요합니다. 생성·접속 라우팅, 빈 서버 중지, 버전 일치와 백업 대상 증가도 운영 부담입니다. 서버 분리는 DB·AI의 공용 키 충돌이나 잘못 공유한 저장 경로까지 해결하지 않습니다.

컨테이너는 CPU·RAM을 추가로 만들어 주지 않습니다. Docker는 기본적으로 자원 제한이 없으므로 자동으로 자원 간섭을 차단한다고 가정할 수 없습니다. 향후 적용한다면 제한값과 전체 호스트 예산을 함께 검토해야 합니다. 같은 호스트의 메모리 고갈·디스크 장애는 여러 진행에 영향을 줄 수 있습니다. [Docker 자원 제한 공식 문서](https://docs.docker.com/engine/containers/resource_constraints/)

현재 자원에서 여러 서버와 필수 AI를 동시에 실행할 수 있는지는 **미검증**입니다. 높은 격리 또는 별도 호스트 확장이 필요할 때 재검토할 후보입니다.

## B. 하나의 서버에서 진행별 독립 월드 운영

하나의 서버 프로세스 안에서 진행마다 별도 월드 데이터와 블록·엔티티 공간을 둡니다. 예를 들어 같은 마을 원본에서 복사한 두 월드에서 한 파티만 다리를 건설할 수 있습니다. 여러 차원이 필요한 콘텐츠라면 진행 하나가 월드 묶음에 대응할 수 있으며 포털·부활 경로도 같은 진행에 묶어야 합니다.

장점은 서버 런타임을 공유하면서 실제 월드 변화를 분리할 수 있다는 점입니다. 싱글 진행도 한 명짜리 진행 단위로 취급하고 코옵 인원은 같은 월드에 배치할 수 있습니다. 서버 인스턴스 수가 적어 A보다 배포·접속 운영을 단순화할 가능성이 있습니다.

제약은 월드 분리가 프로세스·플레이어 데이터 전체의 격리는 아니라는 점입니다. 인벤토리, 경험치, 업적, 퀘스트 저장소, 스코어보드, 전역 이벤트, NPC 식별자, 플러그인 캐시 등을 별도로 점검해야 합니다. 월드를 바꾸는 것만으로 이 상태가 자동 분리된다고 가정하지 않습니다. 모든 명령·이동·포털·부활·보상 처리는 진행 경계를 확인해야 합니다. 서버 장애나 공유 힙의 메모리 부족은 전체 진행에 영향을 줍니다.

로드된 월드가 많으면 청크·엔티티·NPC 비용이 누적됩니다. 월드를 추가해도 전용 CPU 코어나 독립적인 틱 실행이 자동 배정되지 않으며, 구체적인 스레딩·스케줄링은 구현체에 따라 **미검증**입니다. 유휴 월드를 저장·언로드할 수 있다면 비용을 줄일 여지가 있지만, 플레이어·청크 강제 로드·NPC 작업·타이머·확장 기능 참조를 정리해야 하며 절감량은 **미검증**입니다.

Paper API에는 월드 생성·로드 및 언로드 기능이 있습니다. 이는 B의 구현 경로가 존재한다는 근거일 뿐, NPC·퀘스트 확장 기능의 호환성과 안전한 월드 복제·언로드를 보장하지 않습니다. 아래 버전은 참고 사례이며 채택 버전이 아닙니다. [Paper 1.21.11 Server API](https://jd.papermc.io/paper/1.21.11/org/bukkit/Server.html)

월드 복사본은 디스크·백업 공간을 늘립니다. 실행 중 원본 파일을 단순 복사하는 방식은 전제하지 않으며, 안전한 원본 템플릿과 버전 관리·복제 절차는 **미검증**입니다.

## C. 하나의 공통 월드에서 진행 상태 논리 분리

실제 지형과 시뮬레이션은 공유하면서 플레이어·파티별 퀘스트 단계, 대화, 해금 상태 등을 별도로 저장합니다. 서버 프로세스와 같은 지형의 중복을 줄일 가능성이 있지만, 플레이어가 서로 먼 곳에 있으면 활성 청크는 여전히 늘어납니다.

대화 분기나 개인별 목표 표시 중심이라면 적합한 후보입니다. 같은 파티는 진행 ID를 공유할 수 있습니다. 반면 파티 1에서는 NPC가 사망하고 파티 2에서는 살아 있어야 하거나, 같은 좌표에 파티별로 다른 다리가 있어야 한다면 상태 키 분리만으로 해결되지 않습니다. 공유 NPC를 실제로 제거하거나 블록을 변경하면 다른 파티에도 영향을 줍니다.

플레이어별 표시·가상 NPC·블록 표현을 도입하더라도 시각적 차이만으로 서버의 충돌 판정, 길 찾기, 공격 대상, 아이템 드롭, 상자, 유체·레드스톤 등을 격리했다고 볼 수 없습니다. 후보 기술의 지원 범위와 호환성은 **미검증**입니다. 공유 세계의 변경을 제한하는 설계는 가능하지만 독립적인 제작·건설 요구를 축소할 수 있습니다.

동일 월드에서 서로 멀리 떨어진 구역을 복제하는 대안도 있으나, 이는 순수한 논리 상태 분리와 다르게 지형·청크 비용을 중복시킵니다. 구역 간 이동·이벤트·전역 상태 누출 방지가 추가로 필요하며 B와 같은 월드 경계가 생기는 것은 아닙니다.

이벤트마다 진행별 권한을 검사해야 하므로 콘텐츠와 확장 기능이 늘수록 간섭 검증 비용이 커집니다. 자원을 가장 적게 쓴다는 보장도 없으며 개인화 구현의 CPU·RAM 비용은 **미검증**입니다.

## 채택된 방향과 비교 근거

**사용자 결정으로 B안을 채택했습니다.** 아래 비교 근거와 기술적 제약은 보존하며 채택이 구현 검증 완료를 뜻하지는 않습니다. 실제 월드 변화의 독립성을 유지하면서 서버 프로세스의 기본 비용을 공유할 수 있어 현재 목표와 제한된 자원 사이의 타협점이 될 가능성이 있습니다. NPC·퀘스트 확장 기능의 월드 대응과 유휴 월드 정리가 검증되어야 이 근거가 성립합니다.

A는 높은 격리와 호스트 간 분산에 유리하지만 현재 RAM에서 필수 로컬 AI와 여러 서버의 기본 비용을 함께 감당하는지는 알 수 없습니다. C는 대화·퀘스트 위주로 범위를 제한한다면 재검토할 수 있지만, 실제 NPC·지형 변화까지 독립시킬 때 개발 부담과 누락 위험이 큽니다. 어느 구조도 측정 없이 현재 호스트에 적합하다고 확정하지 않습니다.

채택 결정에 따라 플레이어 ID나 변경 가능한 파티 명단과 별개인 논리 진행 ID(`story_run_id`)를 물리 배치와 분리합니다. 싱글도 하나의 진행으로 취급하고 코옵은 해당 진행에 참여하는 방식입니다. 퀘스트·NPC 상태·보상 이력·AI 대화와 검색 범위는 진행 ID에 귀속하고, 개인 상태가 필요한 항목은 그 아래 플레이어 ID로 구분하는 방향입니다. 실제 스키마는 미정입니다.

파티 가입·탈퇴·분할·병합 때 진행을 어떻게 유지할지, 진행 소유자 부재 시 접근 권한, 보상 중복 방지와 개인 인벤토리 이동 정책은 별도 결정이 필요합니다. 다른 진행을 자동 병합하거나 소속 변경만으로 저장된 진행을 덮어쓰는 방식은 전제하지 않습니다. AI도 서버나 월드 분리만으로 안전해지지 않으므로 대화·캐시·검색 필터에 진행 경계를 적용하는 방안을 검증해야 합니다.

향후 A로 전환할 가능성을 위해 진행 ID와 물리 서버·월드의 배치 관계를 분리하기로 확정했습니다. 이는 자동 이전을 보장하지 않으며 실제 월드·플레이어·확장 기능 데이터의 이식성과 복구는 **미검증**입니다.

## 구현 전 필요한 검증

아래는 후속 검증 계획이며 이번 작업에서 실행하지 않았습니다. 서버 설치·실행이나 운영 변경을 승인하는 지침이 아닙니다.

| 항목 | 확인 방법과 판단 기준 | 현재 상태 |
| --- | --- | --- |
| 자원 예산 | 기존 서비스의 지속·최대 사용량과 OS 여유를 확인하고 AI 모델 로딩·동시 질의 비용까지 포함해 Minecraft 예산 산정 | 미검증 |
| B 구현 가능성 | 후보 에디션·서버·NPC·퀘스트 기술에서 복수 월드, 월드별 상태 저장, 안전한 저장·언로드·재로드 지원 확인 | 미검증 |
| 상호 간섭 | 두 진행에서 서로 다른 퀘스트 단계·NPC 생존 상태·다리·상자 상태를 만들고 이동·명령·포털·부활·재접속 후 교차 접근과 상태 누출이 없는지 확인 | 미검증 |
| 코옵 일관성 | 같은 진행에서 동시 퀘스트 완료·보상·NPC 상호작용, 파티 변경과 재접속 시 중복 보상·진행 유실이 없는지 확인 | 미검증 |
| AI 경계 | 서로 다른 진행의 NPC·퀘스트 정보를 질문하고 다른 진행의 정보·대화·캐시가 검색·응답에 섞이지 않는지 확인 | 미검증 |
| 부하와 유휴 처리 | 단일 진행을 기준으로 두 진행 동시 활동, 탐험·NPC 활동·저장·AI 질의가 겹치는 경우와 유휴 월드 정리 전후를 비교 | 미검증 |
| 복구와 템플릿 | 월드와 퀘스트 상태를 같은 복구 시점으로 복원하고 다른 진행이 유지되는지 확인. 복제·업데이트 시 원본 보존 확인 | 미검증 |

부하 측정에는 프로세스 전체 RSS와 JVM 사용 시 힙·GC, CPU 사용량과 틱 지연(MSPT/TPS를 지원하는 구현체의 경우), 디스크 I/O, 로드 청크·엔티티 수, AI 응답 지연을 포함합니다. JVM 힙 상한만으로 프로세스 전체 RAM을 계산하지 않습니다. Paper를 후보로 선택한다면 공식 프로파일링 안내가 틱·GC 측정의 참고가 됩니다. [Paper 프로파일링 공식 문서](https://docs.papermc.io/paper/profiling/)

유휴 월드는 저장 후 언로드하는 방향으로 확정했습니다. 진행 정지 또는 재접속 시 경과 시간 반영 정책, 유휴 판단과 대기 시간은 미정입니다. 공통 로컬 AI 서비스를 사용하되 진행별 정보 접근을 격리하는 요구도 확정했으며 세부 구현은 검증해야 합니다.

B의 구현 검증에서 상태 격리나 자원 문제가 확인되면 활성 진행 수·콘텐츠 범위와 대체 구현을 검토합니다. 필요 시 A안 전환을 재검토하고 구조 변경은 후속 [의사결정 기록](decisions/README.md)에 남깁니다. 현재 채택 결정은 ADR-0001이며 본문의 미검증 항목은 그대로 남아 있습니다.
