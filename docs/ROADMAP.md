# Hearth 개발 로드맵

마지막 정리: 2026-11-17. [현재 구현·검증 상태](PROJECT_STATUS.md), [설계 정본 ADR](decisions/README.md), [작업·검증 정책](DEVELOPMENT_WORKFLOW.md)을 함께 사용한다. [이전 로드맵](ROADMAP-archive-2026-10-27.md)은 이력으로 보존한다. 아래 계획은 새 기능 구현·실행·운영 변경의 일괄 승인이 아니며 일정·밸런스·미정 기술을 확정하지 않는다.

## 개발 목표와 상태 기준

Hearth의 목표는 현대 과학·기술 지식을 활용하는 싱글·소규모 코옵 스토리 RPG와 별도 경제 월드다. 테스트는 이 게임을 완성하기 위한 검증 수단이다. 다음 작업은 실제 기능이나 플레이 흐름을 완성하는 중형~대형 배치로 선정한다. 토큰 절약을 위해 승인 범위를 줄이거나 기술 시험만 반복하지 않는다.

- **완료**: 해당 단계의 명시한 완료 조건을 충족. 설계 완료는 구현·실행 검증 완료와 다르다.
- **진행 중**: 구현 또는 검증을 시작했으며 완료 조건이 남음.
- **예정**: 후속 계획이며 착수·완료를 뜻하지 않음.
- **보류**: 재개 조건·사용자 결정을 기다림.

## 현재 개발 우선순위 — 멀티서버 네트워크

2026-11-18 사용자 요청으로 스토리 모드의 추가 개발을 보류한다. [ADR-0025](decisions/0025-lobby-economy-network.md)의 Velocity 프록시·로비/경제 Paper, 정품 modern forwarding·고정 경로·경제 저장 후 서버 이동을 한 배치로 구현/검증한다. 기존 스토리 B안은 보존하며 진행별 서버 분리/A안 전환을 뜻하지 않는다. 실제 접속/전환·운영 예산·배포 적용은 별도 수용/승인 경계다. [설정/플레이 경로](../infrastructure/network/README.md)를 따른다.

일반 마크 기반의 경제 backend는 [ADR-0026](decisions/0026-vanilla-survival-world-selection.md)의 `survival` 모드로 시작한다. 거주·야생·지옥 3월드와 `/월드` 선택 UI·native 개인 데이터/기본 생존을 연결했다. [기존 경제의 일반 생존 연결](native-economy-verification.md)로 PG 화폐·상점/개인 거래·생산/수급/운송·공개 조회를 구현했다. [시장 에이전트](market-automation-verification.md)의 자동 비축/출하량 배분·운영 모드/PG 복원을 추가했고 경제 운영은 LLM 없이 수행한다. [단일 스폰·종류별 원격 상점](spawn-shops-verification.md)으로 진입을 통합했다. 여러 마을/스토리식 동선은 추가하지 않는다. 후속 범위는 단일 스폰의 실제 시설/지형·콘텐츠 수치·장기 수급/화폐량 균형·거주 기능의 실제 수용·야생 초기화 정책, 실제 플레이·부하/운영 수용이다. 기존 RPG 경제 프로토타입의 PG 인벤토리를 새 모드에 자동 채택하지 않는다.

[거주 시스템 배치](housing-system-verification.md)로 공용 구획/WG 보호·개인 월드 구매/차액 확장/초대 공동 거주·기존 `/월드`·PG 거래/이동·포탈/복귀·저장 종료를 통합했다. 사용자 지시에 따라 가격/크기·정원·실제 지형·밸런싱은 추후 설정하며 운영에 적용하지 않는다. 다음 수용 범위는 실제 클라이언트/동접·장기 부하·운영 백업/복구/배포이며, 자원 월드 세대 교체와 주기는 별도 정책/구현 범위다.

## S4 후속 기능 배치

현재 잔여 기능과 선행 조건은 [S4 잔여 기능 배치](s4-remaining-work.md)에서 관리한다. 공개 코스에 개인 컷신/재시청·가공/설치된 이동식 보관함·개인 엔더·스마트폰 지급·지도/미니맵/HUD·추가 보스 기술·재시작 복귀/HOLD를 묶어 연결했다. 실제 인증 플레이와 리소스팩/HUD 배치·코옵/장애 수용이 남아 있으며 자동 검증만으로 S4 완료를 선언하지 않는다.

[관리자 읽기 전용 복구 진단](recovery-inspection-verification.md)을 추가해 검증 연결의 저장/런타임 상태와 보고서 차이를 확인할 수 있다. [실제 한 명 부분 수용](s4-client-acceptance.md)을 진행한 뒤 사용자가 종료했다. 추가 실제 수용은 재개 요청 전 보류하며 미실행 범위를 완료로 바꾸지 않는다. 재개 요청 후 개인/코옵·화면/팩·시설/전투·저장/재접속·장애 흐름을 함께 확인하고 발견한 문제를 관련 기능과 묶어 보완한다. 시험 확장만 다음 목표로 반복하지 않으며 S5 정식 품질/캐시·운영 예산과 S6 콘텐츠/성능·운영 단계는 별도 범위를 따른다.

Issue #1·#2의 격리 효과 완료와 Issue #3의 `not_planned` 종료는 유지한다. S5 필수 로컬 AI·S6 콘텐츠/성능·경제는 별도 완료 기준을 따른다.

## 공통 완료 경계

- 설계·구현·자동 검증·실제 플레이·운영 배포를 구분한다. 게임 정의와 미정 정책은 [ADR](decisions/README.md), S3 설계 완료 근거는 [감사](s3-completion-audit.md)를 따른다.
- [ADR-0003](decisions/0003-inventory-performance-and-recovery.md)의 성능 우선·30초 dirty 비동기 저장, 거래 즉시 저장·보상 중복 방지·전환 전 source 저장 원칙을 유지한다. 거래/보상 전체 구현은 아직 없다. 고비용 체크포인트·완전 자동 무손실 복구를 완료 조건에 추가하지 않는다.
- 기존 진행·월드·인벤토리·콘텐츠를 보존하고 필요한 오류 기록·로그/백업 기반 관리자 수동 대응을 마련한다. 승인된 기능 범위에서 기성 플러그인 검토와 위험별 필수 검증을 수행하며 같은 성공 검사를 반복하지 않는다.
