# 스토리 월드 S3 상세 설계 초안

- 작성·확인일: 2026-10-23. 기준 커밋: `fc438a86d56205c3a60038ce8b8a922a072ccbff`.
- 상태: **S3 진행 중 / 제안**. ADR-0001·0002의 확정 사항을 구체화하는 후보안이며 신규 정책 승인이 아닙니다. 스키마·상태 전이·복구 절차는 미구현·미검증입니다. 인벤토리·아이템 저장과 장애 대응의 확정 정책은 [ADR-0003](decisions/0003-inventory-performance-and-recovery.md)을 우선합니다.
- 선행 결과: [S2 빌드/API 검토](stack-build-verification.md). S2 완료는 구현 경로·위험·시험 기준 정리까지이며 런타임 동작 보증이 아닙니다.

## 1. 확정 경계와 모듈 책임 후보

[ADR-0001](decisions/0001-story-world-multiworld.md)의 단일 프로세스 B안, [ADR-0002](decisions/0002-stack-and-world-policies.md)의 Paper 26.2·Java 25·Gradle·단일 JAR 내부 모듈·PostgreSQL·템플릿/콘텐츠 분리·보호/채집 원칙을 유지합니다. [ADR-0003](decisions/0003-inventory-performance-and-recovery.md)에 따라 서버 성능과 원활한 플레이를 복잡한 자동 복구보다 우선합니다. 일반 상자·창고는 월드 파일, 플레이어 인벤토리는 PostgreSQL 중심으로 관리합니다. [ADR-0004](decisions/0004-community-quests-and-chapter-skip.md)의 공동체·개인 퀘스트·분기 고정·장별 스킵 정책도 확정입니다. 아래 구체 자료구조·상태 전이·스키마는 제안이며 미구현·미검증입니다.

| 내부 책임 후보 | 소유할 상태·행위 |
| --- | --- |
| 진행·참가자 | run_id, 멤버십·권한, 세션별 현재 컨텍스트 |
| 월드 수명주기 | 템플릿 복제·배치 매핑·로드·저장·언로드·복구 상태 |
| 콘텐츠 | 불변 템플릿/콘텐츠 버전 참조와 정의 ID 해석 |
| 영속 상태 | 진행별 DAO·개인 상태의 배치 저장·오류 기록. 고비용 체크포인트는 기본 범위 밖 |
| 보호·인벤토리 | 행위별 구역 판정·상태 전환 차단·개인 상태 적용 |
| AI 연결 경계 | 인증된 진행·플레이어 범위의 읽기 DTO 제공. AI 구현 기술은 미정 |

모듈의 실제 패키지·Gradle 멀티프로젝트·연동 라이브러리는 확정하지 않습니다. 월드/플레이어/인벤토리는 서버 스레드에서 캡처·반영하고 DB·파일·AI I/O에는 불변 DTO·바이트만 넘깁니다. event handler에서 DB 응답을 기다리지 않도록 권한·구역·콘텐츠를 버전 고정 캐시로 판정합니다. 필요한 캐시가 없거나 복구 중이면 변경·입장을 차단하는 후보입니다.

## 2. 식별 모델

| 식별자 후보 | 의미·불변식 |
| --- | --- |
| run_id (UUID) | story_run_id의 본문 약칭. 싱글 또는 공동체의 공유 논리 진행; 물리 배치와 분리 |
| 공동체 ID (논리 식별) | 개인 진행의 공동체 범위. story_run_id와의 물리 키 관계·타입은 미정; party_id 대체 스키마 채택이 아님 |
| world_instance_id (UUID) | 해당 진행에 속한 하나의 물리 월드 인스턴스 레코드 |
| logical_role | main, gathering 등 역할. 차원 구성·채집 소유권은 후속 결정 |
| physical_uuid / world_key / directory_ref | 실제 Paper 월드의 UUID·키·허용 루트 하위 경로. 글로벌 UUID·키 충돌 검사 |
| server_id / placement_epoch | 배치 위치와 쓰기 세대. 현재 B안은 한 프로세스지만 A안 이전에 재사용 |
| player_uuid / session_epoch | 계정과 현재 접속/전환 세대. 늦은 DB·AI·이동 응답을 거부하는 기준 |

접근 컨텍스트는 `(mode, scope_id, run_id?, player_uuid, session_epoch, placement_epoch)` 후보로 정의합니다. 클라이언트가 보낸 run_id·월드 이름을 신뢰하지 않고 서버의 참가 관계·배치 매핑과 대조합니다. 물리 월드 ID가 우연히 같더라도 DB 진행 데이터를 선택하는 근거가 되지 않습니다. 하나의 scope는 하나의 데이터 소유권 경계이며 story는 run_id, economy는 후속 결정할 realm 식별자를 쓰는 후보입니다.

## 3. 템플릿·콘텐츠 버전과 최초 복제

- 공간 템플릿은 `(template_id, template_version, checksum, server/data_version)` 불변 manifest로 관리하는 후보입니다. 원본은 플레이 중 쓰지 않는 사전 제작 데이터이며 신규 복제에만 사용합니다.
- 콘텐츠 정의는 `(content_id, content_version)`으로 NPC 배치·대화·퀘스트·안정된 정의 ID를 관리합니다. 템플릿과 별개이며 호환 template 범위·좌표 기준·지원 데이터 버전을 manifest로 연결하는 후보입니다.
- 신규 진행은 사용할 두 버전을 명시적으로 고정합니다. 새 템플릿 추가가 기존 진행의 버전을 자동 변경하지 않습니다. 기존 월드의 신규 지형·건축물 적용 방식은 **미정**이며 덮어쓰기하지 않습니다.
- 기존 콘텐츠 변경은 안정된 quest/NPC ID를 보존하고 이전→새 버전 변환표·검증·백업·되돌리기 조건을 준비한 뒤 적용하는 후보입니다. 호환되지 않는 진행은 구버전을 유지하거나 입장을 막고 검토합니다. 삭제된 정의를 임의 초기화·재보상하지 않습니다.
- 저장소의 콘텐츠 형식(JSON/YAML 등), 버전 게시·배포 도구와 적용 시점은 미정입니다. Paper/Minecraft 데이터 변환의 역방향 호환을 가정하지 않습니다.

최초 생성 후보 절차:

1. DB에서 run·선택 버전·배치 예약을 `PROVISIONING`으로 만들고 operation_id를 고정합니다. 동일 요청은 같은 작업에 합류합니다.
2. I/O 작업에서 허용 루트의 staging 디렉터리에 템플릿을 복제하고 완료 manifest·파일 체크섬을 확인합니다. 경로 탈출·링크·불완전 복사본을 거부합니다. 하드링크 공유 쓰기를 사용하지 않는 후보입니다.
3. 월드 UUID·키·엔티티/NPC 참조의 충돌 및 포털 목적지를 검증합니다. 복제 도구별 식별자 재생성 방법은 S4 검증 과제이며 기존 파일을 추측으로 삭제하지 않습니다.
4. staging 완료를 기록하고 같은 파일시스템의 공개 경로로 전환하는 후보입니다. 디렉터리 전환과 DB 커밋은 원자적이지 않으므로 작업 journal로 재시작 시 중단 지점을 구분합니다.
5. 서버 스레드의 안전한 시점에서 `createWorld`로 로드, 물리 매핑·콘텐츠·진행 데이터 일치 확인 후 준비 완료를 기록합니다. null·예외·기존 다른 월드 반환 시 격리합니다. 입장 허용은 초기화가 모두 성공한 뒤입니다.

## 4. 월드 수명주기 상태 전이 후보

상태는 월드 인스턴스 단위이고 run 전체는 모든 필수 월드·DB 상태가 준비됐을 때만 사용 가능합니다. 아래 전이는 구현·DB에 적용하지 않았습니다.

| 전이 | 사전 조건·처리 | 실패 시 후보 처리 |
| --- | --- | --- |
| PROVISIONING → OFFLINE | 복제·manifest·매핑 완료 | FAILED로 격리, 기존 원본·다른 진행 보존 |
| OFFLINE → LOADING | 참가 권한, 호환 버전, 저장 오류 여부·단일 소유권 확인 | RECOVERY_REQUIRED; 임의로 새 빈 월드 생성 금지 |
| LOADING → READY | Paper 로드·DB·NPC·보호 초기화 완료 | 입장 차단, 이미 로드한 월드 정리 여부 확인 |
| READY → ACTIVE | 현재 세대에 속한 입장 예약·이동·개인 상태 복원 완료 | 이동 실패면 예약 해제 또는 원래 위치 복원 |
| ACTIVE → IDLE | 참가자·입장 중 요청 0, 마지막 퇴장 처리 완료 | 입장 예약이 생기면 ACTIVE 유지 |
| IDLE → QUIESCING | 유휴 대기 만료, 새 입장 예약 차단, 상태 변경·작업 정지 | 재접속은 대기시킴. 유휴 시간 수치는 미정 |
| QUIESCING → SAVING | 비행 중 DB·보상 작업 정리, 사용자·월드 작업 스냅샷 | 타임아웃이면 ERROR_HOLD, 언로드하지 않음 |
| SAVING → UNLOADING | 개인/진행 DB 저장 순서 확인과 일반 월드 저장; 전체 복사·일체형 체크포인트 불필요 | DB/파일 실패 시 ERROR_HOLD, 입장·변경 차단 |
| UNLOADING → OFFLINE | 안전한 호출 시점의 unloadWorld 성공 확인, 참조·티켓 해제 | false·예외면 실제 로드 상태 유지, 재시도 판단 |
| 임의 상태 → RECOVERY_REQUIRED | 손상·저장 결과 불명·소유권 불명 | 해당 범위 데이터 보존·접근 제한·오류 기록 후 관리자 확인. 정상적인 저장 시점 차이만으로 전체 서버 차단 금지 |

메인 스레드에서 실행하더라도 월드 틱 중 로드·언로드는 피해야 합니다. `isTickingWorlds()` 검사와 다음 안전한 스케줄 시점으로 미루는 처리가 필요하며 정확한 시점은 런타임 검증 대상입니다. 월드 저장 방식·writer 대기는 언로드 경계의 필요성과 지연을 검토하며 매 아이템 이동마다 동기 flush를 하지 않습니다. 저장 실패를 무시하거나 성공하지 않은 언로드를 OFFLINE으로 기록하지 않습니다.

접속: 플레이어의 허용 진행 선택 → run 입장 예약·session_epoch 갱신 → 필요한 월드 로드에 합류 → DB 개인 상태 로드 → 서버 스레드에서 인벤토리·위치 적용과 이동 → 성공 확인 후 조작 허용 후보입니다. 초기 스폰/로그인 단계에서 안전한 대기 공간 또는 접속 지연이 가능한지는 S4 검증 과제입니다. 초기 스폰이 타 진행 데이터를 노출하지 않아야 합니다.

퇴장: 진행 전환 전에 GUI·커서·거래·아이템 이동을 안정화하고 개인 상태 캡처·저장 완료 후 세션 소유권을 넘깁니다. 연결 종료 이벤트에서 무기한 DB 대기하지 않으며 실패 시 저장 미완료 상태로 잠그고 재접속 복원을 중단하는 후보입니다. 단순 로그아웃은 공동체 구성원 변경이 아닙니다. 게임 내 파티 탈퇴 시스템은 구현하지 않습니다. 일반 자동 저장 초기값은 30초이며 조정할 수 있습니다. 장애 시 허용 유실 시간의 보장값은 확정하지 않았습니다.

이동: `teleportAsync` future를 메인 스레드에서 join/get하지 않습니다. 완료 후 Boolean·예외·세션·배치·참가 권한을 확인합니다. 포털·사망·부활·명령 이동도 같은 진행 입장 경계를 사용합니다. 베드·부활 위치는 run과 논리 월드 역할을 포함하며 타 진행으로 자동 복귀시키지 않습니다.

## 5. PostgreSQL 데이터 범위와 스키마 후보

SQL·DB 서버 실행은 하지 않았습니다. 아래는 물리 DDL이 아닌 키·열·제약 후보입니다. PostgreSQL 세부 버전·마이그레이션 도구·드라이버·풀과 DB 인스턴스/스키마 분리 방식은 미정입니다.

| 테이블 후보 | 핵심 열·키·제약 |
| --- | --- |
| progress_scope | scope_id UUID PK, mode(story/economy), 상태. UNIQUE(scope_id,mode) |
| story_run | run_id UUID PK=scope_id FK, 공동체 참조의 물리 표현 미정, content_id/version, state, revision bigint, last_saved_at. scope mode=story는 검증/복합 FK로 강제 |
| 공동체 구성원 관계 (물리 테이블·키 미정) | 공동체 ID·player_uuid의 소속 관계와 run 매핑. role·가입/변경 절차는 미정. 기존 party_member 후보를 확정 대체 테이블로 승계하지 않음 |
| world_instance | world_id UUID PK, run_id FK, logical_role, template_id/version, physical_uuid, world_key, directory_ref, server_id, placement_epoch, state. UNIQUE(run_id,world_id), 물리 배치 충돌 제약 |
| player_progress | PK(run_id,player_uuid), revision, last_world_id, 위치·체력·XP·개인 변수. 공동체 구성원 관계와의 참조 제약은 키 결정 후 검토; FK(run_id,last_world_id)→world_instance |
| quest_progress | PK(run_id,owner_kind,owner_id,quest_id), content_version, stage, variables jsonb, revision. 공동체 중요 퀘스트와 개인 퀘스트를 구별. 개인 논리 키는 공동체 ID·player_uuid·quest_id; owner 물리 표현·소유 유형 제약 미정 |
| npc_relation | PK(run_id,player_uuid,npc_definition_id), 관계 값·revision. 참가자 복합 FK |
| story_branch / npc_state | PK(run_id,definition_id), 고정 분기 선택·생존/활동 상태·revision·content_version. run 공통 상태; 개인 따라잡기의 쓰기 대상에서 제외 |
| inventory_snapshot | PK(scope_id,player_uuid), db_revision, payload bytea, format_version, minecraft_data_version, checksum, saved_at. 배치 저장용 현재 상태이며 무손실 복원 이력이 아님 |
| transfer 상태 | 기본은 세션 내 단일 전환·source/target scope와 revision 검사. 영속 상세 journal은 단순하고 비용이 낮을 때만 선택 검토 |
| reward marker | run/quest/회차/player의 고유 지급 키, 지급 상태·관련 inventory revision. 중복 지급 방지·상태 즉시 저장은 확정, 열/트랜잭션 구성은 후보 |
| wallet | PK(scope_id,account_id,currency_id), amount·revision. 화폐형·잔액 제약·계정 모델은 후보이며 경제 규칙 확정이 아님 |
| economic_transaction | transaction_id UUID PK, scope·종류·참가자·서버 검증 요청 요약/hash·금액·아이템 요약·결과 revision·DB 완료 시각. 거래별 고유 키로 중복 억제. 필수 거래 기록이며 전체 이동 원장/보관함이 아님 |
| 선택 확장 | checkpoint/checkpoint_player·거래 보관함·전체 이동 원장은 기본 스키마에서 제외. 필요·성능을 별도 검토 |
| lifecycle_operation | operation_id PK, run_id/world_id, 종류·전이 전후 상태·epoch·단계·오류. 재시작 복구용 journal |

외래 키는 run_id를 함께 포함해 다른 진행의 월드·참가자를 가리키지 못하게 하는 후보입니다. 예: player_progress의 `(run_id,last_world_id)`는 world_instance의 동일 복합 키만 참조합니다. 단순 world_id FK와 애플리케이션 필터만으로 이 교차 참조를 맡기지 않습니다. [PostgreSQL 제약 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)를 근거로 검토했으며 제약 간 정확한 DDL·마이그레이션은 미시험입니다.

jsonb는 유동적인 콘텐츠 변수에만 사용하고 run·소유자·버전·참조 무결성은 구조화된 열과 제약으로 유지하는 후보입니다. owner_kind별 FK가 복잡하면 quest_progress를 run_quest와 player_quest로 분리하는 대안이 있습니다. 단일 테이블/분리 테이블 선택은 제안 상태입니다.

월드 파일은 블록·청크·컨테이너·엔티티의 물리 상태를 소유합니다. PostgreSQL은 진행·관계·분기·참가자·개인 상태·작업 이력을 소유합니다. 엔티티는 논리 NPC ID를 서버 매핑으로 연결하고 DB의 npc_state에서 재구성하되 중복 생성·삭제 판정은 검증합니다. vanilla playerdata와 DB가 인벤토리를 동시에 독립적인 정본으로 저장하지 않도록 플레이어 인벤토리를 PostgreSQL 중심으로 관리한다는 확정 원칙 아래 DB snapshot을 읽기 기준으로 두고 서버 파일의 초기 로드 상태를 안전한 입장 절차에서 교체하는 설계를 검토합니다. 구현 라이브러리와 이벤트 순서는 미정입니다.

진행 유출 방지: 모든 DAO는 서버에서 검증된 scope 컨텍스트를 필수로 받으며 UUID만으로 조회하지 않습니다. 캐시·작업·AI 조회 키에 mode/scope_id와 필요 시 player_uuid·epoch를 넣습니다. RLS는 보조 후보이며 전용 역할·풀 연결 컨텍스트 초기화까지 시험하기 전 격리 보장으로 쓰지 않습니다. 서버 명령·콘텐츠 스크립트·관리 도구도 같은 경계를 통과해야 합니다.

## 6. 공동체 진행과 인벤토리 전환

확정 정책은 [ADR-0004](decisions/0004-community-quests-and-chapter-skip.md)를 따릅니다. 공동체는 같은 story_run_id·월드·세계 변화·주요 스토리 결과를 공유하며 개인 인벤토리·퀘스트 완료·보상 기록은 분리합니다. 게임 내 파티 탈퇴는 구현하지 않습니다. 기존 party_id·party_member·파티장·탈퇴·분할·병합 후보는 현행 구현 요구에서 제외하며 대체 물리 스키마는 채택하지 않습니다. 공동체 가입 및 관리자 구성원 변경은 미정입니다.

### 공동체·개인 진행 모델 후보

| 논리 상태 | 범위·불변식 | 구체 구현 후보 (미확정) |
| --- | --- | --- |
| 공동체 중요 퀘스트 | 공동체 ID / story_run_id. 중요 메인·분기점 | 개인 상태와 분리한 레코드, revision 비교로 동시 진행 요청 경합 감지 |
| 개인 퀘스트 | 공동체 ID + 플레이어 UUID + quest_id | 독립 stage·완료 상태; A의 완료를 B에게 복사하지 않음 |
| 공동체 분기·세계 효과 | 공동체 ID + branch/effect 정의 ID | 확정 선택 변경 거부·효과 적용 식별자로 정상 중복 요청 억제. 개인 따라잡기 경로는 공유 NPC/분기/월드 쓰기 권한 없음 |
| 개인 장 진행 | 공동체 ID + 플레이어 UUID + chapter_id | 직접 플레이 완료 / 스킵 / 선행 조건 충족을 구분하는 상태 후보. 실제 enum·테이블 미정 |
| 장 콘텐츠 정의 | 콘텐츠 버전 + chapter_id | 메인·필수 길목 목록과 일반 서브 목록 분리. 누락·잘못된 의존성 검사는 콘텐츠 시험 대상 |
| 개인 보상 기록 | 공동체 범위 + 플레이어 UUID + 지급 식별자 | ADR-0003의 중복 방지·지급 상태 즉시 저장. 스킵·재참여의 지급 여부는 결정하지 않음 |

공동체 ID와 story_run_id의 동일 키 여부, 소속 관계의 물리 DDL과 소유권 제약은 미정입니다. 논리 범위를 명시한 것이 새로운 테이블/권한 정책 승인은 아닙니다.

### 공동체 중요 퀘스트 조건 검사

진행 조건은 `접속 중인 공동체 구성원 모두가 해당 퀘스트 조건 충족`입니다. 단 한 명의 미충족으로 진행이 막히며 비접속자는 제외합니다. 근처 플레이어·임의 참가자만 검사하거나 모든 등록 구성원의 동시 접속을 요구하지 않습니다. 조건 충족은 개인 퀘스트 일괄 완료·보상 지급과 구분합니다.

후보 흐름은 인증된 공동체/진행 컨텍스트 확인 → 접속 구성원과 개인 선행 조건 조회 → 전원 충족 판정 → 공동체 진행 변경 요청 순서입니다. 검사·확정 사이 접속자 변화의 기준 시점, 스냅샷 고정/재검사/중단 여부는 **미정**입니다. 특정 동작을 기본으로 채택하지 않으며 정책 결정 전 변동 상황의 성공 기준을 확정하지 않습니다. 분기 선택 투표·파티장 결정 등 의사결정 방식도 미정입니다.

### 고정 분기와 장별 따라잡기·스킵

공동체가 이미 진행한 장을 놓친 개인은 각 장을 직접 플레이하거나 스킵할 수 있습니다. 선택은 장마다 독립적입니다. 스킵 범위는 그 장의 메인과 진행에 필요한 길목 퀘스트이며 다음 장의 개인 선행 조건을 충족합니다. 일반 서브 퀘스트는 일괄 스킵으로 처리하지 않습니다. 미래의 미진행 장을 임의로 해금하는 정책은 채택하지 않습니다.

직접 따라잡기는 공동체가 확정한 분기만 읽고 개인 상태를 변경합니다. 완료자는 지원할 수 있지만 개인 지원/스킵 요청으로 공유 NPC 상태·월드 효과를 다시 쓰거나 공동체 분기를 되돌리지 않습니다. 공유 효과 적용 경로와 개인 따라잡기 경로를 분리하고 요청 ID·revision으로 정상 중복 실행을 억제하는 후보입니다. 공유 월드에서 과거 인스턴스·연출·NPC를 재현할 방법은 미정이며 별도 검증이 필요합니다.

스킵을 실제 플레이 완료나 자동 보상 지급으로 기록하지 않습니다. 개인 장 결과·선행 조건과 보상 기록을 구분합니다. 스킵 보상·감소 비율 및 완료자의 재참여 보상은 미정입니다. DB·게임 메모리·월드 파일은 자동 원자적이지 않으며 고비용 체크포인트/완전 자동 복구를 추가하지 않습니다. 실패 시 성공 오기록·공유 효과 재적용을 피하도록 상태 확인·최소 오류 기록과 ADR-0003의 수동 대응을 검토합니다.

스토리 scope와 경제 scope 인벤토리는 독립 snapshot입니다. 일반 상자·창고 내용은 월드 파일이 소유하며 PostgreSQL에 매 이동을 복제하지 않습니다. 엔더 상자·커서·열린 GUI 등 개인 상태의 정확한 범위와 저장 포맷은 상세 설계 대상으로 남깁니다.

### 6.1 확정된 저장 정책

| 대상·계기 | 확정 정책 |
| --- | --- |
| 일반 플레이어 인벤토리 | 변경된 데이터만 **30초 간격의 비동기 배치 저장**. 30초는 성능 측정 후 조정할 수 있는 초기 운영값 |
| 일반 상자·창고 | Minecraft 월드 파일 저장. 클릭/이동마다 DB·동기 디스크 flush 불필요 |
| NPC 상점 구매·판매 / 플레이어 간 경제 거래 | 30초를 기다리지 않고 거래마다 즉시 DB 반영 |
| 퀘스트 보상 | 중복 지급 방지, 지급 상태 즉시 저장 방향 |
| 스토리·경제 월드 전환 | 이전 인벤토리 저장 완료 확인 후 전환 |

즉시 저장은 요청을 주기 대기열에서 30초 대기시키지 않는다는 뜻입니다. DB는 비동기로 처리하고 메인 스레드에서 SQL/future를 동기 대기하지 않습니다. 위는 확정 정책이며 아래 저장 자료구조·잠금·트랜잭션 구성·실패 상태는 구현 후보입니다. 이번에 DB·게임 코드를 실행하지 않았습니다.

### 6.2 일반 저장과 충돌 방지 후보

1. 정상 메모리 변경마다 dirty 표식과 `memory_version`을 올립니다. 초기 30초 주기에 dirty인 플레이어/scope만 캡처해 불변 DTO로 비동기 저장합니다. 변경 없는 인벤토리/진행은 쓰지 않습니다. 슬롯별 SQL delta를 강제하지 않고 dirty inventory 단위 snapshot도 후보입니다. 배치 크기·주기 분산은 별도 측정합니다.
2. scope/player별 일반 저장·거래·보상·전환을 같은 저장 조정자에서 순서화합니다. 한 소유자에 저장 하나만 in-flight로 두는 간결한 큐를 기본 후보로 하고, 큐의 오래된 일반 snapshot은 합치거나 폐기합니다. 거래는 이전 in-flight 일반 저장이 완료/실패 확정되기 전 추월하지 않습니다. 둘 이상의 플레이어를 묶는 거래는 참가자 모두의 큐에 장벽을 둡니다.
3. 메모리 변경 번호와 DB의 `db_revision`을 구분합니다. DB 쓰기는 예상 db_revision·소유 세션을 확인하고 성공 시 revision을 올리는 후보입니다. 오래된 callback/세션의 결과를 최신으로 채택하지 않으며 충돌 시 저장 성공으로 처리하지 않습니다.
4. 일반 저장 성공 때 캡처한 memory_version까지만 저장 완료로 표시합니다. 캡처 이후 변경이 있으면 dirty를 유지합니다. 거래 성공 뒤 거래 이전 snapshot을 재전송하거나, 오래된 저장 완료가 dirty를 지우지 못하도록 합니다.
5. 30초는 스케줄러·큐·실제 DB 지연 때문에 정확한 디스크 내구성 시각이나 최대 유실 30초를 보장하지 않습니다. DB 실패 시 dirty를 유지하고 재시도 한도를 둡니다. 클릭마다 SQL·전체 이동 로그·동기 flush를 수행하지 않습니다.

### 6.3 비동기 경제 거래 흐름 후보

NPC 구매/판매와 플레이어 간 거래에 동일한 조정 경로를 사용합니다. 거래·아이템·화폐 규칙은 서버에서 검증하며 클라이언트가 보낸 금액·보유량·revision을 신뢰하지 않습니다. 아래는 DB 트랜잭션 후보이지 실행 검증 결과가 아닙니다.

| 단계 | 서버 스레드 / 비동기 처리 | 조건·경계 |
| --- | --- | --- |
| 요청 식별 | 서버가 transaction_id와 scope·참가자·가격/조건 요약을 묶고 같은 요청에 같은 ID 사용 | 중복 확인·다른 payload로 ID 재사용 거부. 성공 거래를 새 ID로 재시도하지 않음 |
| 참가자 예약 | 서버 스레드에서 해당 참가자와 필요한 상태의 중복 거래·전환을 차단 | 전체 서버 잠금 없음. 참가자 큐 예약 순서를 일정하게 두어 두 플레이어 거래 간 교착 방지 |
| 이전 저장 정리 | 비동기로 이미 진행 중인 일반 저장 결과 확정을 기다리고 대기 중 옛 snapshot 정리 | 메인 스레드는 대기하지 않음. 타임아웃·저장 실패는 거래 진행 중단, 성공 처리 금지 |
| 짧은 변경 보호 | 최신 캡처 직전~결과 적용 사이 필요한 참가자 상태만 보호 | 전체 snapshot을 쓰는 후보에서는 관련 플레이어 인벤토리 전체가 보호 범위. 슬롯 단위만 막으면 비거래 슬롯의 최신 변경을 덮을 수 있어 적용 금지. 외부 드롭/획득·죽음·상자/자동 이동·전환 처리와 경합도 정해야 함 |
| 최신 상태 확정 | 서버 스레드로 돌아와 세션·scope·memory_version, 현재 아이템 종류/수량/메타데이터·수용 공간·거래 조건 검증 후 최신 snapshot과 거래 후 상태를 캡처 | DB에 없는 최신 획득·소비·상자 이동까지 포함. 검증 전에 캡처한 오래된 상태로 거래하지 않음 |
| DB 트랜잭션 | 비동기로 관련 inventory·wallet 행을 일정한 키 순서로 잠그거나 예상 revision으로 검증, 거래 ID 중복 확인, 잔액·정책 재검증, **최신 snapshot + 거래 delta**에서 계산한 최종 인벤토리·화폐·거래 기록을 같은 트랜잭션에 저장 | 두 참가자의 인벤토리와 관련 화폐를 함께 반영, 부분 commit 금지. 조건 불일치면 전체 rollback. DB 작업 동안 서버 스레드를 기다리게 하지 않음 |
| 커밋 확인 | DB commit 결과와 최종 revision을 반환 | 정상 응답 없는 타임아웃은 rollback이라고 단정하지 않음. 커밋 전 임의 아이템/화폐 지급 금지 |
| 메모리 적용 | 서버 스레드에서 세션·scope·보호 상태를 재확인해 커밋된 최종 상태를 한 번 적용 | callback 중복·재접속/이탈 뒤 stale 적용 금지. DB 성공만으로 아직 메모리 미반영인 거래를 플레이 완료로 표시하지 않음 |
| 완료 | DB 확인과 필요한 메모리 적용 완료 후 성공 표시·해당 보호 해제 | 이후 일반 저장은 새 db_revision을 기준으로 재개. 적용 중 변경이 남으면 dirty 유지 |

거래 시작 시 **DB의 30초 전 snapshot을 거래 기준으로 그대로 쓰지 않습니다.** 이전 저장이 끝난 뒤 확보한 현재 메모리 snapshot의 미저장 변경과 거래 delta를 같은 즉시 저장에 포함합니다. 별도 선행 flush를 선택하더라도 source 저장과 거래 사이 보호·순서가 유지돼야 하며, flush만 하고 상태를 다시 검증하지 않는 흐름은 허용하지 않습니다.

재전송된 transaction_id가 DB에서 이미 완료됐다면 기존 결과를 조회하되 아이템·화폐 delta를 다시 실행하지 않습니다. 이미 적용한 세션에 전체 snapshot을 다시 덮어쓰지도 않습니다. 프로세스 재시작 뒤에는 인벤토리의 DB 최신 상태를 정상 로그인 경로로 읽는 방향이며 오래된 거래 snapshot을 무조건 재지급하지 않습니다.

경제 화폐·가격·세금·상점 재고 정책과 잔액 캐시, 교차 서버 조정 방식은 미정입니다. 현재 후보는 참가자의 한 소유 프로세스/세션에서 처리하는 경로이며 경제 서버 분리나 분산 원자성을 확정하지 않습니다. 관련 상점 DB 재고가 생기면 같은 DB 경계의 행으로 검토하되 일반 상자·월드 파일은 여기에 포함하지 않습니다.

행 잠금·고유 키 후보는 [PostgreSQL 잠금](https://www.postgresql.org/docs/current/explicit-locking.html)과 [제약](https://www.postgresql.org/docs/current/ddl-constraints.html)을 참고합니다. 실제 SQL·격리 수준·연결 풀·쿼리/잠금 타임아웃·재시도 값은 미정입니다. 영속 거래 식별·중복 방지는 필수 요구이며 그 구현을 고비용 escrow나 전체 아이템 이동 원장으로 확대하지 않습니다.

### 6.4 실패·불명확 결과·메모리 반영 후보

| 결과 | 처리 후보 |
| --- | --- |
| 검증 실패·확실한 rollback | 거래 delta를 메모리에 선반영하지 않아 성공 표시/지급 없음. 원래 최신 상태·dirty를 유지하고 해당 보호 해제. 단순 ID 중복은 새 거래로 실행하지 않음 |
| 일반 저장 revision 충돌 | 무조건 UPDATE/성공 처리 금지. 오래된 snapshot 폐기·현재 소유 세션/DB 상태 확인 후 새 캡처 필요. 영향을 받은 플레이어만 처리 |
| commit 결과 불명·연결 종료 | 같은 transaction_id의 상태를 제한적으로 조회. 행 미조회만으로 원래 트랜잭션이 영원히 실패했다고 단정하지 않으며 실행 종료/잠금 상태까지 확인 전 재지급·새 ID 재시도·오래된 자동 저장 금지 |
| DB commit 성공 후 연결 끊김/메모리 적용 실패 | 성공 UI·추가 지급 금지. 해당 인벤토리/거래를 적용 미완료로 표시, DB 최종 상태와 세션을 확인한 재접속/재적용 후보 또는 관리자 수동 조정. stale 메모리 자동 저장으로 커밋된 DB를 덮지 않음 |
| 재시도/보호 시간 한도 초과 | 메인 스레드나 전체 서버를 막지 않고 해당 거래·필요한 개인 상태만 보류/접근 제한 후 최소 오류 기록·관리자 확인. 결과 미확정 상태를 풀어 중복 거래를 허용하지 않음 |

게임 메모리 적용과 PostgreSQL commit은 자동으로 원자적이지 않습니다. 참가자 보호·revision·고유 키는 정상 경쟁을 제어하는 후보일 뿐 모든 crash window를 없애지 않습니다. 일반 상자 입출고·드롭·월드 파일을 DB transaction으로 묶지 않습니다. 비정상 종료 때 일부 유실·복사는 ADR-0003의 로그/백업 기반 관리자 수동 대응을 허용합니다.

### 6.5 퀘스트 보상·전환·성능 후보

퀘스트 보상은 `(run_id,quest_id,completion_sequence,player_uuid)` 같은 안정된 지급 키와 지급 상태를 즉시 저장하는 후보입니다. 같은 보상 청구를 다시 실행하지 않으며 아이템·화폐 보상과 지급 표식의 DB 반영을 같은 저장 조정 경로에서 검토합니다. DB 실패/불명 결과에 지급 완료를 알리거나 재지급하지 않습니다. 반복 퀘스트 회차·공동체 보상·가득 찬 인벤토리의 처리 정책은 미정입니다. 복잡한 보관함을 기본 해결책으로 추가하지 않습니다.

스토리·경제 전환은 참가자의 미완료 거래/보상·저장을 정리하고 **이전 인벤토리의 저장 완료를 확인한 뒤** target 상태 적용·이동·컨텍스트 전환을 진행하는 후보입니다. 30초 자동 저장을 기다리는 방식이 아니며 source 저장 실패/거래 결과 불명 상태에서는 전환을 완료하지 않습니다. 로그아웃·유휴 언로드·정상 종료의 대기 한도와 실패 처리는 후속 상세 설계 대상입니다.

연결 풀·제한된 I/O worker·대기열 상한·타임아웃·제한 재시도를 간결하게 적용하는 후보입니다. 거래 처리는 필요한 플레이어·아이템 상태에 한정하고 전체 서버·모든 플레이어를 잠그지 않습니다. 필수 SQL 트랜잭션·중복 억제는 유지하고 부가 안전장치·과도한 로그·전체 이동 이력·고비용 checkpoint·escrow를 제외합니다. 지연·처리량 기준은 성능 측정 전에 정하며 이번에 검증하지 않았습니다.

ItemStack 포맷·Minecraft 버전·체크섬 등 경량 표식은 검토할 수 있지만 자동 무손실 복원은 보장하지 않습니다. 손상·미지원 포맷은 빈 데이터로 덮어쓰지 않습니다.

## 7. 성능 우선 저장·수동 장애 대응

**확정 우선순위: 서버 성능과 원활한 플레이 > 복잡한 자동 장애 복구.** 월드 파일과 PostgreSQL은 서로 다른 시점에 저장될 수 있습니다. 정상 플레이의 기본 중복·유실 예방은 유지하지만 비정상 종료 때 일부 아이템 유실·복사가 생길 수 있음을 수용합니다. 자동 무손실 복구나 모든 상황의 아이템 복사 방지를 보장하지 않습니다.

일상 경로는 Minecraft 일반 월드 저장과 변경된 플레이어 인벤토리의 30초 비동기 배치 저장을 사용합니다. 경제 거래·퀘스트 지급 상태·이전 인벤토리 전환 저장은 30초를 기다리지 않는 예외입니다. 유휴 저장·언로드마다 전체 월드 복사·파일/DB 동시 세대 확정·fsync 묶음·checkpoint 테이블을 요구하지 않습니다. 복잡한 거래 보관 시스템, 고비용 체크포인트·완전 자동 복구는 필수 범위에서 제외했습니다. 이전 초안의 일체형 checkpoint 절차는 ADR-0003으로 기본 후보에서 철회했으며 이전 Git 기록으로 확인할 수 있습니다.

백업 자체와 승인된 유지보수·A안 이전의 사전 보존/롤백 계획은 유지합니다. 백업의 주기·보존·비용은 별도 설계하며 정상 클릭 처리와 연결하지 않습니다. 가용 백업도 DB·월드 시점이 다를 수 있어 자동 일치·정전 내구성을 가정하지 않습니다.

### 최소 오류 기록 후보

저장 실패·재시도 한도 초과·손상 payload·모호한 전환/거래/지급·비정상 종료 감지를 기록합니다. 거래별 DB 기록은 별도로 유지하며 일반 이동 전체 로그와 구분합니다. 최소 필드는 시간, 오류 유형, scope/run/world/player 식별자, 세션/요청 ID(있는 경우), 저장 revision·마지막 성공 시각, 처리 단계·오류 요약·조치 결과입니다. 아이템 관련 정보는 이미 확인 가능한 요약만 남기며 모든 이동·payload 전체를 동기 로그로 저장하지 않습니다. 같은 오류는 집계·빈도 제한하고 불필요한 개인 정보·인증 정보는 기록하지 않습니다. 보존·회전·권한은 미정입니다.

### 관리자 대응 후보

| 상황 | 기본 처리·관리자 조치 |
| --- | --- |
| DB 저장 실패 | 해당 개인 상태의 dirty/오류 유지·제한된 재시도·기록. 전환/복원만 필요한 범위에서 막고, 무관한 진행의 전체 정지를 기본으로 하지 않음 |
| 월드 저장·언로드 실패 | 성공으로 오기록하지 않고 실제 로드 상태 유지, 해당 진행 오류 기록·관리자 확인. 강제 삭제/자동 빈 월드 대체 금지 |
| 비정상 종료 후 아이템 불일치 의심 | 로그·마지막 성공 저장 시점·가용 DB/월드 백업을 대조. 모든 플레이어를 자동 rollback하거나 세대가 다르다는 이유만으로 전체 입장을 차단하지 않음 |
| payload 손상·버전 미지원·진행 소유권 불명 | 해당 범위 접근 제한, 원본 보존 후 관리자가 복구·변환·수동 조정 판단 |
| 수동 지급·회수·백업 복원 | 조치 전 대상 데이터 보존·중복 작업 확인, 승인된 범위에서만 적용. 사유·대상·수량·조치자·시각·근거·결과 기록 |

관리자는 영향을 받은 플레이어/진행·상자 위치와 오류 시점을 확인하고, 필요한 범위만 임시 제한한 뒤 로그·백업·현재 상태를 비교하는 방향입니다. 일부 유실·복사는 수동 지급/회수·상태 보정으로 처리할 수 있습니다. 근거가 부족하면 불확실성을 기록하고 자동 재지급하지 않습니다. 상자 또는 인벤토리 한쪽만 과거 상태로 복원하면 불일치가 커질 수 있으므로 범위·시점을 함께 검토합니다. 정확한 전체 이동 재구성은 필수도 보장도 아닙니다.

이번 작업에서 로그·관리 명령·복원 도구를 구현하거나 운영 데이터를 보정하지 않았습니다. 실제 데이터 덮어쓰기·복원·삭제·서비스 조작에는 별도 승인이 필요합니다. 자동 복구 확대는 경량성·성능 근거가 있을 때만 별도로 검토합니다.

## 8. 보호와 자원 채집

확정 원칙: 스토리는 전체 보호·지정 구역 건축 허용, 경제는 주요 도시·공용 시설 등 지정 구역 보호·일반 지역 자유도 확대, 주요 자원 수급은 양쪽 전용 채집 인던 중심입니다. 건축 지형 변경과 채집은 별도 정책입니다.

구역 후보 키는 `(scope_id, logical_world_role, region_id, policy_version)`이며 정수 블록 좌표 AABB·허용 행위·권한을 갖습니다. 경계 포함 규칙과 구역 중첩 우선순위는 S3 검토 항목입니다. 기본 후보는 명시적 금지 우선, 불명확한 진행/정책은 변경 거부입니다. 경제 일반 지역도 다른 진행 접근·아이템 복제·시스템 시설 변경을 허용하는 뜻은 아닙니다.

| 행위 축 | 후보 판정·이벤트 | 미검증 위험 |
| --- | --- | --- |
| 직접 건축·철거 | BlockBreak/Place/MultiPlace, 버킷·아이템 상호작용 | 양손·다중 블록·지정 구역 경계에서 일부만 허용되는 경우 |
| 상자·기능 블록·엔티티 | PlayerInteract·InventoryClick/Drag, entity interact·damage, hanging/vehicle 등 | 건축 허용이 상자/시설 사용 권한까지 자동 부여하지 않음 |
| 간접 변경 | explosion·piston extend/retract·fluid·fire·growth·entity block change 등 | 시작점 밖에서 보호 구역으로 유입, 목적지·모든 영향 블록 검사 |
| 외부 코드·명령 | 명령·콘텐츠 변경을 내부 정책 API로 통일 | 이벤트를 발생시키지 않는 외부 플러그인 직접 변경은 이벤트 취소만으로 막을 수 없음 |
| 채집 | 전용 인던과 scope별 채집/반출 허용 규칙 별도 적용 | 생성·초기화·재생성·반출·공유 여부는 미정 |

이벤트 카탈로그는 구현 전 더 구체화해야 하며 위 전체 이벤트의 컴파일·런타임 검증을 했다는 뜻이 아닙니다. S2에서는 대표적인 일부 이벤트 API만 참조 컴파일했습니다. PlayerInteract는 블록 사용·손 아이템 사용을 구분하고 양손 이벤트를 고려합니다. 무조건 모든 인터랙션을 취소하면 정상 퀘스트·스마트폰도 막을 수 있으므로 행위별 정책이 필요합니다.

채집 인던이 개인/공동체/공용인지, 독립 서버인지, 입장·귀환·재생성 시점과 아이템 귀속은 **미정**입니다. 후보로 부모 scope의 인벤토리 문맥을 유지할 수 있으나 이는 확정하지 않습니다. 건축 구역에서 부서진 블록의 드롭·광물·작물 정책도 미정이며 건축 허용을 무제한 자원 채집 허용으로 해석하지 않습니다. 인던 수명주기를 설계하기 전 실제 자동 초기화를 만들지 않습니다.

## 9. 후속 테스트와 성공 기준 (모두 미실행)

시험은 별도 승인된 환경·테스트 데이터에서 수행합니다. 실패·미실행을 성공으로 표시하지 않습니다. 횟수·동시 이용량·시간/메모리 한계는 시험 시작 전 확정하며 다음은 기능 성공 기준 후보입니다.

| ID·단계 | 시험 | 성공 기준 |
| --- | --- | --- |
| T1 / S4 | 두 템플릿 복제·로드, 반복 요청 | 서로 다른 물리 식별자·같은 요청 하나의 작업, 원본/기존 월드 보존. null·예외 시 타 진행/빈 월드로 대체 안 함 |
| T2 / S4 | 공동체 동시 입장·마지막 퇴장·재접속 경합 | 하나의 로드/저장 소유자, 다른 진행 접근 0건, 상태 준비 전 조작 불가 |
| T3 / S4 | unload false·DB 타임아웃·재시도 한도 주입 | 저장 성공 오기록 없음, 오류·원본 보존, 해당 범위 제한·관리자 대응 가능, 무한 대기·전체 잠금 없음 |
| T4 / S4 | 저장·전환 중 강제 종료와 수동 대응 연습 | 시점 불일치·영향과 확인 가능한 근거 기록, 관리자 조치 절차 확인. 일부 장애 유실·복사 허용; 자동 무손실·모든 장애 중복 0건은 요구하지 않음 |
| T5 / S4 | 정상 상자 입출고·드롭·보상·동시 저장·재접속·story/economy 전환 | 정상 경로의 중복·유실 없음, scope별 격리·저장 순서 확인. 손상 payload 덮어쓰기 금지. 강제 종료는 T4로 분리 |
| T5a / S4 | dirty·미변경 상태와 30초 자동 저장 | dirty 대상만 저장, 새 변경의 dirty 유지, 주기 설정 조정 가능, 매 클릭 SQL 없음 |
| T5b / S4 | 미저장 획득/소비 뒤 NPC 구매·판매·두 플레이어 거래 | 최신 보유 상태·수용 공간 검증, 양측 최종 인벤토리·화폐·거래 기록 일관, 30초 주기를 기다리지 않음 |
| T5c / S4 | 이전 자동 저장 지연·중복 callback·동시 거래·보상·전환 | 오래된 snapshot 덮어쓰기/dirty 초기화 없음, 같은 거래/보상 한 번만 반영, source 저장 성공 전 전환 안 됨 |
| T5d / S4 | rollback·commit 응답 소실·DB 성공 후 적용 실패 | 실패/불명 결과에 성공 UI·중복 지급 없음, 거래 ID 조회/해당 상태 보류·수동 대응 확인. 메모리·DB 원자성 보장은 아님 |
| T6 / S4 | DB 교차 run 참조·권한 위조·오래된 session 응답 | 복합 FK·DAO가 거부, 타 진행 조회/변경 0건. SQL migration·동시성 시험 필요 |
| T7 / S4 | 구역 내외 건축·다중 블록·유체·피스톤·폭발·엔티티·양손 우회 | 보호 구역의 비허용 변화 0건, 허용 건축/정상 퀘스트 동작, 전체 변경 전후 대조 |
| T8 / S4 | 콘텐츠·템플릿 버전 추가/비호환 migration | 기존 월드 불변, 삭제/변경 ID가 진행 초기화·중복 보상을 유발하지 않음, rollback 세대 확인 |
| T9 / S4 | async DB·I/O 지연과 async 접근 감시 | Bukkit 비동기 위반·메인 스레드 future 대기 0건, 늦은 응답이 새 세션 상태 변경하지 않음 |
| T10 / S5 | AI 검색·캐시·대화·권한 변경 중 지연 응답 | 다른 진행/개인의 비공개 정보 유출 0건. 모델·AI 구현은 미정 |
| T11 / S6 | 활성 진행·플레이어·NPC·AI 중첩 부하 | 사전 합의 CPU·RAM·I/O·MSPT/GC·입장 지연 한계 만족, 반복 언로드 후 지속 참조 누수 없음. 클릭별 DB 트랜잭션/flush 부재 확인, 선택 안전장치의 부하·지연이 크면 제외 |

S3 완료 전에는 아래 정책 제안 검토, 스키마/전이/복구 모순 해소, 콘텐츠 참조·보호 이벤트 목록과 검증 입력/결과 기록 형식까지 준비해야 합니다. 현재는 초안 작성만 완료했고 구현을 시작하지 않았습니다.

### 공동체 정책 시험 명세 (구현 전 준비, 모두 미실행)

| ID | 입력·상황 | 성공 기준 |
| --- | --- | --- |
| C1 | 같은 공동체 A만 개인 길목/서브 완료 | B의 개인 완료·보상 기록이 자동 변경되지 않음 |
| C2 | 고정 접속 명단 A·B 모두 중요 퀘스트 조건 충족 / B만 미충족 | 전자는 진행 가능, 후자는 차단; 개인 일괄 완료로 해석하지 않음 |
| C3 | A만 접속·충족, 미충족 B는 비접속 | B 때문에 차단하지 않음; 전원 동시 접속 불필요 |
| C4 | 공동체 분기 X 확정 후 뒤늦은 개인 진행 | X 라인만 진행 가능, Y 선택·공유 분기 변경 불가 |
| C5 | 완료자가 과거 장 직접 플레이 지원·반복 요청 | 공유 NPC·세계 효과 전후 동일, 기존 분기 유지; 재참여 보상 기대값은 미정 |
| C6 | 놓친 장 N 스킵 | N 메인·필수 길목 스킵 및 N+1 개인 선행 충족, 일반 서브 일괄 스킵 없음; 보상 기대값 미정 |
| C7 | N 직접 플레이·N+1 스킵 등 장마다 다른 선택 | 선택 독립, 실제 플레이/스킵 구별, 공동체 분기·월드 변화 불변 |
| C8 | 두 공동체의 같은 quest/chapter ID·서로 다른 플레이어, 중복 스킵 요청·재접속 | 다른 공동체/개인 상태 유출 없음, 개인 결과 보존·공유 효과 재적용 없음 |
| C9 | 중요 퀘스트 검사/확정 중 접속자 변경, 분기 의사결정, 과거 NPC 재현 | 정책·방법 미정으로 기대 결과 확정 보류. 결정 후 경합·연출 시험 추가; 통과로 기록하지 않음 |

C1~C8도 실제 구현과 실행 없이 통과로 표시하지 않습니다. 보상·가입·관리자 변경 절차는 정책 승인 후 시험을 보완합니다. 분기/효과 상태의 DB 실패·메모리 반영 실패·재접속 시험은 정상 중복 방지와 오류 기록·수동 대응을 구분하며 자동 무손실을 요구하지 않습니다.

## 10. 결정 대기 목록

- 스키마별 owner 구분, PostgreSQL 중심 개인 인벤토리의 정확한 범위/저장 포맷·전환 정책, 캐시·RLS 사용과 DB 연결 기술.
- 유휴 시간·진행 시간 경과, 30초 초기 주기의 조정 기준·배치 크기·대기/재시도 한도·백업/로그 보존·관리자 조치 권한, 안전한 로그인 대기 방식. 고비용 checkpoint·자동 무손실은 필수 결정 항목에서 제외.
- ADR-0004의 미정 정책: 스킵 보상 지급·감소 여부/비율, 완료자의 재참여 보상, 중간 가입 절차·관리자 구성원 변경, 중요 퀘스트 중 접속자 변경, 분기 의사결정 방식, 과거 인스턴스·연출·NPC 처리. 게임 내 파티 탈퇴·분할·병합은 구현 요구로 승계하지 않음.
- 템플릿/콘텐츠 manifest 형식·버전 호환·migration/rollback, 기존 월드 신규 지형 적용 방식.
- 보호 구역 충돌·행위별 권한·건축 드롭과 채집 반출 정책, 채집 인던 소유/초기화/재생성.
- 경제 멀티 프로세스 분리 여부와 AI 세부 기술은 그대로 미정.

확정 설계 변경이 필요한 항목은 사용자 검토 후 후속 ADR로 관리합니다. 이번 초안은 ADR-0001·0002를 유지하고 인벤토리·장애 대응에는 ADR-0003, 공동체·퀘스트·장별 스킵에는 ADR-0004를 반영하며 서버·컨테이너·DB 실행이나 운영 변경을 승인하지 않습니다.
