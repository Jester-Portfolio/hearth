# 스토리 월드 S3 상세 설계

- 최초 작성: 2026-10-23. 최종 설계 감사: 2026-10-25. S4-5 상태 링크 확인: 2026-10-26. 기준 커밋: `fc438a86d56205c3a60038ce8b8a922a072ccbff`.
- 상태: **S3 설계 완료 / 구현·런타임 검증 미완료**. ADR-0001~0014의 승인 정책과 구체 구현 후보를 구분한 설계 기준선입니다. C1 최종 승인 이후 [12영역 감사](s3-completion-audit.md)에 따라 완료를 기록했습니다. S4는 [최소 구현/검증](s4-1-verification.md) 진행 중이며 전체 기능 구현·런타임 수용 시험은 남아 있습니다. 구현 후보·의도적 보류를 추가 승인한 것이 아닙니다. 전체 스키마·상태 전이·복구 절차는 미구현·미검증입니다. 후속 [S4-4](s4-4-verification.md)에서 공유/개인 키·FK·revision의 최소 V001과 비동기 저장만 구현·실DB 시험했으며 아래 전체 후보를 구현한 것은 아닙니다. 인벤토리·아이템 저장과 장애 대응의 확정 정책은 [ADR-0003](decisions/0003-inventory-performance-and-recovery.md)을 우선합니다.
- 후속 [S4-5 통합 기록](s4-5-verification.md)은 최소 공유/개인 상태의 Paper–PostgreSQL 연결·두 JVM 복원·대표 오류 처리를 확인했습니다. 전체 스키마·인벤토리·게임 상태 전이 검증과 구분합니다.
- 후속 [S4-6~8](s4-8-verification.md)은 V002·명시한 41슬롯·30초/dirty·내부 source/target 전환의 최소 구현·통합 근거입니다. 전체 인벤토리/게임·경제 realm·실제 로그인/이벤트 검증으로 확대하지 않습니다.
- 선행 결과: [S2 빌드/API 검토](stack-build-verification.md). S2 완료는 구현 경로·위험·시험 기준 정리까지이며 런타임 동작 보증이 아닙니다.

- 후속 [S4-9](s4-9-verification.md)·[S4-10](s4-10-verification.md)은 상태/저장 경계 단위를 검사했습니다. [S4-11](s4-11-verification.md) 최초 통합은 시험 대기 루프 오류로 중단됐으며 실패 이력을 보존합니다. 사용자 재개 후 수정본의 내부 컨텍스트 IDLE·저장/재진입·두 JVM·대표 실패/정상 종료는 통과했습니다. 실제 로그인/텔레포트·전체 운영 수명주기 검증으로 확대하지 않습니다.

## 1. 확정 경계와 모듈 책임 후보

[ADR-0001](decisions/0001-story-world-multiworld.md)의 단일 프로세스 B안, [ADR-0002](decisions/0002-stack-and-world-policies.md)의 Paper 26.2·Java 25·Gradle·단일 JAR 내부 모듈·PostgreSQL·템플릿/콘텐츠 분리·보호/채집 원칙을 유지합니다. [ADR-0003](decisions/0003-inventory-performance-and-recovery.md)에 따라 서버 성능과 원활한 플레이를 복잡한 자동 복구보다 우선합니다. 일반 상자·창고는 월드 파일, 플레이어 인벤토리는 PostgreSQL 중심으로 관리합니다. [ADR-0004](decisions/0004-community-quests-and-chapter-skip.md)의 공동체·개인 퀘스트·분기 고정·장별 스킵 정책도 확정입니다. 아래 구체 자료구조·상태 전이·스키마는 제안이며 미구현·미검증입니다.

| 내부 책임 후보 | 소유할 상태·행위 |
| --- | --- |
| 진행·참가자 | run_id, 서버 내부 player_uuid 연결·접근 컨텍스트, 세션별 현재 컨텍스트 |
| 월드 수명주기 | 템플릿 복제·배치 매핑·로드·저장·언로드·복구 상태 |
| 콘텐츠 | 불변 템플릿/콘텐츠 버전 참조와 정의 ID 해석 |
| 영속 상태 | 진행별 DAO·개인 상태의 배치 저장·오류 기록. 고비용 체크포인트는 기본 범위 밖 |
| 보호·인벤토리 | 행위별 구역 판정·상태 전환 차단·개인 상태 적용 |
| AI 연결 경계 | 인증된 진행·플레이어 범위의 읽기 DTO 제공. AI 구현 기술은 미정 |

전체 모듈의 패키지·Gradle 멀티프로젝트 구성은 확정하지 않습니다. S4-4의 최소 영속 계층만 pgJDBC/HikariCP를 사용하며 운영 전체 연결 정책의 검증을 대신하지 않습니다. 월드/플레이어/인벤토리는 서버 스레드에서 캡처·반영하고 DB·파일·AI I/O에는 불변 DTO·바이트만 넘깁니다. event handler에서 DB 응답을 기다리지 않도록 권한·구역·콘텐츠를 버전 고정 캐시로 판정합니다. 필요한 캐시가 없거나 복구 중이면 변경·입장을 차단하는 후보입니다.

## 2. 식별 모델

| 식별자 후보 | 의미·불변식 |
| --- | --- |
| run_id (UUID) | story_run_id의 본문 약칭. 싱글 또는 공동체의 공유 논리 진행; 물리 배치와 분리 |
| 공동체 ID (논리 식별) | 개인 진행의 공동체 범위. story_run_id와의 물리 키 관계·타입은 미정; party_id 대체 스키마 채택이 아님 |
| world_instance_id (UUID) | 해당 진행에 속한 하나의 물리 월드 인스턴스 레코드 |
| logical_role | main, gathering 등 역할. 차원 구성은 후보, 스토리 채집은 run 범위·경제 소유는 E1 |
| physical_uuid / world_key / directory_ref | 실제 Paper 월드의 UUID·키·허용 루트 하위 경로. 글로벌 UUID·키 충돌 검사 |
| server_id / placement_epoch | 배치 위치와 쓰기 세대. 현재 B안은 한 프로세스지만 A안 이전에 재사용 |
| player_uuid / session_epoch | 계정과 현재 접속/전환 세대. 늦은 DB·AI·이동 응답을 거부하는 기준 |

접근 컨텍스트는 `(mode, scope_id, run_id?, player_uuid, session_epoch, placement_epoch)` 후보로 정의합니다. 클라이언트가 보낸 run_id·월드 이름을 신뢰하지 않고 서버의 참가 관계·배치 매핑과 대조합니다. 물리 월드 ID가 우연히 같더라도 DB 진행 데이터를 선택하는 근거가 되지 않습니다. 하나의 scope는 하나의 데이터 소유권 경계이며 story는 run_id, economy는 후속 결정할 realm 식별자를 쓰는 후보입니다.

## 3. 템플릿·콘텐츠 버전과 최초 복제

- 공간 템플릿은 `(template_id, template_version, checksum, server/data_version)` 불변 manifest로 관리하는 후보입니다. 원본은 플레이 중 쓰지 않는 사전 제작 데이터이며 신규 복제/채집 리셋 및 승인된 부분 업데이트의 읽기 기준으로 사용합니다. 기존 진행을 자동 교체하지 않습니다.
- 콘텐츠 정의는 `(content_id, content_version)`으로 NPC 배치·대화·퀘스트·안정된 정의 ID를 관리합니다. 템플릿과 별개이며 호환 template 범위·좌표 기준·지원 데이터 버전을 manifest로 연결하는 후보입니다.
- 신규 진행은 사용할 두 버전을 명시적으로 고정합니다. 새 템플릿 추가가 기존 진행의 버전을 자동 변경하지 않습니다. 기존 신규 지형/건축물은 변경 영역 충돌 검사 후 적용하고 충돌 시 보존/업데이트 보류·실패 시 기존 정상 상태 유지입니다. 구체 적용 도구/manifest는 S4 미정이며 통째 덮어쓰기는 금지합니다(ADR-0012).
- 기존 콘텐츠 변경은 안정된 quest/NPC ID를 보존하고 이전→새 버전 변환표·검증·백업·되돌리기 조건을 준비한 뒤 적용하는 후보입니다. 호환되지 않는 진행은 구버전을 유지하거나 입장을 막고 검토합니다. 삭제된 정의를 임의 초기화·재보상하지 않습니다.
- 저장소의 콘텐츠 형식(JSON/YAML 등), 버전 게시·배포 도구와 적용 시점은 미정입니다. Paper/Minecraft 데이터 변환의 역방향 호환을 가정하지 않습니다.

최초 생성 후보 절차:

1. DB에서 run·선택 버전·배치 예약을 `PROVISIONING`으로 만들고 operation_id를 고정합니다. 동일 요청은 같은 작업에 합류합니다.
2. I/O 작업에서 허용 루트의 staging 디렉터리에 템플릿을 복제하고 완료 manifest·파일 체크섬을 확인합니다. 경로 탈출·링크·불완전 복사본을 거부합니다. 하드링크 공유 쓰기를 사용하지 않는 후보입니다.
3. 월드 UUID·키·엔티티/NPC 참조의 충돌 및 포털 목적지를 검증합니다. 복제 도구별 식별자 재생성 방법은 S4 검증 과제이며 기존 파일을 추측으로 삭제하지 않습니다.
4. staging 완료를 기록하고 같은 파일시스템의 공개 경로로 전환하는 후보입니다. 디렉터리 전환과 DB 커밋은 원자적이지 않으므로 작업 journal로 재시작 시 중단 지점을 구분합니다.
5. 서버 스레드의 안전한 시점에서 `createWorld`로 로드, 물리 매핑·콘텐츠·진행 데이터 일치 확인 후 준비 완료를 기록합니다. null·예외·기존 다른 월드 반환 시 격리합니다. 입장 허용은 초기화가 모두 성공한 뒤입니다.

## 4. 월드 수명주기 상태 전이 후보

구현 방식은 [기성 플러그인 적합성 검토](plugin-suitability-review.md)에서 Multiverse-Core API와 Paper API+Hearth 관리자를 비교합니다. Multiverse-Core는 미채택 후보이며 아래 진행/저장/접근 경계는 어느 방식에서도 유지합니다. WorldGuard 채택은 ADR-0014를 따르고 실제 연동 시험은 미실행입니다.

동일 run 생성/로드는 단일 작업을 공유하고 IDLE 대기 내 재접속은 언로드 예약을 취소합니다. IDLE 초기 5분은 추천값이며 확정값이 아닙니다. 저장 중 접속은 해당 작업 완료 후 복원을 처리합니다.

상태는 월드 인스턴스 단위이고 run 전체는 모든 필수 월드·DB 상태가 준비됐을 때만 사용 가능합니다. 아래 전이는 구현·DB에 적용하지 않았습니다.

| 전이 | 사전 조건·처리 | 실패 시 후보 처리 |
| --- | --- | --- |
| PROVISIONING → OFFLINE | 복제·manifest·매핑 완료 | FAILED로 격리, 기존 원본·다른 진행 보존 |
| OFFLINE → LOADING | 참가 권한, 호환 버전, 저장 오류 여부·단일 소유권 확인 | RECOVERY_REQUIRED; 임의로 새 빈 월드 생성 금지 |
| LOADING → READY | Paper 로드·DB·NPC·보호 초기화 완료 | 입장 차단, 이미 로드한 월드 정리 여부 확인 |
| READY → ACTIVE | 현재 세대에 속한 입장 예약·이동·개인 상태 복원 완료 | 이동 실패면 예약 해제 또는 원래 위치 복원 |
| ACTIVE → IDLE | 참가자·입장 중 요청 0, 마지막 퇴장 처리 완료 | 입장 예약이 생기면 ACTIVE 유지 |
| IDLE → QUIESCING | 유휴 대기 만료, 새 입장 예약 차단, 상태 변경·작업 정지 | 재접속은 작업 완료 뒤 처리. 유휴 초기 5분은 추천값(미확정) |
| QUIESCING → SAVING | 비행 중 DB·보상 작업 정리, 사용자·월드 작업 스냅샷 | 타임아웃이면 ERROR_HOLD, 언로드하지 않음 |
| SAVING → UNLOADING | 개인/진행 DB 저장 순서 확인과 일반 월드 저장; 전체 복사·일체형 체크포인트 불필요 | DB/파일 실패 시 ERROR_HOLD, 입장·변경 차단 |
| UNLOADING → OFFLINE | 안전한 호출 시점의 unloadWorld 성공 확인, 참조·티켓 해제 | false·예외면 실제 로드 상태 유지, 재시도 판단 |
| 임의 상태 → RECOVERY_REQUIRED | 손상·저장 결과 불명·소유권 불명 | 해당 범위 데이터 보존·접근 제한·오류 기록 후 관리자 확인. 정상적인 저장 시점 차이만으로 전체 서버 차단 금지 |

메인 스레드에서 실행하더라도 월드 틱 중 로드·언로드는 피해야 합니다. `isTickingWorlds()` 검사와 다음 안전한 스케줄 시점으로 미루는 처리가 필요하며 정확한 시점은 런타임 검증 대상입니다. 월드 저장 방식·writer 대기는 언로드 경계의 필요성과 지연을 검토하며 매 아이템 이동마다 동기 flush를 하지 않습니다. 저장 실패를 무시하거나 성공하지 않은 언로드를 OFFLINE으로 기록하지 않습니다.

접속: 플레이어의 허용 진행 선택 → run 입장 예약·session_epoch 갱신 → 필요한 월드 로드에 합류 → DB 개인 상태 로드 → 서버 스레드에서 인벤토리·위치 적용과 이동 → 성공 확인 후 조작 허용 후보입니다. 초기 스폰/로그인 단계에서 안전한 대기 공간 또는 접속 지연이 가능한지는 S4 검증 과제입니다. 초기 스폰이 타 진행 데이터를 노출하지 않아야 합니다.

퇴장: 진행 전환 전에 GUI·커서·거래·아이템 이동을 안정화하고 개인 상태 캡처·저장 완료 후 세션 소유권을 넘깁니다. 연결 종료 이벤트에서 무기한 DB 대기하지 않으며 실패 시 저장 미완료 상태로 잠그고 재접속 복원을 중단하는 후보입니다. 단순 로그아웃은 공동체 구성원 변경이 아닙니다. 게임 내 파티 탈퇴 시스템은 구현하지 않습니다. 일반 자동 저장 초기값은 30초이며 조정할 수 있습니다. 장애 시 허용 유실 시간의 보장값은 확정하지 않았습니다.

이동: `teleportAsync` future를 메인 스레드에서 join/get하지 않습니다. 완료 후 Boolean·예외·세션·배치·참가 권한을 확인합니다. 포털·사망·부활·명령 이동도 같은 진행 입장 경계를 사용합니다. 베드·부활 위치는 run과 논리 월드 역할을 포함하며 타 진행으로 자동 복귀시키지 않습니다.

## 5. PostgreSQL 데이터 범위와 스키마 후보

SQL·DB 서버 실행은 하지 않았습니다. 아래는 물리 DDL이 아닌 키·열·제약 후보입니다. PostgreSQL 세부 버전·마이그레이션 도구·드라이버·풀과 DB 인스턴스/스키마 분리 방식은 미정입니다.

| 테이블 후보 | 핵심 열·키·제약 |
| --- | --- |
| progress_scope | scope_id UUID PK, mode(story/economy), 상태. UNIQUE(scope_id,mode) |
| story_run | run_id UUID PK=scope_id FK, 공동체 참조의 물리 표현 미정, content_id/version, state, revision bigint, last_saved_at. scope mode=story는 검증/복합 FK로 강제 |
| 플레이어–진행 연결 (내부 식별 후보) | 서버 내부 player_uuid–story_run_id 연결만 허용. 가입·탈퇴·추방·파티장·권한 관리 UI/role 테이블 요구 없음 |
| world_instance | world_id UUID PK, run_id FK, logical_role, template_id/version, physical_uuid, world_key, directory_ref, server_id, placement_epoch, state. UNIQUE(run_id,world_id), 물리 배치 충돌 제약 |
| player_progress | PK(run_id,player_uuid), revision, last_world_id, 위치·체력·XP·개인 변수. 내부 player–run 연결의 참조 제약 후보; FK(run_id,last_world_id)→world_instance |
| quest_progress | PK(run_id,owner_kind,owner_id,quest_id), content_version, stage, variables jsonb, revision. 공동체 중요 퀘스트와 개인 퀘스트를 구별. 개인 논리 키는 공동체 ID·player_uuid·quest_id; owner 물리 표현·소유 유형 제약 미정 |
| npc_relation | PK(run_id,player_uuid,npc_definition_id), 관계 값·revision. 참가자 복합 FK |
| story_branch / npc_state | PK(run_id,definition_id), 고정 분기 선택·생존/활동 상태·revision·content_version. run 공통 상태; 개인 따라잡기의 쓰기 대상에서 제외 |
| inventory_snapshot | PK(scope_id,player_uuid), db_revision, payload bytea, format_version, minecraft_data_version, checksum, saved_at. 배치 저장용 현재 상태이며 무손실 복원 이력이 아님 |
| transfer 상태 | 기본은 세션 내 단일 전환·source/target scope와 revision 검사. 영속 상세 journal은 단순하고 비용이 낮을 때만 선택 검토 |
| reward marker | run/quest/회차/player의 고유 지급 키, 지급 상태·관련 inventory revision. 중복 지급 방지·상태 즉시 저장은 확정, 열/트랜잭션 구성은 후보 |
| wallet | PK(scope_id,account_id,currency_id), amount·revision. 화폐형·잔액 제약·계정 모델은 후보이며 경제 규칙 확정이 아님 |
| economic_transaction | transaction_id UUID PK, scope·종류·참가자·서버 검증 요청 요약/hash·금액·아이템 요약·결과 revision·DB 완료 시각. 거래별 고유 키로 중복 억제. 필수 거래 기록이며 전체 이동 원장/보관함이 아님 |
| 선택 확장 | checkpoint/checkpoint_player·거래 보관함·전체 이동 원장은 기본 스키마에서 제외. 필요·성능을 별도 검토 |
| lifecycle_operation | operation_id PK, run_id/world_id, 종류·전이 전후 상태·epoch·단계·오류. 재시작 복구용 journal |

외래 키는 run_id를 함께 포함해 다른 진행의 월드·참가자를 가리키지 못하게 하는 후보입니다. 예: player_progress의 `(run_id,last_world_id)`는 world_instance의 동일 복합 키만 참조합니다. 단순 world_id FK와 애플리케이션 필터만으로 이 교차 참조를 맡기지 않습니다. [PostgreSQL 제약 문서](https://www.postgresql.org/docs/current/ddl-constraints.html)를 근거로 검토했으며 제약 간 정확한 DDL·마이그레이션은 미시험입니다.

jsonb는 유동적인 콘텐츠 변수에만 사용하고 run·소유자·버전·참조 무결성은 구조화된 열과 제약으로 유지하는 후보입니다. owner_kind별 FK가 복잡하면 quest_progress를 run_quest와 player_quest로 분리하는 대안이 있습니다. 단일 테이블/분리 테이블 선택은 제안 상태입니다.

월드 파일은 블록·청크·컨테이너·엔티티의 물리 상태를 소유합니다. PostgreSQL은 진행·관계·분기·참가자·개인 상태·작업 이력을 소유합니다. 엔티티는 논리 NPC ID를 서버 매핑으로 연결하고 DB의 npc_state에서 재구성하되 중복 생성·삭제 판정은 검증합니다. vanilla playerdata와 DB가 인벤토리를 동시에 독립적인 정본으로 저장하지 않도록 플레이어 인벤토리를 PostgreSQL 중심으로 관리한다는 확정 원칙 아래 DB snapshot을 읽기 기준으로 두고 서버 파일의 초기 로드 상태를 안전한 입장 절차에서 교체하는 설계를 검토합니다. 구현 라이브러리와 이벤트 순서는 미정입니다.

진행 유출 방지: 모든 DAO는 서버에서 검증된 scope 컨텍스트를 필수로 받으며 UUID만으로 조회하지 않습니다. 캐시·작업·AI 조회 키에 mode/scope_id와 필요 시 player_uuid·epoch를 넣습니다. RLS는 보조 후보이며 전용 역할·풀 연결 컨텍스트 초기화까지 시험하기 전 격리 보장으로 쓰지 않습니다. 서버 명령·콘텐츠 스크립트·관리 도구도 같은 경계를 통과해야 합니다.

## 6. 공동체 진행과 인벤토리 전환

확정 정책은 [ADR-0004](decisions/0004-community-quests-and-chapter-skip.md)를 따릅니다. 공동체는 같은 story_run_id·월드·세계 변화·주요 스토리 결과를 공유하며 개인 인벤토리·퀘스트 완료·보상 기록은 분리합니다. 게임 내 파티 탈퇴는 구현하지 않습니다. 기존 party_id·party_member·파티장·탈퇴·분할·병합 후보는 현행 구현 요구에서 제외하며 대체 물리 스키마는 채택하지 않습니다. 가입·탈퇴·추방·파티장 기능은 없습니다. 내부 식별 연결은 해당 기능이 아닙니다(ADR-0010).

### 공동체·개인 진행 모델 후보

| 논리 상태 | 범위·불변식 | 구체 구현 후보 (미확정) |
| --- | --- | --- |
| 공동체 중요 퀘스트 | 공동체 ID / story_run_id. 중요 메인·분기점 | 개인 상태와 분리한 레코드, revision 비교로 동시 진행 요청 경합 감지 |
| 개인 퀘스트 | 공동체 ID + 플레이어 UUID + quest_id | 독립 stage·완료 상태; A의 완료를 B에게 복사하지 않음 |
| 공동체 분기·세계 효과 | 공동체 ID + branch/effect 정의 ID | 확정 선택 변경 거부·효과 적용 식별자로 정상 중복 요청 억제. 개인 따라잡기 경로는 공유 NPC/분기/월드 쓰기 권한 없음 |
| 개인 장 진행 | 공동체 ID + 플레이어 UUID + chapter_id | 직접 플레이 완료 / 스킵 / 선행 조건 충족을 구분하는 상태 후보. 실제 enum·테이블 미정 |
| 장 콘텐츠 정의 | 콘텐츠 버전 + chapter_id | 메인·필수 길목 목록과 일반 서브 목록 분리. 누락·잘못된 의존성 검사는 콘텐츠 시험 대상 |
| 개인 보상 기록 | 공동체 범위 + 플레이어 UUID + 지급 식별자 | ADR-0003의 중복 방지·지급 상태 즉시 저장. 스킵·재참여의 지급 여부는 결정하지 않음 |

story_run_id를 논리 소유 범위로 사용하며 내부 플레이어–진행 연결의 실제 DDL/인덱스는 S4 미정입니다. 별도 공동체 관리 체계를 추가하지 않습니다. 논리 범위를 명시한 것이 새로운 테이블/권한 정책 승인은 아닙니다.

### 공동체 중요 퀘스트 조건 검사

진행 조건은 `접속 중인 공동체 구성원 모두가 해당 퀘스트 조건 충족`입니다. 단 한 명의 미충족으로 진행이 막히며 비접속자는 제외합니다. 근처 플레이어·임의 참가자만 검사하거나 모든 등록 구성원의 동시 접속을 요구하지 않습니다. 조건 충족은 개인 퀘스트 일괄 완료·보상 지급과 구분합니다.

ADR-0004의 추가 확정 정책에 따라 중요 퀘스트 중 구성원이 추가 접속해도 현재 전투·컷신·퀘스트 단계를 강제로 중단하지 않습니다. **다음 중요 진행 단계 진입 시** 현재 접속 중인 구성원 전원의 조건을 다시 확인하고, 미충족자가 있으면 다음 단계 진입을 차단합니다. 비접속자는 제외하며 기존 완료 단계는 되돌리지 않습니다. 세부 단계 경계와 접속·종료 경합 처리는 미정입니다.

후보 흐름은 인증된 공동체/진행 확인 → 다음 중요 단계 진입 요청 → 현재 접속 구성원과 개인 선행 조건 조회 → 전원 충족 판정 → 단계 변경 요청입니다. 검사와 변경 사이 경쟁을 감지할 revision·요청 식별자는 구현 후보입니다. OPEN 대상 변경은 취소/재투표, 과반수 입력마감 이후는 변경으로 재계산하지 않습니다. 스토리 최종 확정은 DB 성공 뒤이며 구체 SQL/API는 미정입니다.

### 중요 분기 투표

진행 조건을 충족한 현재 접속 공동체 구성원들이 중요 분기를 과반수로 선택합니다. 전체 대상 인원 N에 대해 한 선택지의 득표 v가 `2 × v > N`이어야 하며, 과반수 선택지가 없거나 동률이면 분기를 확정하지 않고 재투표합니다. 한 명만 접속·조건 충족이면 직접 선택할 수 있습니다. 확정된 분기는 불변이며 뒤늦은 구성원도 따릅니다.

고정 명단의 예로 N=4에서 2표는 과반수가 아니고 3표는 과반수입니다. 여러 선택지 중 단순 최다 득표만으로 확정하지 않습니다. 투표는 기본 채팅·초기 30초·중복 차단이며 기권/미투표는 찬성 아님, OPEN 대상 변경 시 취소/새 명단 재투표, 과반수 입력마감 뒤 접속변경 재계산 금지입니다. 확정 결과는 접속 변화로 취소하지 않습니다(ADR-0011). 투표 요청과 공동체 분기 저장의 revision 검사·정상 중복 확정 억제는 후보이고 물리 DB 스키마·상세 API는 확정하지 않습니다.

### 고정 분기와 장별 따라잡기·스킵

공동체가 이미 진행한 장을 놓친 개인은 각 장을 직접 플레이하거나 스킵할 수 있습니다. 선택은 장마다 독립적입니다. 스킵 범위는 그 장의 메인과 진행에 필요한 길목 퀘스트이며 다음 장의 개인 선행 조건을 충족합니다. 일반 서브 퀘스트는 일괄 스킵으로 처리하지 않습니다. 미래의 미진행 장을 임의로 해금하는 정책은 채택하지 않습니다.

직접 따라잡기는 공동체가 확정한 분기만 읽고 개인 상태를 변경합니다. 완료자는 지원할 수 있지만 개인 지원/스킵 요청으로 공유 NPC 상태·월드 효과를 다시 쓰거나 공동체 분기를 되돌리지 않습니다. 공유 효과 적용 경로와 개인 따라잡기 경로를 분리하고 요청 ID·revision으로 정상 중복 실행을 억제하는 후보입니다. 공유 월드에서 과거 인스턴스·연출·NPC를 재현할 방법은 미정이며 별도 검증이 필요합니다.

스킵을 실제 플레이 완료나 자동 보상 지급으로 기록하지 않습니다. 개인 장 결과·선행 조건과 보상 기록을 구분합니다. 스킵 보상·감소 비율 및 완료자의 재참여 보상은 미정입니다. DB·게임 메모리·월드 파일은 자동 원자적이지 않으며 고비용 체크포인트/완전 자동 복구를 추가하지 않습니다. 실패 시 성공 오기록·공유 효과 재적용을 피하도록 상태 확인·최소 오류 기록과 ADR-0003의 수동 대응을 검토합니다.

스토리 scope와 경제 scope 인벤토리는 독립 snapshot입니다. 일반 상자·창고 내용은 월드 파일이 소유하며 PostgreSQL에 매 이동을 복제하지 않습니다. 엔더 상자·커서·열린 GUI 등 개인 상태의 정확한 범위와 저장 포맷은 상세 설계 대상으로 남깁니다.

### 6.1 확정된 저장 정책

| 대상·계기 | 확정 정책 |
| --- | --- |
| 일반 플레이어 인벤토리 | 변경된 데이터만 **30초 간격의 비동기 배치 저장**. 30초는 성능 측정 후 조정할 수 있는 초기 운영값 |
| 일반 상자·창고 | Minecraft 월드 파일 저장. 클릭/이동마다 DB·동기 디스크 flush 불필요 |
| NPC 상점 구매·판매 / 플레이어 간 경제 거래 | 30초를 기다리지 않고 거래마다 즉시 DB 반영 |
| 퀘스트 보상 | 중복 지급 방지, 지급 상태 즉시 저장 방향 |
| 스토리·경제 월드 전환 | 이전 인벤토리 저장 완료 확인 후 전환 |

즉시 저장은 요청을 주기 대기열에서 30초 대기시키지 않는다는 뜻입니다. DB는 비동기로 처리하고 메인 스레드에서 SQL/future를 동기 대기하지 않습니다. 위는 확정 정책이며 아래 저장 자료구조·잠금·트랜잭션 구성·실패 상태는 구현 후보입니다. 이번에 DB·게임 코드를 실행하지 않았습니다.

### 6.2 일반 저장과 충돌 방지 후보

1. 정상 메모리 변경마다 dirty 표식과 `memory_version`을 올립니다. 초기 30초 주기에 dirty인 플레이어/scope만 캡처해 불변 DTO로 비동기 저장합니다. 변경 없는 인벤토리/진행은 쓰지 않습니다. 슬롯별 SQL delta를 강제하지 않고 dirty inventory 단위 snapshot도 후보입니다. 배치 크기·주기 분산은 별도 측정합니다.
2. scope/player별 일반 저장·거래·보상·전환을 같은 저장 조정자에서 순서화합니다. 한 소유자에 저장 하나만 in-flight로 두는 간결한 큐를 기본 후보로 하고, 큐의 오래된 일반 snapshot은 합치거나 폐기합니다. 거래는 이전 in-flight 일반 저장이 완료/실패 확정되기 전 추월하지 않습니다. 둘 이상의 플레이어를 묶는 거래는 참가자 모두의 큐에 장벽을 둡니다.
3. 메모리 변경 번호와 DB의 `db_revision`을 구분합니다. DB 쓰기는 예상 db_revision·소유 세션을 확인하고 성공 시 revision을 올리는 후보입니다. 오래된 callback/세션의 결과를 최신으로 채택하지 않으며 충돌 시 저장 성공으로 처리하지 않습니다.
4. 일반 저장 성공 때 캡처한 memory_version까지만 저장 완료로 표시합니다. 캡처 이후 변경이 있으면 dirty를 유지합니다. 거래 성공 뒤 거래 이전 snapshot을 재전송하거나, 오래된 저장 완료가 dirty를 지우지 못하도록 합니다.
5. 30초는 스케줄러·큐·실제 DB 지연 때문에 정확한 디스크 내구성 시각이나 최대 유실 30초를 보장하지 않습니다. DB 실패 시 dirty를 유지하고 재시도 한도를 둡니다. 클릭마다 SQL·전체 이동 로그·동기 flush를 수행하지 않습니다.

### 6.3 비동기 경제 거래 흐름 후보

NPC 구매/판매와 플레이어 간 거래에 동일한 조정 경로를 사용합니다. 거래·아이템·화폐 규칙은 서버에서 검증하며 클라이언트가 보낸 금액·보유량·revision을 신뢰하지 않습니다. 아래는 DB 트랜잭션 후보이지 실행 검증 결과가 아닙니다.

| 단계 | 서버 스레드 / 비동기 처리 | 조건·경계 |
| --- | --- | --- |
| 요청 식별 | 서버가 transaction_id와 scope·참가자·가격/조건 요약을 묶고 같은 요청에 같은 ID 사용 | 중복 확인·다른 payload로 ID 재사용 거부. 성공 거래를 새 ID로 재시도하지 않음 |
| 참가자 예약 | 서버 스레드에서 해당 참가자와 필요한 상태의 중복 거래·전환을 차단 | 전체 서버 잠금 없음. 참가자 큐 예약 순서를 일정하게 두어 두 플레이어 거래 간 교착 방지 |
| 이전 저장 정리 | 비동기로 이미 진행 중인 일반 저장 결과 확정을 기다리고 대기 중 옛 snapshot 정리 | 메인 스레드는 대기하지 않음. 타임아웃·저장 실패는 거래 진행 중단, 성공 처리 금지 |
| 짧은 변경 보호 | 최신 캡처 직전~결과 적용 사이 필요한 참가자 상태만 보호 | 전체 snapshot을 쓰는 후보에서는 관련 플레이어 인벤토리 전체가 보호 범위. 슬롯 단위만 막으면 비거래 슬롯의 최신 변경을 덮을 수 있어 적용 금지. 외부 드롭/획득·죽음·상자/자동 이동·전환 처리와 경합도 정해야 함 |
| 최신 상태 확정 | 서버 스레드로 돌아와 세션·scope·memory_version, 현재 아이템 종류/수량/메타데이터·수용 공간·거래 조건 검증 후 최신 snapshot과 거래 후 상태를 캡처 | DB에 없는 최신 획득·소비·상자 이동까지 포함. 검증 전에 캡처한 오래된 상태로 거래하지 않음 |
| DB 트랜잭션 | 비동기로 관련 inventory·wallet 행을 일정한 키 순서로 잠그거나 예상 revision으로 검증, 거래 ID 중복 확인, 잔액·정책 재검증, **최신 snapshot + 거래 delta**에서 계산한 최종 인벤토리·화폐·거래 기록을 같은 트랜잭션에 저장 | 두 참가자의 인벤토리와 관련 화폐를 함께 반영, 부분 commit 금지. 조건 불일치면 전체 rollback. DB 작업 동안 서버 스레드를 기다리게 하지 않음 |
| 커밋 확인 | DB commit 결과와 최종 revision을 반환 | 정상 응답 없는 타임아웃은 rollback이라고 단정하지 않음. 커밋 전 임의 아이템/화폐 지급 금지 |
| 메모리 적용 | 서버 스레드에서 세션·scope·보호 상태를 재확인해 커밋된 최종 상태를 한 번 적용 | callback 중복·재접속/이탈 뒤 stale 적용 금지. DB 성공만으로 아직 메모리 미반영인 거래를 플레이 완료로 표시하지 않음 |
| 완료 | DB 확인과 필요한 메모리 적용 완료 후 성공 표시·해당 보호 해제 | 이후 일반 저장은 새 db_revision을 기준으로 재개. 적용 중 변경이 남으면 dirty 유지 |

거래 시작 시 **DB의 30초 전 snapshot을 거래 기준으로 그대로 쓰지 않습니다.** 이전 저장이 끝난 뒤 확보한 현재 메모리 snapshot의 미저장 변경과 거래 delta를 같은 즉시 저장에 포함합니다. 별도 선행 flush를 선택하더라도 source 저장과 거래 사이 보호·순서가 유지돼야 하며, flush만 하고 상태를 다시 검증하지 않는 흐름은 허용하지 않습니다.

재전송된 transaction_id가 DB에서 이미 완료됐다면 기존 결과를 조회하되 아이템·화폐 delta를 다시 실행하지 않습니다. 이미 적용한 세션에 전체 snapshot을 다시 덮어쓰지도 않습니다. 프로세스 재시작 뒤에는 인벤토리의 DB 최신 상태를 정상 로그인 경로로 읽는 방향이며 오래된 거래 snapshot을 무조건 재지급하지 않습니다.

경제 화폐·가격·세금·상점 재고 정책과 잔액 캐시, 교차 서버 조정 방식은 미정입니다. 현재 후보는 참가자의 한 소유 프로세스/세션에서 처리하는 경로이며 경제 서버 분리나 분산 원자성을 확정하지 않습니다. 관련 상점 DB 재고가 생기면 같은 DB 경계의 행으로 검토하되 일반 상자·월드 파일은 여기에 포함하지 않습니다.

행 잠금·고유 키 후보는 [PostgreSQL 잠금](https://www.postgresql.org/docs/current/explicit-locking.html)과 [제약](https://www.postgresql.org/docs/current/ddl-constraints.html)을 참고합니다. 실제 SQL·격리 수준·연결 풀·쿼리/잠금 타임아웃·재시도 값은 미정입니다. 영속 거래 식별·중복 방지는 필수 요구이며 그 구현을 고비용 escrow나 전체 아이템 이동 원장으로 확대하지 않습니다.

### 6.4 실패·불명확 결과·메모리 반영 후보

| 결과 | 처리 후보 |
| --- | --- |
| 검증 실패·확실한 rollback | 거래 delta를 메모리에 선반영하지 않아 성공 표시/지급 없음. 원래 최신 상태·dirty를 유지하고 해당 보호 해제. 단순 ID 중복은 새 거래로 실행하지 않음 |
| 일반 저장 revision 충돌 | 무조건 UPDATE/성공 처리 금지. 오래된 snapshot 폐기·현재 소유 세션/DB 상태 확인 후 새 캡처 필요. 영향을 받은 플레이어만 처리 |
| commit 결과 불명·연결 종료 | 같은 transaction_id의 상태를 제한적으로 조회. 행 미조회만으로 원래 트랜잭션이 영원히 실패했다고 단정하지 않으며 실행 종료/잠금 상태까지 확인 전 재지급·새 ID 재시도·오래된 자동 저장 금지 |
| DB commit 성공 후 연결 끊김/메모리 적용 실패 | 성공 UI·추가 지급 금지. 해당 인벤토리/거래를 적용 미완료로 표시, DB 최종 상태와 세션을 확인한 재접속/재적용 후보 또는 관리자 수동 조정. stale 메모리 자동 저장으로 커밋된 DB를 덮지 않음 |
| 재시도/보호 시간 한도 초과 | 메인 스레드나 전체 서버를 막지 않고 해당 거래·필요한 개인 상태만 보류/접근 제한 후 최소 오류 기록·관리자 확인. 결과 미확정 상태를 풀어 중복 거래를 허용하지 않음 |

게임 메모리 적용과 PostgreSQL commit은 자동으로 원자적이지 않습니다. 참가자 보호·revision·고유 키는 정상 경쟁을 제어하는 후보일 뿐 모든 crash window를 없애지 않습니다. 일반 상자 입출고·드롭·월드 파일을 DB transaction으로 묶지 않습니다. 비정상 종료 때 일부 유실·복사는 ADR-0003의 로그/백업 기반 관리자 수동 대응을 허용합니다.

### 보상 로직과 설정 분리 — 확정 원칙

보상 지급 로직과 실제 설정 데이터를 분리합니다. 퀘스트·인던별 보상 종류와 수량을 쉽게 수정하고, 보상 값 변경 때마다 플러그인 코드를 수정하거나 재빌드하지 않아도 되는 구조를 지향합니다. 이는 즉시 핫 리로드나 특정 설정 도구를 확정한 것이 아닙니다.

최종 수치·배율, 장별 스킵·이미 완료한 사람의 재참여 보상은 스토리라인과 실제 인게임 진행 방식이 구체화된 뒤 결정합니다. 현재 밸런싱은 **보류**입니다. YAML/JSON/PostgreSQL 등 설정 저장 방식·반영 시점·물리 스키마·상세 API는 미정입니다. ADR-0003의 퀘스트 보상 중복 지급 방지·지급 상태 즉시 저장은 유지합니다.

구현 후보는 quest/dungeon 정의에서 보상 설정을 참조하고, 지급 요청에 해석된 값·설정 버전 또는 식별자를 연결하는 방식입니다. 설정 변경과 이미 처리 중인 지급의 일관성·중복 지급 키의 안정성을 검토하되 저장 형식·버전 적용 방식은 확정하지 않습니다. 설정 값 변경을 기존 지급 기록 초기화나 자동 재지급으로 연결하지 않는 후보입니다. 공개 문서에는 일반 데이터 역할만 기록하며 실제 스토리·비밀·반전·결말·원고를 넣지 않습니다.

### 6.5 퀘스트 보상·전환·성능 후보

퀘스트 보상은 `(run_id,quest_id,completion_sequence,player_uuid)` 같은 안정된 지급 키와 지급 상태를 즉시 저장하는 후보입니다. 같은 보상 청구를 다시 실행하지 않으며 아이템·화폐 보상과 지급 표식의 DB 반영을 같은 저장 조정 경로에서 검토합니다. DB 실패/불명 결과에 지급 완료를 알리거나 재지급하지 않습니다. 반복 퀘스트 회차·공동체 보상·가득 찬 인벤토리의 처리 정책은 미정입니다. 복잡한 보관함을 기본 해결책으로 추가하지 않습니다.

스토리·경제 전환은 참가자의 미완료 거래/보상·저장을 정리하고 **이전 인벤토리의 저장 완료를 확인한 뒤** target 상태 적용·이동·컨텍스트 전환을 진행하는 후보입니다. 30초 자동 저장을 기다리는 방식이 아니며 source 저장 실패/거래 결과 불명 상태에서는 전환을 완료하지 않습니다. 로그아웃·유휴 언로드·정상 종료의 대기 한도와 실패 처리는 후속 상세 설계 대상입니다.

연결 풀·제한된 I/O worker·대기열 상한·타임아웃·제한 재시도를 간결하게 적용하는 후보입니다. 거래 처리는 필요한 플레이어·아이템 상태에 한정하고 전체 서버·모든 플레이어를 잠그지 않습니다. 필수 SQL 트랜잭션·중복 억제는 유지하고 부가 안전장치·과도한 로그·전체 이동 이력·고비용 checkpoint·escrow를 제외합니다. 지연·처리량 기준은 성능 측정 전에 정하며 이번에 검증하지 않았습니다.

ItemStack 포맷·Minecraft 버전·체크섬 등 경량 표식은 검토할 수 있지만 자동 무손실 복원은 보장하지 않습니다. 손상·미지원 포맷은 빈 데이터로 덮어쓰지 않습니다.

| 데이터 책임 | 확정 경계 | 상세 모델 후보 |
| --- | --- | --- |
| 퀘스트 정의 | 메인/필수 길목의 자동 또는 NPC 시작, 서브의 NPC/게시판 직접 수락; 퀘스트별 자동 완료/NPC 보고, 실패 조건과 재시작 방식 | 시작 조건·완료 모드·실패 조건·제작자 지정 checkpoint 참조를 콘텐츠 버전과 연결 |
| 개인/공동체 진행 | ADR-0004 소유 범위 유지; 보고형 목표 달성은 보고 대기 지원 | 진행 중 → 목표 달성/보고 대기 → 보고 확인 → 완료 후보. 자동형은 보고 없이 완료. 완료/보상 표식 분리 |

| 개인 컷신 기록 | 플레이어별 재시도·시청 완료·이후 스킵 선택 기록 분리 | 공동체 ID·player_uuid·cutscene 정의/버전·퀘스트 문맥의 논리 키 후보; 실제 키/버전 변경 시 승계는 미정 |
| 전투 상태 | 길목 전원 사망 실패/보스 전멸 대기, 특수 실패 조건, 사망자 관전·조건부 복귀 | 진행/전투 인스턴스 참조·참가자 생존/관전 상태·설정 버전 후보. 보스 명단은 시작 시 고정·신규 합류 금지, 전이/경합 상세 미정 |
| 부활 설정/사용량 | 조건·부활 불가·횟수·개인/공유 카운터·체력/효과·위치와 안전성 | 전투별 설정과 실행 상태를 분리, 요청 식별·revision으로 중복/공유 횟수 경합 억제 후보 |

#### 퀘스트 시작·실패·NPC 대화

퀘스트 실패 조건은 사망·호위 실패·시간 초과 등을 설정하고 결과는 진행도 유지·제작자 지정 체크포인트 재시작·처음부터 재시작 중 하나로 설정합니다. 이는 콘텐츠 진행 지점이며 고비용 저장 체크포인트가 아닙니다. 재시작으로 이미 확정된 공동체 분기·NPC·세계 효과를 되돌리거나 다시 적용하지 않고 소비 아이템도 자동 복구하지 않습니다. 길목 전원 사망 실패·보스 전멸 대기와 퀘스트별 사망 실패 조건을 별도로 판정하며 구체 우선순위/동시 이벤트 처리는 후속 설계입니다.

일반 NPC는 간단한 대화 UI, 상점·퀘스트 NPC는 기능 연결, 주요 NPC는 카메라 연출/컷신을 사용할 수 있습니다. 일반 대사는 단순 진행하고 정보 수집·질문·퀘스트 수락·중요 선택에서만 선택지를 제공합니다. 순정 클라이언트의 UI 방식과 카메라 기술은 미검증이며 특정 모드/플러그인을 확정하지 않습니다. 스마트폰 퀘스트 목록은 ADR-0009의 슬롯 GUI, AI 실제 대화는 기본 채팅창으로 구분하며 입력 연결·세부 표현은 미정입니다.

#### 개인 컷신 재생 흐름

| 상황 | 확정 동작 | 미정 경계 |
| --- | --- | --- |
| 일반 NPC 대화 | 이동·시점 자유 유지 | UI 기술 |
| 중요 컷신 발동 | 발동한 개인만 이동/카메라 제어·시청, 다른 구성원 강제 중단 없음 | 카메라·이동 제한과 복원 구현 |
| 첫 시청 | 끝까지 시청 필수, 스킵 불가 | 정상 종료 판정/기록 구현 |
| 첫 시청 중 접속 종료 | 완료 기록 없음, 재접속 후 처음부터 재생 | 접속 경합/기록 저장 순서 |
| 두 번째 도전 | 스킵 여부 질문 | 도전/재시도 카운트 경계 |
| 스킵 선택 후 이후 재도전 | 질문 없이 퀘스트 진행, 지정 입력으로 다시 시청 가능 | 입력 키·구현, 재시청 이후 선호 처리 |
| 두 번째 도전에서 스킵하지 않음 | 시청 가능; 이후 동작은 미정 | 이후 반복 질문/자동 재생 등을 채택하지 않음 |

시청 중단 횟수를 완료 기록으로 대체하지 않으며 첫 시청 필수 정책을 우회하지 않습니다. 시청·재시도·스킵 선호를 분리한 상태 전이를 후속 설계합니다. 컷신 종료·재생·스킵이 퀘스트/보상의 중복 완료나 공유 분기·월드 상태 재적용을 직접 유발하지 않도록 정상 요청 식별·완료/보상 표식 검사를 연결하는 후보입니다. 이 개인 컷신 스킵은 장별 스킵과 별개이며 공동체 결과·투표는 ADR-0004 그대로입니다.

#### 전투 사망·관전·조건부 부활

ADR-0007에 따라 길목은 전원 사망 시 실패하며 보스전은 전원 사망·접속 중이면 전멸 대기입니다. 즉시 실패/자동 재시작하지 않으며 개인/무관 퀘스트 실패는 보스를 종료하지 않고 직접 필수 실패만 종료합니다. 결과 경합은 ADR-0013의 직렬 terminal 후보를 따릅니다. 사망자는 관전자 모드로 생존 동료 시점을 보며 관전 대상을 전환할 수 있도록 설계합니다. 관전자는 전투에 개입하지 못하며 기본적으로 종료 전 복귀 불가, 설정된 부활 조건 충족 시에만 재참여합니다. 길목 완료 후 보스방 진입 자동 부활은 ADR-0007의 단계 전환 규칙입니다. 전투 참가자 범위를 공동체 전체 접속자나 ADR-0005 난이도 산정 바운더리 인원과 동일시하지 않습니다.

부활 조건(아이템·동료 행동·목표 등), 부활 불가, 전투별 횟수, 개인/전투 참가자 공동 횟수, 회복 체력 비율·효과, 위치(사망/시작/제작자 지정)·안전성 검사를 전투 설정 데이터로 관리합니다. 실제 수치·밸런싱은 보류합니다. 후보 흐름은 요청의 전투/플레이어 권한·현재 사망/관전 상태·조건·잔여 횟수 확인 → 위치 안전성 확인 → 요청/횟수 경쟁 제어 → 부활 반영/결과 확인입니다. 단계별 저장/적용 순서는 후보이며 불안전 위치의 대안, 부활 아이템의 주체·소비 시점, 부분 실패·전원 사망 판정과의 경합은 미정입니다.

전투 사망과 부활은 현재 인벤토리·착용 장비를 유지하며 사망 드롭은 없습니다. 사망 전 소비 아이템을 되돌리거나 과거 DB snapshot으로 복원하지 않습니다. PostgreSQL 정본·30초 dirty 비동기 저장과 즉시 거래/보상 상태 저장·메인 스레드 DB 대기 금지 등 ADR-0003을 유지합니다. 사망 시점마다 새 고비용 동기 저장/복구를 요구하지 않습니다. 이미 소환된 몬스터 난이도는 사망·부활로 재산정하지 않으며 필드 다음 구역 계산은 ADR-0005, 보스전 중간 소환의 최초 난이도 고정은 ADR-0007을 따릅니다. 전투 종료 후 복귀·전투 외 사망 규칙까지 확정하지 않습니다.

## 7. 성능 우선 저장·수동 장애 대응

**확정 우선순위: 서버 성능과 원활한 플레이 > 복잡한 자동 장애 복구.** 월드 파일과 PostgreSQL은 서로 다른 시점에 저장될 수 있습니다. 정상 플레이의 기본 중복·유실 예방은 유지하지만 비정상 종료 때 일부 아이템 유실·복사가 생길 수 있음을 수용합니다. 자동 무손실 복구나 모든 상황의 아이템 복사 방지를 보장하지 않습니다.

일상 경로는 Minecraft 일반 월드 저장과 변경된 플레이어 인벤토리의 30초 비동기 배치 저장을 사용합니다. 경제 거래·퀘스트 지급 상태·이전 인벤토리 전환 저장은 30초를 기다리지 않는 예외입니다. 유휴 저장·언로드마다 전체 월드 복사·파일/DB 동시 세대 확정·fsync 묶음·checkpoint 테이블을 요구하지 않습니다. 복잡한 거래 보관 시스템, 고비용 체크포인트·완전 자동 복구는 필수 범위에서 제외했습니다. 이전 초안의 일체형 checkpoint 절차는 ADR-0003으로 기본 후보에서 철회했으며 이전 Git 기록으로 확인할 수 있습니다.

백업 자체와 승인된 유지보수·A안 이전의 사전 보존/롤백 계획은 유지합니다. 백업의 주기·보존·비용은 별도 설계하며 정상 클릭 처리와 연결하지 않습니다. 가용 백업도 DB·월드 시점이 다를 수 있어 자동 일치·정전 내구성을 가정하지 않습니다.

### 최소 오류 기록 후보

저장 실패·재시도 한도 초과·손상 payload·모호한 전환/거래/지급·비정상 종료 감지를 기록합니다. 거래별 DB 기록은 별도로 유지하며 일반 이동 전체 로그와 구분합니다. 최소 필드는 시간, 오류 유형, scope/run/world/player 식별자, 세션/요청 ID(있는 경우), 저장 revision·마지막 성공 시각, 처리 단계·오류 요약·조치 결과입니다. 아이템 관련 정보는 이미 확인 가능한 요약만 남기며 모든 이동·payload 전체를 동기 로그로 저장하지 않습니다. 같은 오류는 집계·빈도 제한하고 불필요한 개인 정보·인증 정보는 기록하지 않습니다. 보존·회전·권한은 미정입니다.

### 관리자 대응 후보

| 상황 | 기본 처리·관리자 조치 |
| --- | --- |
| DB 저장 실패 | 해당 개인 상태의 dirty/오류 유지·제한된 재시도·기록. 전환/복원만 필요한 범위에서 막고, 무관한 진행의 전체 정지를 기본으로 하지 않음 |
| 월드 저장·언로드 실패 | 성공으로 오기록하지 않고 실제 로드 상태 유지, 해당 진행 오류 기록·관리자 확인. 강제 삭제/자동 빈 월드 대체 금지 |
| 비정상 종료 후 아이템 불일치 의심 | 로그·마지막 성공 저장 시점·가용 DB/월드 백업을 대조. 모든 플레이어를 자동 rollback하거나 세대가 다르다는 이유만으로 전체 입장을 차단하지 않음 |
| payload 손상·버전 미지원·진행 소유권 불명 | 해당 범위 접근 제한, 원본 보존 후 관리자가 복구·변환·수동 조정 판단 |
| 수동 지급·회수·백업 복원 | 조치 전 대상 데이터 보존·중복 작업 확인, 승인된 범위에서만 적용. 사유·대상·수량·조치자·시각·근거·결과 기록 |

관리자는 영향을 받은 플레이어/진행·상자 위치와 오류 시점을 확인하고, 필요한 범위만 임시 제한한 뒤 로그·백업·현재 상태를 비교하는 방향입니다. 일부 유실·복사는 수동 지급/회수·상태 보정으로 처리할 수 있습니다. 근거가 부족하면 불확실성을 기록하고 자동 재지급하지 않습니다. 상자 또는 인벤토리 한쪽만 과거 상태로 복원하면 불일치가 커질 수 있으므로 범위·시점을 함께 검토합니다. 정확한 전체 이동 재구성은 필수도 보장도 아닙니다.

이번 작업에서 로그·관리 명령·복원 도구를 구현하거나 운영 데이터를 보정하지 않았습니다. 실제 데이터 덮어쓰기·복원·삭제·서비스 조작에는 별도 승인이 필요합니다. 자동 복구 확대는 경량성·성능 근거가 있을 때만 별도로 검토합니다.

## 8. 보호와 자원 채집

확정 원칙: 스토리는 전체 보호·지정 구역 건축 허용, 경제는 주요 도시·공용 시설 등 지정 구역 보호·일반 지역 자유도 확대, 주요 자원 수급은 양쪽 전용 채집 인던 중심입니다. 건축 지형 변경과 채집은 별도 정책입니다.

기본 보호 엔진은 스토리·경제 모두 **WorldGuard**입니다([ADR-0014](decisions/0014-worldguard-protection-engine.md)). 기존 Hearth 자체 범용 보호 엔진·별도 공간 중첩/우선순위 엔진 후보는 제외합니다. WorldEdit는 제작/관리 도구로 사용하되 공식 설치 문서상의 dependency와 선택 버전 실제 런타임 요구를 S4에서 확인합니다. 경제 프로세스 분리 자체는 미정입니다.

WorldGuard는 건축/파괴·보호 구역/일반 간접 변경과 중첩/flags 판정을 담당하고, Hearth는 검증된 run/콘텐츠의 NPC/퀘스트 세계 변경·접근 격리·채집 reset/generation·전용 예외만 검사합니다. 대화/상호작용 허용을 건축 허가로 해석하지 않고, 내부 직접 월드 변경이 WorldGuard만으로 자동 차단된다고 가정하지 않습니다. 자세한 책임/보호 시험 W1~W13은 ADR-0014에 둡니다.

월드 생성/로드 시 (run,world_instance,물리UUID/key/name)에 독립 구역 데이터를 연결하고 manager/정책 검증 전 입장·변경을 허용하지 않는 후보입니다. 저장/언로드는 구역 저장 성공 확인·런타임 연결/참조 해제 뒤 수행하되 영속 구역 설정을 삭제하지 않습니다. 재로드/채집 새 세대는 같은 run/현 world 매핑과 정책 버전을 검증합니다. 파일 경로/이름·null/error·WorldGuard 캐시 수명주기는 S4 검증입니다. WorldGuard 구역 YAML/저장 계층을 Hearth PostgreSQL 진행 데이터와 혼동하지 않습니다.

같은 story_run_id 코옵의 채집은 같은 진행 범위로 운영하고 다른 run의 자원/초기화와 분리합니다. 이는 기존 격리의 구체화입니다. 경제 소유 범위는 E1, 별도 배치 도구·반출/건축 드롭 밸런싱은 미정입니다. 정기/전원 퇴장 뒤 재입장 리셋은 ADR-0011·0013을 따르며 실패 시 해당 ERROR_HOLD/원본 보존·파괴적 리셋 보류입니다. 보호 엔진 채택은 설치/실행 승인이 아닙니다.

### 필드 인던 스폰·난이도 (ADR-0005·0007 확정 / 구현 모델 후보)

[ADR-0005](decisions/0005-dungeon-spawning-and-difficulty.md)의 구역별 인원 난이도는 ADR-0007에 따라 필드 인던(일반 파밍·개인 퀘스트·일반 필드 전투)에 적용합니다. 채집 인던의 자원 수급/수명주기와는 별개입니다. 특수 인던·보스전은 아래 별도 시작 명단 난이도를 따릅니다. 인던 몬스터를 최초부터 모두 소환하지 않고 내부 스폰 바운더리 진입으로 구역 이벤트를 발생시킵니다. 그보다 넓은 난이도 산정 바운더리 안의 **소환 시점 인원**으로 몬스터 수·체력·공격력 등을 조절할 수 있어야 합니다. 소환한 몬스터는 이후 이동에 따라 능력치를 실시간 변경하지 않고, 다음 구역에서 인원을 새로 계산합니다.

후보 흐름: 서버의 허용 진행/물리 월드 컨텍스트 확인 → 내부 경계 진입 감지 → 동일 소환 이벤트의 실행 중/실행 여부 검사 → 소환 시점 외부 경계 인원 캡처 → 난이도 설정 해석 → 소환·결과 기록. 바운더리/인원/설정 식별자·결과를 연결하고 동시 진입 요청을 순서화하는 후보입니다. 논리 이벤트 ID의 물리 저장 방식·정확한 스폰 시점·부분 실패 복구는 미정입니다. 게임 객체 조작은 서버 스레드 경계를 지키고 DB 응답을 동기 대기하지 않는 기존 원칙을 유지합니다.

반복 진입으로 같은 이벤트를 의도치 않게 중복 실행하지 않습니다. 중복 억제 표식은 영구 재소환 금지나 인던 초기화 정책을 의미하지 않으며, 세부 재실행 단위는 후속 설계가 필요합니다. 내부/외부 정확한 크기·경계 포함 규칙·인원별 배율·보스 패턴·재소환/초기화 실행·생성·소유권 및 ADR-0006·0007에 남긴 복귀/사망/부활 상세는 미정입니다. 길목 초기화 선택지·보스 명단/복귀 정책은 ADR-0007로 확정했습니다. 전투 인던을 채집 인던과 같은 물리 인스턴스·수명주기로 가정하지 않습니다.

### 특수 인던·보스전 운영 모델 후보

정책 원문은 [ADR-0007](decisions/0007-dungeon-and-boss-operations.md)입니다. 아래 상태명·논리 키·저장 자료구조는 후보이며 확정 물리 스키마/API가 아닙니다.

| 논리 범위 | 후보 데이터와 경계 |
| --- | --- |
| 인던 실행 | run_id + dungeon_run_ref, 유형·재도전 범위·길목 초기화 범위·시작/제작자 checkpoint·설정 버전. 채집 인던과 수명주기 동일시 금지 |
| 길목 진행 | 돌파 구역·몬스터 처치 상태·checkpoint·길목 부활 최대/사용량, 개인/공유 카운터 |
| 보스 도전 | boss_attempt_ref, 시작 고정 명단·인원·난이도 기준·보스 부활 최대/사용량·상태. 새 도전과 종료 도전 구별 |
| 참가자 세션 | 도전 참조·player_uuid·생존/사망/관전, 접속 상태·종료 위치·복귀 대기·세션 세대. 접속 여부와 생존 여부는 별도 축 |
| 재도전 투표 | 도전 참조·투표 요청·대상·찬성·결과. 스토리 분기 투표 상태와 분리, 대상 변화 취소/재투표·중복 차단·기본 채팅·초기30초; 마감 경합 구현 미정 |
| 개인 컷신 | 기존 플레이어별 시청/스킵 기록 참조. 보스 도전 데이터 초기화로 시청 이력 삭제 금지 |

특수 인던·보스전은 시작 명단 인원으로 난이도를 고정하고 중간 소환도 같은 기준을 사용합니다. 사망/부활/접속 종료/재접속으로 재계산하지 않고 새 도전에서만 새 명단·난이도를 확정합니다. 길목 집결 대상은 온라인 생존자이며 오프라인/관전 사망자는 대기 검사에서 제외합니다. ADR-0013의 C1 후속 승인으로 보스 시작 당시 온라인 참가자만 시작 명단과 난이도에 반영합니다. 온라인 생존자 집결 후 보스방 진입 시 온라인 길목 사망자를 자동 부활하고 보스 시작 인원에 포함하며 길목 횟수는 소비하지 않습니다. 시작 당시 오프라인 길목 참가자는 해당 도전에 중도 참가하지 않고 다음 도전부터 참여합니다. 이미 시작 명단에 포함된 뒤 종료한 참가자는 기존 재접속 권리를 유지합니다. 길목/보스 부활 횟수는 분리하고 보스방 진입 및 새 보스 도전 때 보스 전용 횟수를 새로 설정합니다. 개인/공유 제한과 서로 다른 최대값을 지원하며 길목 없는 보스는 보스 설정만 사용할 수 있습니다.

| 전이 후보 | 확정된 동작 | 미정 경계 |
| --- | --- | --- |
| 길목 진행 → 집결/보스 시작 | 온라인 생존자 집결·온라인 사망자 자동 부활, 온라인 시작 명단/난이도 고정. 시작 당시 오프라인 길목 참가자는 다음 도전부터 | 시작/접속/이동/부활 조정의 실제 이벤트 순서·부분 실패 보류 S4 |
| 길목 일부 사망 / 전원 사망 | 생존자는 계속, 전원 사망은 실패·시작 또는 지정 checkpoint 재도전 | 재도전 시 길목 횟수 재설정 상세 |
| 보스 ACTIVE → WIPE_WAIT | 전원 사망·온라인 참가자 존재 시 진행 중단·관전 유지, 즉시 실패/자동 재시작 없음 | 보호 생존자/오프라인 혼합은 ADR-0013·§13 PAUSED 분류, 실제 이벤트 조정 S4 |
| ACTIVE/WIPE_WAIT → CLOSED | 재도전 투표 통과 또는 마지막 참가자 접속 종료 | 투표/종료/복귀 동시 경합. 특수 실패/성공 종료와 연동 |
| 투표 부결 | 재도전 미확정, 다시 요청 가능; 전멸 대기는 유지 | 기본 채팅·초기30초·중복 차단은 확정, 입력 구문/이벤트 조정 S4 |
| CLOSED → 새 도전 준비 | 인던 설정의 보스만/길목부터 재도전, 새 보스 시작 때 난이도/횟수 재확정 | 준비/개인저장/이동/월드정리 실패 보류·원본보존은 확정, 실제 I/O/배치·DB/월드 순서 S4 |

보스 명단은 시작 후 신규 합류를 받지 않되 기존 참가자는 진행 중 재접속할 수 있습니다. 접속 종료 시 즉시 캐릭터 제거·오프라인 피해 없음·위치 기억, 복귀 시 정확한 종료 좌표/방향으로 이동하며 안전 좌표 보정은 하지 않습니다. 짧은 무피해/전투 개입 불가 보호(3초는 추천값) 뒤 기존 상태로 복귀합니다. 사망자는 관전 유지, 횟수 초기화 없음, 종료 도전 복귀 불가입니다. 전원 접속 종료는 도전 종료이며 ‘접속 중 전투 가능 인원 0’ 판정으로 대체하지 않습니다. 모든 생존자 오프라인/관전자만 온라인이면 일시정지·생존자 정상 복귀 시 재개, 전원 사망/온라인은 전멸 대기·전원 오프라인은 종료입니다. 생존자 전부 오프라인/보호 중이고 온라인 참가자가 남으면 해당 보스만 PAUSED·보호시간 경과, 정상 복귀 뒤 재개합니다(ADR-0013).

재도전 투표는 기존 참가자가 전멸 전에도 요청 가능하고 현재 접속한 보스 참가자(사망 관전자 포함, 오프라인 제외)의 50% 초과 찬성으로 통과합니다. 동률/미달은 미확정·재투표 가능입니다. 스토리 투표는 공동체 중요 분기를 고정하지만 이 투표는 현재 도전 종료와 재도전 범위 적용만 수행합니다. 서로 다른 목적·대상·결과이며 공유 분기를 rollback하지 않습니다.

길목 재도전은 전체 초기화/돌파·처치 상태 유지/checkpoint 이전 유지·이후만 초기화 중 설정을 적용합니다. 보스 재도전은 보스방 앞에서 보스만 또는 시작/checkpoint에서 길목부터 중 설정을 따릅니다. 구현 후보는 새 도전 식별자·종료 표식·세션/revision 검사로 종료 도전 지연 응답·중복 재시작을 억제하는 방식입니다. 초기화 시점·지급 키/중복 보상 방지의 구체 방식은 후속 설계이며 소비품 복원·고비용 일체형 checkpoint를 추가하지 않습니다.

보스 컷신은 ADR-0006의 개인 시청 정책 그대로이며 재도전해도 시청/스킵 기록은 보존합니다. 두 번째 도전 스킵 거절 이후 동작은 미정입니다. 전투 인벤토리 유지·드롭 없음·소비품 미복원·30초 비동기 저장·관전/조건부 부활 설정·중요 진행 조건/고정 분기 투표도 유지합니다.

### 스토리 탐험·지역 접근·거점 이동 (ADR-0008)

[ADR-0008](decisions/0008-story-exploration-regions-and-fast-travel.md)은 초반 NPC/메인 중심 학습 → 제작자 지정 메인 진행 시점의 자유 탐험 개방 → 메인과 탐험/파밍/제작/서브 병행을 확정합니다. 독립 튜토리얼 월드는 필수가 아니며 별도 필수 학습 퀘스트 완료 검사를 개방의 추가 필수 조건으로 두지 않습니다. 구체 챕터·사건은 미정입니다. AI는 질문/도움 필요 시 보조하며 스토리 필수 기능 지위를 유지합니다.

개방 기준은 공동체 공유 상태이며 기존/늦은 구성원 모두 따르지만 개인 퀘스트 완료·기록을 자동 변경하지 않습니다. 중요 지역·사건의 조건은 계속 적용합니다. 지역 접근은 진입 제한/콘텐츠 제한(탐험 가능·주요 NPC/퀘스트/이벤트 조건부)/일반 개방 3종이며 공동체 상태로 판단합니다. ADR-0002의 건축/보호 정책과 별도 판정입니다.

빠른 이동은 개인이 직접 방문·해금한 출발 거점의 지정 시설에서 본인이 해금한 목적 거점으로만 실행하며 스토리/지역 권한도 검사합니다. 공동체 발견 공유·동행 초대·일괄 이동을 만들지 않고 각자 실행합니다. 늦은 구성원도 직접 방문해야 합니다. 필드/스마트폰 즉시 이동은 기본 범위 밖이며 시설 외형·교통 수단·비용·시간은 미정입니다.

| 논리 책임 | 데이터/검사 후보 (물리 스키마·API 미정) |
| --- | --- |
| 공유 탐험 개방 | run_id/공동체 범위의 메인 진행 milestone 참조·revision. 별도 학습 완료 검사 자동 추가 금지 |
| 지역 접근 | run + region 정의/정책 버전·조건 결과. 보호 구역 권한과 별도; 조건/좌표 목록 미정 |
| 개인 발견 | run/공동체 + player_uuid + hub 정의 ID·직접 방문/해금 기록. 공동체 개방과 개인 해금 다른 키 |
| 거점 이동 | 검증된 세션·출발 시설·양쪽 개인 해금·목적 지역 권한·목적 물리 월드 확인 후보. 이동 직전 최신 권한/epoch 재검사·비동기 이동 결과 확인 |

진입/콘텐츠 허가를 캐시/조회/이동 경로에 일관 적용하고 명령·포털·빠른 이동이 우회하지 않도록 하는 후보입니다. 빠른 이동의 전투/관전 이용 세부·직접 방문 인정 경계·조건 경합/실패 시 복귀는 미정이며 ADR-0007 신규 보스 합류 금지와 ADR-0003 전환 저장을 우회하지 않습니다.

### 스마트폰 아이템·6메뉴·AI·지도 (ADR-0009)

[ADR-0009](decisions/0009-smartphone-item-gui-and-information.md)에 따라 순정 기본 인벤토리·E키·제작/기존 슬롯을 보존하고 별도 전용 아이템으로 여는 슬롯 기반 커스텀 GUI를 사용합니다. 손에 든 아이템 좌클릭 또는 우클릭 호출을 목표로 하고 드롭은 불가해야 합니다. 0키 호출·E키 교체·제작 슬롯 버튼은 현행 요구가 아닙니다. 모드 없이 Paper/필요시 리소스팩 방향이며 아이템 지급 시점·위치 고정·거래/양도·복구/중복 지급 방식은 미정입니다.

기본 메뉴는 **퀘스트·월드 지도·일지·공동체·알림·설정 6개**입니다. 도감은 포함하지 않습니다. 퀘스트는 메인/서브 목록 → 선택 → 목표/완료/상세·진행이며 화면 추적 목표는 ADR-0006을 유지합니다. 월드 지도는 지역/플레이어 위치/개인 발견 거점, 일지는 자동 사건 기록(스토리/인물/탐험/연대기), 공동체는 구성원/스토리 진행/진행 조건 3개만, 알림은 개인 퀘스트 주요 변화/개인 발견만 읽음/미확인 개수/최신순으로 관리하고 공동체 알림은 저장/표시하지 않습니다. 설정은 미니맵/퀘스트 HUD·마커별 켜기/끄기(초기 전부 켜짐·개인 저장)입니다. 종류별 알림 필터는 필수가 아닙니다.

버튼으로 메뉴/상세 페이지를 연결하되 슬롯 수·아이콘·페이지 배치·Lore/책 등 표현은 기술/사용성 검증 후 선택합니다. AI 실제 대화는 기본 채팅창이며 스마트폰 별도 대화창을 만들지 않습니다. 채팅 명령/입력 모드·연동 기술은 미정입니다. AI·지도·일지·알림은 인증된 진행/개인 권한과 공개/발견 범위를 적용하고 공통 AI 검색/캐시/지연 응답에도 비공개 서사·미발견 비밀 유출을 막는 후보를 검증합니다. 공개 저장소/시험에는 실제 서사가 아닌 일반/합성 데이터만 사용합니다.

| 논리 책임 | 후보·미정 경계 |
| --- | --- |
| 전용 아이템 | 서버 식별자/버전과 인증된 개인 상태를 연결하는 후보. 식별 포맷·발급/복구는 미정; 재접속/사망/분실 예외 검증 |
| GUI 세션 | player/run/session_epoch·현재 메뉴/선택 정의 참조, 권한 재검사·오래된 callback 거부 후보. 슬롯 클릭/드래그와 일반 아이템 이동 충돌 시험 |
| 개인 기록·알림·설정 | run + player 범위 기록/읽음·개수·정렬·선호 후보. 실제 열/저장 순서·로그 보존·알림 보존/삭제·성능 한도는 미정 |
| 지도 정보 | 지역 공개 권한과 개인 허브 발견을 결합하는 후보. 기본 지리/주요 도시·마을+개인 발견, 스토리/지역 공개 제한 우선 |
| 상시 미니맵 | 스마트폰 월드 지도와 별개 화면 UI, 위치·탐험 표시 목표. S4에서 Paper/리소스팩만으로 가능한 범위 검증; 오른쪽 상단 원형 배치는 목표 확정, 실제 크기/렌더링/확대/갱신/성능 예산은 S4 검증 |

좌/우클릭과 블록 파괴·공격·아이템 사용의 충돌, Q키·인벤토리 밖 드롭을 시험해야 하며 양도 금지·슬롯 고정·자동 재지급을 해결책으로 임의 채택하지 않습니다. 전투 사망 인벤토리 유지·30초 dirty 비동기 저장 등 ADR-0003·0006을 유지합니다. 상시 미니맵은 목표 기능이며 모드 수준 자유 HUD의 기술 검증 완료를 뜻하지 않습니다. 지도 자체에서 즉시 빠른 이동하지 않습니다.

## 9. 후속 테스트와 성공 기준 (모두 미실행)

시험은 별도 승인된 환경·테스트 데이터에서 수행합니다. 실패·미실행을 성공으로 표시하지 않습니다. 횟수·동시 이용량·시간/메모리 한계는 시험 시작 전 확정하며 다음은 기능 성공 기준 후보입니다.

| ID·단계 | 시험 | 성공 기준 |
| --- | --- | --- |
| T1 / S4 | 두 템플릿 복제·로드, 반복 요청 | 서로 다른 물리 식별자·같은 요청 하나의 작업, 원본/기존 월드 보존. null·예외 시 타 진행/빈 월드로 대체 안 함 |
| T2 / S4 | 공동체 동시 입장·마지막 퇴장·재접속 경합 | 하나의 로드/저장 소유자, 다른 진행 접근 0건, 상태 준비 전 조작 불가 |
| T3 / S4 | unload false·DB 타임아웃·재시도 한도 주입 | 저장 성공 오기록 없음, 오류·원본 보존, 해당 범위 제한·관리자 대응 가능, 무한 대기·전체 잠금 없음 |
| T4 / S4 | 저장·전환 중 강제 종료와 수동 대응 연습 | 시점 불일치·영향과 확인 가능한 근거 기록, 관리자 조치 절차 확인. 일부 장애 유실·복사 허용; 자동 무손실·모든 장애 중복 0건은 요구하지 않음 |
| T5 / S4 | 정상 상자 입출고·드롭·보상·동시 저장·재접속·story/economy 전환 | 정상 경로의 중복·유실 없음, scope별 격리·저장 순서 확인. 손상 payload 덮어쓰기 금지. 강제 종료는 T4로 분리 |

| T5c / S4 | 이전 자동 저장 지연·중복 callback·동시 거래·보상·전환 | 오래된 snapshot 덮어쓰기/dirty 초기화 없음, 같은 거래/보상 한 번만 반영, source 저장 성공 전 전환 안 됨 |

| T9 / S4 | async DB·I/O 지연과 async 접근 감시 | Bukkit 비동기 위반·메인 스레드 future 대기 0건, 늦은 응답이 새 세션 상태 변경하지 않음 |
| T10 / S5 | AI 검색·캐시·대화·권한 변경 중 지연 응답 | 다른 진행/개인의 비공개 정보 유출 0건. 모델·AI 구현은 미정 |
| T11 / S6 | 활성 진행·플레이어·NPC·AI 중첩 부하 | 사전 합의 CPU·RAM·I/O·MSPT/GC·입장 지연 한계 만족, 반복 언로드 후 지속 참조 누수 없음. 클릭별 DB 트랜잭션/flush 부재 확인, 선택 안전장치의 부하·지연이 크면 제외 |

S3 완료 조건인 논리 모델/전이/실패·콘텐츠/보호 참조·검증 입력/결과 형식은 [최종 감사](s3-completion-audit.md)에서 대조했습니다. C1 승인으로 필수 충돌은 해소되어 설계 완료이며 구현은 시작하지 않았습니다. 아래 보류된 기대값은 관련 정책 승인·S4 상세화 후 보완하고 실행 전까지 통과로 표시하지 않습니다.

### 공동체 정책 시험 명세 (구현 전 준비, 모두 미실행)

| ID | 입력·상황 | 성공 기준 |
| --- | --- | --- |
| C1 | 같은 공동체 A만 개인 길목/서브 완료 | B의 개인 완료·보상 기록이 자동 변경되지 않음 |
| C2 | 고정 접속 명단 A·B 모두 중요 퀘스트 조건 충족 / B만 미충족 | 전자는 진행 가능, 후자는 차단; 개인 일괄 완료로 해석하지 않음 |

| C4 | 공동체 분기 X 확정 후 뒤늦은 개인 진행 | X 라인만 진행 가능, Y 선택·공유 분기 변경 불가 |
| C5 | 완료자가 과거 장 직접 플레이 지원·반복 요청 | 공유 NPC·세계 효과 전후 동일, 기존 분기 유지; 재참여 보상 기대값은 미정 |
| C6 | 놓친 장 N 스킵 | N 메인·필수 길목 스킵 및 N+1 개인 선행 충족, 일반 서브 일괄 스킵 없음; 보상 기대값 미정 |
| C7 | N 직접 플레이·N+1 스킵 등 장마다 다른 선택 | 선택 독립, 실제 플레이/스킵 구별, 공동체 분기·월드 변화 불변 |

C1~C13도 실제 구현과 실행 없이 통과로 표시하지 않습니다. 보상은 의도적 보류이며 내부 연결 시험을 구체화합니다. 가입/관리자 관리 기능 시험을 추가하지 않습니다. 분기/효과 상태의 DB 실패·메모리 반영 실패·재접속 시험은 정상 중복 방지와 오류 기록·수동 대응을 구분하며 자동 무손실을 요구하지 않습니다.

## 10. 미정·의도적 보류와 S4 이관

- 사용자 정책 미정: 두 번째 컷신 스킵 거절 후 동작·재시도 집계 경계, 과거 장면 재현, 길목 재도전 횟수 상세. C1 온라인 시작 명단은 ADR-0013 후속 승인으로 해소했습니다. 가입 기능은 미정이 아니라 제외입니다.
- 추천안: 복귀 보호 초기 3초·IDLE 초기 5분, 작업 ID/generation 기반 리셋 단일 소유권, 지도 3층 캐시·개인 표시 DTO, 백업 manifest/쓰기 정리 경계. 사용자 승인값/구현 완료가 아닙니다.
- S4 구현/기술 검증: 물리 SQL/버전/드라이버/풀, manifest/버전 적용 도구, 정확 좌표/카메라·원형 미니맵/고정 HUD/개인 머리 위 표식, 입력/드롭/아이템 식별, DB/월드 경합·일시정지/리셋 실패·부하·보호 이벤트 상세.
- 의도적 보류: 보상/몬스터/부활 수치·정기 채집 주기·빠른 이동 비용/시간·구체 서사/지역. 경제 E1·AI 모델/런타임은 별도 범위입니다.

| 공유 | story_run_id + quest/branch/NPC/world/event 정의 ID | 중요 퀘스트·고정 분기·NPC/세계·주요 일지 공유, 내부 run 참조만 사용 |
| 개인 | story_run_id + player_uuid + 정의 ID | 퀘스트/장 스킵·관계·장소/허브·일지/알림/설정·인벤토리/보상 격리 |
| 월드 | story_run_id + world_instance_id | 복합 FK/유일성 후보로 타 진행 참조 차단, 물리 배치/논리 진행 분리 |
| 보스 도전 | story_run_id + boss_attempt_ref + player_uuid | 참가 상태/필요 복귀 좌표(x,y,z,yaw,pitch)·사용량·도전 종료 식별. 복귀는 정확 위치, 카메라 연결과 생존 상태 별도 |
| 채집 인던 | 소유 scope + instance_ref + template_version + generation | 다음 리셋 시각·작업 ID 후보, 경제 scope와 story_run_id 혼동 금지 |
| 개인 표시 | story_run_id + player_uuid + notification/journal/setting key | 표시 off는 원본 진행 불변, 타 개인 조사/퀘스트 노출 금지 |

가입/탈퇴 테이블·역할/권한 관리 UI는 만들지 않습니다. 서버 내부 연결 정보와 진행 접근 검사는 가입 기능이 아닙니다. 실시간 투표/보스HP/관전 대상은 기본 메모리, 분기/지급/개인 진행 등 지속성 필요 상태만 DB입니다. 이 표는 DDL이 아니며 도전/프로세스 강제 종료의 자동 재개를 약속하지 않습니다.

### 분기·저장·실패 후보

분기 투표 통과 → 검증된 run/정의/예상 revision으로 비동기 영속화 요청 → 성공 확인 뒤 확정 결과/세계 적용의 순서입니다. DB commit 실패/불명에는 확정이라고 안내하거나 효과/보상을 재실행하지 않고 같은 요청 상태를 확인하는 후보입니다. 접속 변경은 OPEN에서만 취소/재투표하며 과반수 입력마감 뒤에는 재계산하지 않습니다. 성공/실패/불명 결과를 동일 요청 ID로 구분하는 ADR-0013 전이를 따릅니다. 이미 확정 결과는 취소하지 않습니다. 30초 dirty 저장·버전/revision·즉시 거래/보상 저장 조정과 스토리/경제 전환 저장은 기존 6.1~6.5를 유지합니다. 무관한 진행은 가능한 한 계속 운영합니다.

### 지도·일지·메뉴·HUD 후보

공유 기본 지도 캐시 + run 변경 영역 묶음 갱신 + 개인 발견/목표/NPC 표식 DTO를 합성하는 후보입니다. 월드 지도와 미니맵의 정보 출처는 공유하지만 UI는 별개입니다. 같은 실제 월드의 주변 플레이어만 표시하며 비밀 제한은 물음표의 정확/대략 좌표에도 선행합니다. 기본 도시 표시가 개인 거점 해금을 바꾸지 않습니다. 새 퀘스트 ?/보고 !는 개인 판정·초록 ! 우선이고 머리 위 표식은 미니맵 토글과 분리합니다. 목표 단계별 정확/대략/비공개와 다중 추적을 표시 한도와 분리합니다.

일지는 공유 사건/개인 사실/연대기 시각을 분리하고 동일 반복 대화 dedup·새 사실 상세 갱신 후보를 사용합니다. 공유 사건 열람은 개인 완료/보상이 아니며 경험 전 공유 기록에는 구분 문구를 둡니다. 알림 생성기는 개인 퀘스트 주요 변화/발견만 허용 목록으로 처리하고 공동체/접속/투표/일지/잡담/일반 획득/매 처치 알림을 생성하지 않습니다. 읽음/모두 읽음/개수/정렬/관련 페이지는 개인 키로 검사합니다.

공동체 하위 3개(구성원/스토리 진행/진행 조건), 일지 내부 4개(스토리/인물/탐험/연대기), 기본 최상위 6개는 별개 계층입니다. 분기 상세는 퀘스트 메뉴, 투표와 안내는 채팅이며 스마트폰 기록/투표 화면을 추가하지 않습니다. 설정 기본 켜짐/저장과 HUD 최대 표시 수·보이는 개수를 분리합니다. 긴급 전투→부활 횟수→중요 퀘스트→발견 순 출력 조정자 후보와 BossBar/ActionBar 후보는 S4에서 확인합니다.

### 보스·카메라 전이 후보

생존/접속/보호/카메라 연결은 별도 상태 축입니다. 정상 전투 가능한 생존자가 있으면 ACTIVE, 생존자 전부 오프라인/복귀 보호 중+온라인 참가자가 있으면 PAUSED, 생존자 정상 복귀 뒤 ACTIVE, 전원 사망/온라인이면 WIPE_WAIT, 전원 오프라인이면 CLOSED 후보입니다. 복귀 보호 중 대상은 보호 종료까지 자동 관전 연결하지 않습니다. 대상 사망/로그아웃→유효 생존자로 교체 또는 명시 해제/자유 관전 대기, 정상 생존자 등장→재연결, 종료→연결/카메라 상태 정리입니다. 카메라 실패는 생존/사망 변경 금지입니다. 복귀 정확 좌표 정책은 조건부 부활의 안전성 검사와 분리합니다.

### 채집 리셋 전이 후보

| 단계 후보 | 처리/실패 경계 |
| --- | --- |
| OPEN → RESET_PENDING | 정기 시각 또는 빈 인던 다음 입장, operation_id와 예상 generation으로 단일 작업 획득 |
| RESET_PENDING → EVACUATING | 정기 시 잔류자 사전 안내/입구 이동, 새 입장·채집 차단, 개인 획득품 유지 |
| EVACUATING → RESETTING | 개인 저장/이동/월드 정리/템플릿 준비 확인 후 재구성; 실패 시 원본 보존·해당 ERROR_HOLD·파괴적 초기화 보류(확정) |

주기 값·물리 배치·경제 소유 단위·리셋 I/O 구현은 후속입니다. 스토리 채집은 story_run_id 범위, 경계 저장/이동/준비 확인과 실패 보류는 확정입니다. 메인 월드 IDLE/언로드와 이 작업을 같은 타이머로 취급하지 않습니다.

### 백업·콘텐츠·관측 후보

승인된 유지보수에서 관련 쓰기 정리·DB/월드/콘텐츠 버전 식별 기록·원본 보존·백업·복원 대조를 검토하며 매 이동 동기 checkpoint를 추가하지 않습니다. 파일/DB 원자성·강제 종료 무손실은 보장하지 않습니다. 업데이트는 영향 영역/변경 블록 충돌 확인→호환 콘텐츠/안정 ID 검사→영향 범위 보존→부분 적용→결과 확인 후보이고 충돌은 보류·실패는 정상 상태 유지입니다. rollback은 적용 범위/버전·원본으로 검토하며 실제 도구는 S4입니다. Zabbix 서버/연결/저장 실패/메모리/틱 지연 후보만 기록하고 설정은 만들지 않습니다.

## 13. G1~G4 후속 상태·경합 명세 (모두 미실행)

원문은 ADR-0013·0014입니다. 아래 이벤트 조정자·표식·상태명은 승인 정책을 구현하기 위한 후보이며 실제 SQL/Paper/WG 검증은 S4입니다. 게임 내 가입/탈퇴 기능과 내부 연결 정보는 계속 분리합니다.

### G1 투표 입력/DB 경계

서버의 run/attempt별 직렬 처리 경로 후보에서 OPEN의 표/접속/마감 이벤트를 하나씩 최신 상태로 판정합니다. 과반수면 INPUT_CLOSED로 선택·요청을 고정하고 접속/만료로 재계산하지 않습니다. 스토리는 PERSISTING→성공 CONFIRMED→APPLIED, 실패 SAVE_FAILED/미확정, 불명 RESULT_UNKNOWN/같은 요청 조회·경쟁 확정 차단입니다. 결과 적용 실패는 저장된 분기 rollback/재지급이 아니라 적용 오류로 구분합니다. 보스 재도전은 (기존attempt,retry_request) 중복키 후보로 기존 종료/새 준비 한 번만 수행합니다. 모든 투표표 DB 원장·전체 서버 잠금을 추가하지 않습니다.

| ID | 순서화 입력 fixture | 예상 결과 |
| --- | --- | --- |
| VOTE1 | N=4,2표 후 대상변경→지연3번째표 | 기존 OPEN 취소, 새 명단 재투표, 구 vote_ref 표 무시 |
| VOTE2 | N=4,3번째찬성→대상변경/timeout→DB성공 | 먼저 입력 마감·재계산 없음, DB 성공 후 한 분기만 확정/적용 |
| VOTE3 | N=4,timeout→3번째표 / 3번째표→timeout | 전자는 미확정, 후자는 마감 유지. 직렬 순서/동일 요청 증거 기록 |
| VOTE4 | 입력마감→DB확실실패 / commit응답소실 | 전자는 최종확정/세계적용 없음, 후자는 기존 요청 확인 전 새 분기 차단 |
| VOTE5 | 같은 retry요청·같은DB완료/효과 callback 반복 | 기존 보스 종료/새 준비·분기효과 한 번, 늦은 세션/attempt 거부 |

### G2 보스 상태·결과 경합

도전별 처리 경로 후보는 최신 생존/접속/보호 상태로 정상생존≥1 ACTIVE, 생존자 있으나 모두 offline/protected이고 온라인 남음 PAUSED, 전원사망+온라인 WIPE_WAIT, 전원offline CLOSED를 판정합니다. PAUSED에서는 해당 보스 AI/공격/스킬/전용타이머만 정지·보호시간 경과, 정상생존 보호종료→재개입니다. 개인/무관 퀘스트 실패는 도전 종료 원인이 아니며 직접 필수 실패 확정만 종료합니다. 먼저 유효하게 직렬 확정된 승리/실패/종료 결과는 terminal이고 후속 이벤트/보상/효과를 중복 적용하지 않는 후보입니다.

| BOSS1 | A정상생존,B관전 / A종료 / A보호중복귀 / A보호종료 | ACTIVE→PAUSED→PAUSED→ACTIVE; 보호clock만 경과·타 run 계속 |

### G3 채집 범위·세대 전이

추천 키는 (story_run_id,instance_ref,current_generation,operation_ref)이며 같은 run 코옵은 동일 범위, R1/R2는 독립입니다. OPEN→RESET_PENDING(입장/채집차단)→준비/개인저장/입구이동/월드정리 확인→RESETTING→완료/보호연결검증 후 generation 전진·OPEN입니다. 준비/이동/저장 실패는 파괴 단계 이전 ERROR_HOLD/원본 보존, 일부 파괴 작업 실패도 성공/세대 표시 없이 해당범위 수동 판단입니다. 일반 dirty30초 비동기 저장·필수 경계 저장만 사용하며 매 획득 DB 쓰기/전체 checkpoint는 없습니다.

빈 주기와 그 주기를 충족한 reset_generation은 추천 표식입니다. 정기 강제피난 자체를 새 방문/퇴장 주기로 세지 않는 후보이며 정기 리셋 성공이 이미 빈 주기를 충족하면 다음입장 리셋을 재생성하지 않고 새 방문/전원퇴장 주기만 새 계기가 됩니다. 종료/복귀의 session/generation을 검사해 이전 세대 위치로 진입시키지 않습니다. 빈월드 언로드/지연 초기화는 최적화 후보입니다.

| --- | --- | --- |
| RESET1 | R1 A/B코옵·R2 C, R1일부퇴장→전원퇴장→다음입장 | 일부유지·전원뒤다음입장1작업, R2자원/상태 불변 |
| RESET2 | 잔류정기안내→개인저장/입구이동/템플릿준비 중 각각 실패 | 입장/채집차단·파괴적리셋 보류·원본/해당ERROR_HOLD, 타 run 계속 |

### G4 보호·동적 월드 명세

범용 보호/구역 중첩은 WorldGuard, 제작/관리 도구는 WorldEdit(실제 dependency S4확인), Hearth는 콘텐츠 권한/run격리/리셋/전용예외입니다. 구역 manager/파일도 run/물리월드별 연결·검증하고 저장완료 확인 뒤 참조 해제하며 영속 구역은 언로드로 삭제하지 않습니다. W1~W13의 직접/간접/경계/중첩/시설/NPC내부/run침범/채집/동적수명주기 시험은 ADR-0014에 명세했습니다. 버전별flags/성능은 S4 미검증, WorldGuard 구역멤버는 코옵 가입 기능이 아닙니다.

시험 결과 형식은 §12 그대로이며 입력순서/설정/전후 DB·world·WG manager/실제관측·오류/미실행을 기록합니다. G1~G4와 BOSS6/C1은 승인 정책 및 명세로 정리됐고 최종 감사에 따라 S3 설계 완료입니다. 명세 충족은 실행통과와 다릅니다. 후속 S4-1은 합성 월드·블록·구역 API 경로만 확인했으며, 이 절의 G1~G4/BOSS6 전체 기능 시험은 미실행입니다.

BOSS6/C1의 **온라인 시작 명단 최종 승인**과 기대값은 ADR-0013 및 [감사 문서](s3-completion-audit.md)에 기록했습니다. 시작 직전 접속 판정·자동 부활·명단 고정을 도전별 순서화 전이로 조정하는 구현 후보를 S4에서 시험합니다. 고정 전 종료는 이번 명단 제외, 고정 후 종료는 기존 참가자 복귀로 분류하는 후보이며, 부분 이동/부활 실패 시 성공한 시작으로 기록하지 않고 해당 준비를 보류합니다. 보스 신규 참가 금지·정확 복귀·온라인 사망자 자동 부활 정책은 유지합니다.
