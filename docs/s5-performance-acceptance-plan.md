# S5 소규모 코옵 성능 검증 계획

정리일: 2026-11-17. 기준 `253f9a5`. 초기 계획은 기존 증거에 근거해 정리했으며, 후속 [계측·두 논리 요청 배치](s5-ai-observation-verification.md)에서 구현/제한 검사를 진행했다. 사용자가 선택한 목표 사용량과 아직 정하지 않은 운영 조건을 구분한다. [현재 현황](PROJECT_STATUS.md), [격리 예산 ADR-0018](decisions/0018-local-ai-runtime-and-trial-budget.md), [명시적 준비 ADR-0022](decisions/0022-explicit-ai-preparation-and-admission.md)를 따른다.

## 목표 사용량과 결정 경계

사용자는 1차 성능 기준으로 **동접 4명·스토리 진행 1개·동시 AI 요청 2개**를 선택했다. 이를 검증할 목표로 기록하며, 서버의 접속 인원/진행 수 제한이나 운영 설정을 변경하지 않는다.

| 항목 | 상태/기준 |
| --- | --- |
| 플레이 범위 | 한 스토리 진행에 플레이어 4명 |
| AI 사용 | 준비가 끝난 상태에 독립된 두 접속이 동시에 요청; 기존 추론 병렬 1개·대기 1개 구성에서 처리 |
| 질문 비율/빈도 | 플레이어별 분당 질문 수, 자료/계산/일반 질문 비율, 평상시와 순간 집중 비율은 미정 |
| 운영 자원 배정 | 상시 CPU·RAM·GPU/VRAM·디스크, AI와 Paper/PG의 배치 및 다른 서비스와의 공유 예산은 미정 |
| 사용자 응답 목표 | 버튼부터 결과 표시까지 허용 시간·실패율/백분위 목표, 준비/과부하 안내 허용 기준은 미정 |
| 게임 성능 목표 | 같은 플레이 구간의 TPS/MSPT·틱 지연/GC 허용 기준과 측정 구간은 미정 |
| 장기 안정성 | 연속 운영 시간·지속 부하 기준은 미정. 현재 600초 격리 시험으로 장기 수용을 대신하지 않음 |

후속 [합동 관측](s5-joint-observation-verification.md)에서 사용자가 격리 합산 RSS 6GiB를 선택했고 공유 시계/감시를 구현·실행했다. 격리 시험의 중단 상한은 운영에 배정한 자원이 아니다. 기존 CPU 2개/nice 10·AI 트리 표본 RSS 4GiB/GPU 5GiB·호스트 가용 RAM 6GiB·총 600초/작업 550초·개별 90초는 유지한다. 이는 샘플 감시 기준이며 자원 예약이나 커널 하드 제한 보장이 아니다. 모델/컨텍스트/큐·시간 상한을 성능 합격에 맞춰 자동 확대하지 않는다.

## 재사용할 관측과 적용 한계

아래 수치는 서로 다른 코드 버전/입력의 제한된 순차 관측이다. 소요 시간의 평균/백분위나 처리량을 합쳐 계산하지 않는다. 상세 원시 기록은 링크한 기존 증거를 재사용한다.

| 기존 증거 | 확인한 관측 | 이번 목표에 남은 공백 |
| --- | --- | --- |
| [콜드 준비](../verification/s5-ai-preparation-result.json) | 준비 76,402ms, 이후 첫 질문 1,022ms. 사전 준비 없는 질문의 자동 로딩 거부 | 운영 준비 일정/빈도·유휴 후 사용 경험과 동시 요청은 미판정 |
| [구조화 계산](../verification/s5-calculation-comparison-result.json) | 선택한 계산의 실제 생성 7개는 1,316~5,011ms, 캐시 확인 10ms | 동일시각 두 질문의 대기/완료, 게임과의 동시 실행은 미판정 |
| [자료 묶음 후속 질문](../verification/s5-grounded-followup-result.json) | 실제 생성 7개는 1,180~2,934ms, 캐시 확인 5ms. 자료 번호/후속 질문·이력 제외를 부분 확인 | 순차 질의 결과이며 동접 4명/동시 AI 2개 수용 근거가 아님 |
| [같은 배치의 Paper/PG](s5-grounded-followup-verification.md) | 1 JVM·PG 1개에서 조회/캐시·개인 정보·버전 변경 경계 확인 | Paper/PG와 AI는 순차 실행. 합동 자원/TPS·실제 클라이언트 부하는 미측정 |

AI RSS/GPU 최대 표본을 상시 필요량/최대 동접으로 환산하거나, 다른 시각의 Paper/AI 메모리를 더해 운영 합격으로 판단하지 않는다. 합성 자료의 성공을 일반 과학 정답률·실제 코옵/장기 성능으로 확대하지 않는다.

## 현재 제한과 계측의 의미

- HTTP 작업 상한 4개와 모델 추론 병렬 1개/대기 1개, 접속별 대기 작업 1개를 구분한다. HTTP 상한을 동시 추론 가능 수로 읽지 않는다. 준비·모델 신원 조회·캐시 확인도 사용자 생성과 별도다.
- 어댑터의 일반 요청 6초는 버전/manifest·적재 확인과 생성 작업의 한도다. [`PhoneChat`](../src/main/java/io/github/jesterportfolio/hearth/phone/PhoneChat.java)의 답변 대기 8초 뒤에는 **별도의 후속 검증 대기 8초**가 적용된다. 전송 전 PG 조회·미리보기와 클라이언트의 ‘응답 확인’ 조작도 있으므로 기존 8초를 버튼부터 화면 표시까지의 전체 응답시간 목표로 사용하지 않는다. 현재 한도를 변경하는 계획이 아니다.
- [`MeasuredAssistant`](../src/main/java/io/github/jesterportfolio/hearth/phone/MeasuredAssistant.java)의 누계는 생성/준비/캐시 신원 확인별 시작·성공·실패·취소·진행 수, 평균/최대·6개 지연 구간이다. [`hearthai status`](../src/main/java/io/github/jesterportfolio/hearth/phone/AssistantDiagnostics.java)는 이 누계를 읽으며 조회로 추론/초기화하지 않는다.
- 백엔드 성공과 자료 표시·PG/현재성 검사 후 수용·최종 화면 관측을 구분한다. 캐시 lookup hit/신원 확인 성공도 실제로 수용한 캐시 응답 수가 아니다. 집계 구간만으로 정확한 p95/p99를 복원하지 않는다.
- 후속 `PhoneTelemetry`는 확인한 전송부터 전송 전 PG 조회/답변 대기/후속 검증과 서버 수용까지 집계한다. 격리 합동 시험은 구간별 실제 틱 표본/GC와 자료 화면 읽기 완료를 추가했다. 실제 클라이언트 표시를 포함한 전체 타임라인·개별 SQL/독립 모델 큐 대기 시간은 없다. API 총시간의 잔여분을 임의로 큐 대기 시간이라고 부르지 않는다. 플레이어가 실제 화면을 읽은 시점도 내부 Future 완료로 판정하지 않는다.

## 성능 배치의 구현 범위와 후속 조건

관련 계측과 실행 경계를 먼저 한 배치로 구현한 뒤 최종 코드로 필요한 검사를 묶는다. 성공한 기존 기능/같은 조건 검사를 성능 계획만으로 다시 실행하지 않는다.

| 순서 | 한 배치에 포함할 작업 | 판정/경계 |
| --- | --- | --- |
| 1. 관측 연결 | 준비/생성/캐시·전송 전 조회·후속 PG 검증·현재성 수용/거부·대기 중 상태의 시각/결과를 구분 | 질문/답변/문맥·UUID/진행 ID·주소/오류 원문을 운영 집계에 넣지 않음. 유한한 집계와 시험 표본만 사용 |
| 2. 목표 부하 고정 | 한 진행의 4명 플레이 흐름과 실제로 겹치는 두 AI 요청, 입력 길이/자료 수/대화 수·종류·실행 횟수를 실행 전에 고정 | API 논리 접속/Chat 객체의 부하와 실제 Minecraft 플레이어 부하를 분리. 가짜 Player/인증 우회로 실제 시험을 대체하지 않음 |
| 3. 동시 요청·거부/취소 | 준비 후 순차 기준 → 두 요청 동시 도착 → 초과 요청/혼잡 안내 → 취소·늦은 응답 → 독립 질문/캐시의 흐름을 한 런타임에서 확인 | 고정된 정상 2요청 시나리오에서 한 요청의 BUSY/시간 초과를 정상 2요청 수용으로 세지 않음. 명시적 초과 부하 사례의 예정된 거부는 별도 집계 |
| 4. 게임과 함께 측정 | 같은 기간의 격리 Paper/PG/AI, TPS/MSPT·메모리/GC·PG 조회 지연·대화 수용 결과를 연결 | 현재 스크립트 두 개를 각자의 600초 시계로 병렬 실행해 합동 시험으로 취급하지 않음. 공유 최초 시계·합산 6GiB 감시/정리는 구현해 제한된 제어 세션을 관측했다. 실제 플레이/운영 부하는 운영 배정·질문 빈도·수용 기준 확인이 선행 조건 |
| 5. 한 번의 최종 확인 | 영향받은 단위/PG 경계와 합동 부하를 최종 코드 기준으로 구성하고 새 소유 경로·증거로 실행 | 격리 `/home/server/hearth-tmp`, localhost, 기존 EULA/자원·시도 제한 유지. 변경 영향이 없는 전체 기능 회귀·두 번째 JVM은 반복하지 않음 |

동시 요청은 다른 접속/개인 자료를 사용하고 권한/버전·세대 변경을 확인한다. 캐시 성능을 높이기 위해 PG 검사를 생략하거나 인벤토리/저장 계약을 바꾸지 않는다. 두 요청 모두 실제로 겹쳤는지 시작/완료 구간을 기록한다. 준비 전후·캐시 여부·성공/거부/취소를 섞어 속도 개선으로 보고하지 않는다.

서버 수용 계측과 합성 자료의 두 논리 요청·취소/재요청·캐시 재검증은 구현·검사했다. 후속 합동 시험은 공유 최초 시계·합산 6GiB 감시와 한 진행 네 논리 세션/실제 PG·모델을 구현·관측했다. 실제 4명 입력과 운영 질문 빈도/전체 수용은 미실행이다. 기존 단일 AI/순차 Paper 도구가 곧바로 운영 수용량 시험을 지원한다고 주장하지 않는다. 운영 서비스·Docker/Zabbix/SSH/방화벽·드라이버/패키지·영속 데이터 변경은 별도 승인 범위다.

## 수용 판정과 다음 결정

안전 경계는 현재 계약대로 유지한다. 교차 개인/진행 정보 노출, 오래된 자료·늦은 응답의 잘못된 수용, 권한 검사 생략·원본 손상은 수용할 수 없다. 자원/시간·정리 한도 위반이나 모델 불일치도 성공으로 바꾸지 않는다. 실패 원본을 보존하고 수정한 범위의 검사만 다시 실행하며, 새 시계/상한으로 자동 반복하지 않는다.

현재 확정된 것은 목표 사용량과 합산 RSS 6GiB를 포함한 격리 상한이다. **동접 4명/진행 1개/동시 AI 2개 수용은 아직 PASS가 아니다.** 상시 운영 자원, 질문 빈도/종류와 종단 간 응답·게임 성능/실패율 기준이 채워져야 운영 수용 기준을 확정할 수 있다. 그 전에는 관측 연결·유한 동시성 경계 구현과 제한된 선별 결과를 준비할 수 있으나 처리량/백분위·장기 수용을 확정하지 않는다.

초기 계획 정리에서는 문서 확인만 했다. 후속 계측 배치의 실행 횟수·관측·미검증 범위는 [전용 검증 기록](s5-ai-observation-verification.md)을 따른다.
