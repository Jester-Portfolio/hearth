# AI 준비와 첫 사용자 요청의 경계

확인일: 2026-11-17. 기준 `2459dc0` 이후 구현. [ADR-0022](decisions/0022-explicit-ai-preparation-and-admission.md)를 따른다. **최종 내부 검사와 사용자가 별도 승인한 새 1회 콜드 시험을 통과했다.** [최종 JAR·각 단계/원시 결과](../verification/s5-ai-preparation-result.json)에서 첫 실패와 최종 성공을 구분한다.

## 기능·공식 계약

서버 콘솔의 `hearthai prepare`만 명시적 준비를 시작한다. 적재 확인뿐 아니라 고정 공개 노트의 초기 연산·정상 완료/자료 표시를 확인하고, 버전/manifest/적재 상태를 다시 확인한다. 사용자 질문/개인 기록은 준비에 넣지 않으며 준비 응답을 대화에 표시/저장하지 않는다. 이미 준비가 확인됐으면 조회만 한다. 준비/일반 요청/캐시·종료/취소의 슬롯과 수명을 구분하고 `PREPARATION` 집계를 추가했다. `hearthai status`는 새 HTTP 요청 없이 기존 집계만 읽는다.

질의는 매번 고정 버전/manifest와 적재 상태를 확인한다. 적재 목록만으로 초기 연산을 마쳤다고 추측하지 않으며 해당 어댑터의 성공 준비 표식도 필요하다. 모델 해제/실패한 준비/다른 모델·컨텍스트는 질문을 자동 로딩으로 바꾸지 않는다. `NOT_READY`/`PREPARING` 안내와 초안을 유지한다. 유효한 캐시는 기존 신원/현재 권한을 확인해 새 추론 없이 재사용할 수 있다. 메타/질의 6초·화면 8초·준비 최대 90초, 4개 HTTP·2스레드/큐·8192바이트·4096/128토큰·60초 keep-alive·기본 Mock/비활성을 유지한다. 운영 설치/서비스/배포·자동 유지 작업은 실행하지 않았다.

적재 모델 목록은 [Ollama `/api/ps`](https://docs.ollama.com/api/ps)를 따르며 컨텍스트/모델 digest를 검사한다. 빈 요청의 적재 경로는 [고정 v0.40.16 구현](https://github.com/ollama/ollama/blob/v0.40.16/server/routes.go#L519)과 [공식 생성 API](https://docs.ollama.com/api/generate)를 검토했다. 그 경로는 적재 직후 반환하며 일반 질문의 첫 연산 완료를 보증하지 않는다. 최종 코드는 이를 고정 공개 노트의 정상 연산으로 보완했다.

## 실제 첫 관측과 보존

새 격리 `/home/server/hearth-tmp/hearth-s5-trial.16unb2yp`에서 사전 예열 없이 시작했다. 최초 구현은 빈 프롬프트 적재/고정 모델 조회를 준비 완료로 처리했고 이후 실제 과학 질문이 **`LOCAL_AI_TIMEOUT`**으로 6초 한도에 걸렸다. 원시 `run-result.json`은 **FAIL·75.827초·cleanup 오류 0**이며 `probe.log`/`ollama.log`·샘플과 첫 JAR를 보존했다. 준비 단계 성공과 첫 질문 실패를 분리하며 전체 관측을 PASS로 바꾸지 않는다.

최종 보완은 초기 연산을 포함하는 준비와 성공 Future 표식이다. 같은 코드의 내부 검사 **193개 PASS**(실패/오류/skip 0)와 이후 콘솔 표시 문자열의 관련 2개 검사·JAR 빌드로 확인한다. 준비/질의 제한 분리, 적재만 된 상태의 진입 거부·가짜/틀린 적재/버전·실패/취소·닫힘/동시 작업·콘솔 게이트·원문 비노출·준비 집계를 확인했다. Python 시험 제어 회귀 12개 PASS를 유지한다. 변경은 Java/HTTP 수명과 콘솔 연결이며 DB/인벤토리·게임 권한·월드 이벤트 계약은 바꾸지 않아 Paper/PG를 반복하지 않았다.

`scripts/s5_ai_trial.py`의 `reviewable_result`와 [시험 실행 규칙](../scripts/README.md#s5-고정-로컬-ai-격리-시험)은 시간/HTTP 실패 재개를 허용하지 않는다. 첫 실패는 허용 대상이 아니므로 멋대로 새 작업 경로/시계로 재시도하지 않았다. 코드·내부 검사와 구체적 시험 범위를 준비한 뒤 사용자가 **‘동일 상한으로 새 시험 1회 승인’**을 선택했다. 그 별도 승인으로 새 `/home/server/hearth-tmp/hearth-s5-trial.0t8_njo3`에서 한 번 실행했으며 기존 재개 허용 코드를 넓히지 않았다.

## 별도 승인한 최종 콜드 관측

최종 main JAR로 **PASS·103.270초**, 준비/첫 질의/해제 경계 12개 판정을 통과했다. 사전 예열을 생략한 새 런타임이며 준비 전 질문은 초안을 남기고 `NOT_READY`로 거부했다. 준비는 **76.402초**, 준비 후 같은 과학 질문은 **1.022초**에 정상 응답했다. 질문 제한 6초/화면 8초를 늘리지 않았다.

| 확인 | 실제 결과 |
| --- | --- |
| 준비 전 모델/질문 | 적재 없음, 질문이 로딩을 시작하지 않음, 이력 비움/초안 보존 |
| 준비 중 질문 | `PREPARING`으로 거부하며 대기열에 추가하지 않음 |
| 명시적 준비 | 고정 노트 연산·답변/자료 표시·버전/manifest·4096컨텍스트 확인 |
| 이미 준비된 상태의 준비 요청 | 추가 연산 없이 조회만 함 |
| 첫 사용자 답변 | ‘작용 팔이 길어지면 필요한 힘이 작아진다’와 `[자료 1]` 응답 |
| 유한 캐시 | 준비 상태와 시험 소유 모델 해제 뒤 모두 신원 확인 후 새 생성 없이 재사용 |
| 해제 뒤 새 질문 | `NOT_READY`, 기존 이력·새 초안 보존, 자동 로딩 없음 |
| 접속 닫기 | 이력/캐시 비움·활성 작업 0 |

서버 로그의 생성 endpoint POST 세 개는 준비 연산·사용자 연산·시험 소유 모델 해제다. 생성 요청 집계 4개 중 실제 사용자 생성 성공 1개, `NOT_READY` 2개·`PREPARING` 1개 거부를 구분한다. 준비 집계 2개(새 준비와 이미 준비된 상태 확인), 캐시 확인 2개다. 다운로드 0바이트·고정 검증 복사 4,043,062,302바이트, 최대 표본 RSS 3,281,140KiB/GPU 3130MiB·최소 호스트 가용 RAM 12,735,368KiB이며 정리 오류 0이다.

기존 실제 모델 fixture도 새 어댑터의 준비 표식을 명시적으로 얻도록 맞추고 컴파일했다. 이 다른 품질 모드들을 새로 실제 실행한 것으로 주장하지 않는다. 시험 소유 모델 해제는 전용 준비 probe에만 있고, 부모가 해당 새 workspace의 실제 시험 드라이버이며 같은 디렉터리의 Ollama serve 자식이 실행 중이어야 하도록 보호했다. 실제 성공 뒤 추가한 이 fixture의 소유권 검사와 호환 호출은 컴파일·드라이버 없는 실행 거부만 확인했으며 새 GPU 시험을 반복하지 않았다. 성공을 기록한 실제 probe 클래스도 별도로 보존했다.

실제 Minecraft/운영자 콘솔 입력·장기 유휴 후 운영 절차·목표 동시 사용량/상시 예산·운영 배포와 전체 S5 수용은 남는다. 기본 Mock/비활성과 일반 과학 계산 품질 보류는 유지한다.
