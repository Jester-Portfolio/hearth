# S4 채집 인던 초기화·저장·템플릿 세대

확인일: 2026-11-08. 기준 `a211fcd`. [ADR-0011](decisions/0011-votes-boss-return-and-gathering-reset.md)·[ADR-0013 G3](decisions/0013-vote-boss-and-gathering-state-boundaries.md)의 승인 정책을 재사용한다. 상세 수치와 산출물 식별은 [JSON](../verification/gathering-dungeon-result.json)에 한 번 기록한다.

## 구현 범위

- `gathering-demo.yml`의 명시적 합성 구역·입구·입장 위치·정기 간격·버전별 블록 정의를 읽는다. 최대 4096블록의 제한 구역형 개발 프로토타입이며 운영 채집 인던의 물리 배치를 확정하지 않는다. 전체 월드 복제·덮어쓰기는 하지 않는다. 현재 합성 구역은 64블록이며 상자/타일 상태는 지원하지 않는다.
- 같은 `story_run_id + dungeon_id`가 자원·이용자·초기화 세대를 공유한다. 다른 진행은 별도 물리 월드와 DB 행을 사용한다. 개인 아이템은 기존 `story_run_id + player_uuid` 저장을 유지한다. 경제 월드의 소유 범위를 새로 확정하지 않는다.
- 정기 시각 도달 및 전원 퇴장 후 다음 입장이 초기화 계기다. 일부만 퇴장하면 유지하며, 정기로 이미 갱신한 빈 세대에 입장한다고 다시 초기화하지 않는다. 같은 진행의 중복 초기화 요청은 한 작업으로 합친다.
- 초기화 순서는 새 입장/채집 제한 → 이미 시작한 입장 이동 정리 → 대상 구역 원본 표식 준비 → DB RESETTING → 기존 진행별 개인/퀘스트/일지 저장 장벽 → 입구 이동 → 제한 구역 블록 적용 → WorldGuard 구역/월드 저장 → 세대/CAS 저장과 표식 정리 → 공개 세대 확정이다. 대기·예약과 실제 입장 완료를 구분한다.
- 실제 개발 Player 적용기는 기존 `freezeTravel`·인벤토리 저장·안전한 `combatMove`를 재사용한다. 명령 퇴장 외 실제 경계 이탈/종료도 같은 세션의 이용자만 정리한다. 이전 세션·월드 세대·초기화 전 입장의 늦은 응답은 입장 성공으로 적용하지 않는다. 초기화 중에는 이전 구역 좌표로 강제 복귀시키지 않는다.
- 템플릿 버전과 생성 세대는 별개다. 기존 세대에 새 템플릿을 덮어쓰지 않고 다음 초기화에서 선택한다. 첫 소유권 설정 때 구역이 이미 변경돼 있으면 거부한다. 구역 밖 건축·원본 템플릿·다른 진행은 초기화 대상이 아니다.

## 실패·저장 경계

`OPEN → RESETTING → OPEN(다음 세대)`를 사용하며 실패는 해당 인던의 `ERROR_HOLD`다. 준비/개인 저장/입구 이동 실패는 파괴적 적용 전에 중단한다. 적용 이후 실패도 성공이나 새 공개 세대로 표시하지 않는다. DB CAS 실패·결과 불명은 새 요청의 자동 실행으로 해결하지 않는다.

플러그인의 소유 경로 아래 요청별 구역 원본 파일과 pending 표식을 남긴다. 성공 시 일치하는 pending 표식만 정리하고 원본 기록은 남긴다. 실패·재시작 시 pending/비정상 DB 상태·없는 버전·다른 UUID는 자동 초기화하거나 정상 상태로 해제하지 않는다. 중간 블록 적용 실패 시 일부 구역이 변경될 수 있으므로 원본 기록을 보존하고 접근을 막아 관리자 확인 대상으로 남긴다. 파일/DB의 완전 원자성이나 자동 무손실 복구를 보장하지 않는다.

V009는 초기화 상태·요청 ID·버전/해시·세대·다음 시각·전원 퇴장 표시를 추가한다. V001~V008과 기존 인벤토리 데이터는 그대로 유지한다. 기존 bounded DB worker를 사용하며 별도 풀/병렬 저장 체계, 아이템 획득별 DB 쓰기를 추가하지 않는다. 기존 30초 dirty 저장 정책과 초기화 경계의 저장 완료 확인은 구분한다.

Bukkit 블록/월드 작업은 메인 스레드의 비 ticking 시점에서 다음 틱으로 실행한다. 블록 적용은 틱당 최대 64개로 나눈다. DB/원본 파일·WorldGuard 구역 저장은 기존 worker 경로를 사용한다. 입장/초기화와 안전 시점 대기는 개발용 30초 작업 한도를 두며, 무제한 동일 틱 재예약이나 메인 스레드 DB 대기를 하지 않는다. 한 인던의 실패가 다른 진행을 정지시키지 않는다.

## 개발 모드·남은 범위

`gathering-verification-enabled: false`가 기본이다. JVM의 `hearth.verification.gathering`도 명시해야 한다. 자동 통합은 기존 도구의 `--sessions --quests --story-batch --gathering`을 사용한다. 자동 시험은 제어 시계를 같은 `pulse` 경계에 연결하며 실제 60초 경과·Player 텔레포트 성공으로 해석하지 않는다.

향후 사용자가 실제 시험을 요청하면 새 수동 세션 환경에서만 준비한다. 온라인으로 복원된 시험 프로필에 콘솔 `hearthverify gathering-fixture <프로필>`을 실행해 기존 행을 연결하거나 명시적 새 fixture를 만든 뒤, 본인의 `/hearthgather enter`·`/hearthgather leave`로 시험한다. 실제 수동 모드에서만 초 단위 스케줄러가 정기 시각을 검사한다. 이 절차의 실제 인증 행동은 이번에 실행하지 않았다.

독립 물리 채집 월드·운영 배치/주기/자원 밸런스·빈 인던 지연 초기화/언로드 최적화는 후속이다. 일반 서버 활성화·보스 재도전·전투 인던 초기화·경제 소유권을 바꾸지 않았다. 다음 관련 개발 후보는 복수 길목·체크포인트·보스 연속 진행이다. 전체 S4는 진행 중이다.
