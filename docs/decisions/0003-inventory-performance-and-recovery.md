# ADR-0003: 성능 우선 인벤토리 저장과 수동 장애 대응

- 결정일: 2026-10-23
- 상태: **승인** — 사용자가 인벤토리·아이템 관리 운영 원칙을 확정함
- 관계: [ADR-0001](0001-story-world-multiworld.md)의 진행 격리와 [ADR-0002](0002-stack-and-world-policies.md)의 스택·월드 정책을 유지하며, 인벤토리 저장 책임과 장애 복구 범위를 구체화함
- 범위: 설계 문서. 구현·성능·복구 검증 완료나 운영 적용 승인이 아님

## 배경과 판단

기존 [S3 초안](../story-world-detailed-design.md)은 파일·DB를 같은 세대로 복원하기 위한 고비용 체크포인트와 자동 복구 후보를 포함했습니다. 사용자는 **서버 성능과 원활한 플레이 > 복잡한 자동 장애 복구**를 우선하도록 결정했습니다. 따라서 그 후보를 필수 요구에서 제외하고, 정상 동작의 기본 안전성과 수동 장애 대응을 기준으로 상세화합니다.

## 결정

1. 일반 상자·창고의 아이템은 Minecraft 월드 파일에 저장합니다. 플레이어 인벤토리는 PostgreSQL 중심으로 관리하며 스토리·경제 및 진행별 분리는 유지합니다. 일반 상자를 거래 전용 DB 보관함으로 대체하지 않습니다.
2. 정상 플레이의 중복 요청·동시 전환·오래된 저장 덮어쓰기는 기본적인 동시성 제어와 저장 순서로 예방합니다. 이 목표를 낮추기 위해 정상 동작의 재현 가능한 중복·유실을 방치하지 않습니다.
3. 일반 플레이어 인벤토리는 **변경된 데이터만 30초 간격으로 비동기 배치 저장**합니다. 30초는 초기 운영값이며 성능 측정 후 설정으로 조정할 수 있도록 합니다. 일반 아이템 이동·클릭마다 DB 트랜잭션이나 동기식 디스크 flush를 하지 않습니다. 스토리·경제 월드 전환 시에는 이전 인벤토리 저장 완료를 확인합니다. 배치 크기·타임아웃·재시도 한도는 미정입니다.
4. 복잡한 거래 전용 보관 시스템, 고비용의 파일·DB 일체형 체크포인트, 완전 자동 복구는 필수 요구사항에서 제외합니다. 일반 저장·언로드마다 전부 복사하거나 두 저장소의 원자성을 만들지 않습니다.
5. 추가 안전장치는 구현이 단순하고 성능 영향이 작을 때만 도입할 수 있습니다. 서버 부하·플레이 지연이 커지면 생략합니다. 비용이 큰 선택 기능의 부재를 완료 차단 조건으로 사용하지 않습니다.
6. 예기치 못한 서버 장애로 월드 파일과 DB의 저장 시점이 달라져 일부 아이템 유실·복사가 생길 수 있음을 수용합니다. 관리자가 최소 오류 로그와 가용 백업을 참고해 수동 조정할 수 있습니다. 로그·백업만으로 모든 아이템 이동을 재구성할 수 있다는 보장은 하지 않습니다.
7. 최소 오류 기록과 관리자 조치 절차는 유지합니다. 저장 실패·손상 데이터를 빈 상태로 조용히 덮어쓰지 않고, 오류 범위와 확인 가능한 저장 상태를 남깁니다. 자동 무손실 복구나 모든 상황의 아이템 복사 방지를 보장하지 않습니다.

## 자동 저장·즉시 저장의 추가 확정 정책

- NPC 상점 구매·판매와 플레이어 간 경제 거래는 30초 주기를 기다리지 않고 거래마다 즉시 DB에 반영합니다. 퀘스트 보상도 중복 지급을 방지하고 지급 상태를 즉시 저장하는 방향입니다.
- 거래 시 현재 아이템 보유 상태를 검증하고 관련 인벤토리 변경·화폐 변경·거래 기록의 일관성을 관리합니다. 최근 30초 내 아직 DB에 쓰지 않은 인벤토리 변경도 포함해야 합니다.
- 일반 자동 저장과 즉시 저장의 순서가 뒤집혀 이전 snapshot이 최신 상태를 덮지 않도록 합니다. 동일 거래는 중복 실행하지 않습니다. DB 저장 실패를 거래 성공으로 표시하거나 아이템·화폐를 중복 지급하지 않습니다.
- DB 작업은 비동기로 처리하며 메인 스레드에서 DB 응답을 동기 대기하지 않습니다. 여기서 즉시는 **주기적 자동 저장을 기다리지 않는 거래별 저장**이지 메인 스레드 동기 SQL 또는 지연 시간 보장이 아닙니다.
- 필요한 플레이어·아이템 상태만 잠시 보호하고 전체 서버를 잠그지 않습니다. 연결 풀·제한된 재시도·타임아웃은 간결한 구현을 우선합니다.
- 게임 메모리 반영과 DB 트랜잭션은 자동으로 원자적이지 않습니다. 일반 상자·월드 파일까지 DB 트랜잭션으로 보호하지 않으며 비정상 종료의 일부 유실·복사는 기존 수동 대응 정책을 유지합니다.

인벤토리 변경·화폐·거래 기록을 한 DB 트랜잭션에 넣는 구체 후보, 저장 revision·중복 키·메모리 적용 순서는 [S3 상세 설계](../story-world-detailed-design.md)에서 검토합니다. 이들은 미구현·미검증입니다. 필수 거래 기록은 전체 아이템 이동 원장이나 복잡한 escrow 시스템과 구분합니다.

## 기본 안전성과 선택 기능의 구분

기본 상세 설계 후보는 플레이어/진행별 단일 저장 순서, revision·세션 검사, 중복 요청 억제, 메인 스레드의 상태 캡처와 비동기 DB 저장, 제한된 재시도입니다. 실제 방식은 S3에서 검토하며 적용·성능 검증은 미실행입니다. 상자 이동은 정상 Minecraft 처리 경로를 쓰고, 매 클릭마다 DB와 원자적으로 동기화하는 전용 프로토콜을 요구하지 않습니다.

전환 중 짧은 조작 제한이나 저장 오류가 난 플레이어의 입장/전환 차단은 기본 저장 질서를 위한 후보입니다. 장시간 전체 서버 잠금·매 이동 flush·자동 백업 전체 복원으로 확대하지 않습니다. 진행 격리·원본 보존·기본 오류 기록은 성능 이유로 생략하는 선택 기능에 포함하지 않습니다.

고급 자동 복구·거래 escrow·체크포인트 테이블·전체 아이템 이력은 필요성과 비용을 별도로 검토할 선택 기능입니다. 현재 기본 구현 범위에 넣지 않습니다. 이는 백업 자체나 향후 승인된 유지보수·A안 이전의 백업/롤백 계획을 폐지하는 결정이 아닙니다.

## 수용한 위험과 후속 검증

- 비정상 종료·저장 실패 시 최근 변경이 유실되거나 상자/플레이어 간 저장 시점 차이로 일부 복사가 생길 수 있습니다.
- 정상 플레이에서는 상자 입출고·드롭·보상·동시 저장·재접속·진행 전환의 중복·유실을 시험하고 재현 가능한 결함은 수정해야 합니다.
- 장애 주입 시험은 위험·영향·오류 로그·수동 조치 가능성을 확인합니다. 자동 무손실 또는 모든 장애에서 중복 0건을 성공 조건으로 삼지 않습니다.
- 일반 자동 저장의 초기값은 30초로 확정했습니다. 배치 크기·타임아웃/재시도·백업 주기/보존·로그 회전/보존·허용 성능 지표·수동 조치 권한/도구는 미정입니다. 모든 항목은 미구현·미검증입니다.

## 관리자 대응과 운영 범위

최소 기록·대응 후보는 S3 초안에 둡니다. 실제 데이터 보정·백업 복원·아이템 지급/회수·서비스 중단은 이번 문서 작업에 포함하지 않습니다. 운영 변경과 데이터 덮어쓰기에는 기존 승인 정책과 사전 보존·롤백 원칙을 적용합니다. 정책 변경이 필요하면 후속 ADR로 이 결정을 대체하고 연결합니다.
