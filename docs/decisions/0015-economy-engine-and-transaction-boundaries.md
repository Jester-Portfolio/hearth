# ADR-0015 — 경제 엔진·거래·스토리 분리 경계

- 작성일: 2026-11-07
- 상태: 이번 요청 범위의 격리 개발 구조 채택. 운영 E1의 화폐·배치·밸런스 정책은 미확정.
- 관련: [ADR-0002](0002-stack-and-world-policies.md), [ADR-0003](0003-inventory-performance-and-recovery.md), [ADR-0012](0012-progress-storage-world-lifecycle-and-content.md), [ADR-0014](0014-worldguard-protection-engine.md)

## 대안과 선택

| 후보 | 재사용·정합성 | 예상 비용·장애 경계 | 판단 |
| --- | --- | --- | --- |
| A. 플러그인 내부 Java 엔진 | 기존 세션·41슬롯 codec·CAS·제한 DB worker·NPC/GUI·월드 수명주기 재사용 | 별도 프로세스/통신 없음. 계산을 메인 스레드에서 실행하면 위험하므로 분리 필요 | 기반으로 선택 |
| B. Python 별도 서비스 | 별도 시뮬레이션 실험에는 유용. 현재 제공된 Python 시뮬레이터는 없음 | 추가 프로세스·HTTP 직렬화·장애/배포/모니터링, DB와 게임 적용의 복수 경계 필요 | 이번에는 제외. 성능 열등을 측정한 것은 아님 |
| C. Java 순수 계산 + DB 작업 + Paper 적용 분리 | A의 재사용을 유지하면서 계산을 Bukkit/SQL에서 분리 | 기존 제한 worker에서 계산/트랜잭션 실행, owner executor로 게임 적용. 작은 배포 단위 유지 | 최종 선택. 별도 네트워크 서비스 없이 C 구조로 A 구현 |

호스트 CPU/RAM에 대한 위 비용 비교는 구조적 추정이다. Java/Python 동등 구현 간 실측 우열은 주장하지 않는다. 이번 Java 측정값은 [검증 기록](../economy-verification.md)에 둔다. 경제 프로세스의 실제 운영 배치와 목표 동시 이용량은 후속 E1에서 결정한다.

## 기성 도구 검토

[VaultAPI 공식 저장소](https://github.com/MilkBowl/VaultAPI)는 경제 공급자 연동 API이고 LGPL-3.0이다. 지역 생산·운송·Hearth 인벤토리와 같은 DB 트랜잭션을 제공하는 엔진으로 간주하지 않는다. [QuickShop-Hikari 공식 문서](https://quickshop-community.github.io/QuickShop-Hikari-Documents/)는 Paper 상자 상점과 개발 API를 제공한다. 이번 NPC 기반 지역 시장·경제 전용 재고/41슬롯 CAS를 대신할 근거가 부족하다. 둘 다 설치·채택하지 않았으며 Paper 26.2 완전 호환성을 검증한 것으로 기록하지 않는다. 후속 외부 경제 연동이 필요할 때 해당 버전·라이선스·유지보수를 다시 평가한다. 기존 NPC와 인벤토리 GUI를 이용하며 Citizens는 도입하지 않는다.

## 데이터와 실행

- 경제 소유권은 `realm_id`, 개인은 `realm_id + player_uuid`. 물리 월드 UUID는 소유권 키가 아니다. 스토리의 `story_run_id` 데이터와 공유하지 않는다.
- 기존 V001~V008을 보존하고 별도 `hearth_economy` 스키마의 E001을 checksum으로 관리한다. 기존 SQL owner Context 타입을 재사용하되 경제 전용 발급자와 adapter를 사용한다. 기존 스토리 저장소는 경제 Context를 신뢰하지 않는다.
- 엔진의 결정적 순서는 도착 → 제조/생산 → 실제 소비 → 출발 재고 예약 → 가격 갱신 → 종료 사건 정리다. 시설·경로 순서는 콘텐츠 정의 순서다. 사건은 요청 ID 순서로 적용한다.
- 운송은 출발 시 재고 차감, 도착 시 목적지 증가. 요청 ID와 도착 표시를 같은 Tick 트랜잭션에서 반영한다. 운송 중 수량을 어느 지역의 판매 가능 재고로도 세지 않는다.
- 경제 Tick은 설정 주기로 제한 worker에서 실행한다. 같은 realm 행 잠금과 expected Tick으로 거래·중복 Tick을 순서화한다. 다른 realm의 상태는 변경하지 않는다. worker/연결 풀은 기존 제한을 공유하므로 실행 자원은 전용으로 무제한 늘리지 않는다.
- 오프라인은 콘텐츠의 `PAUSE` 또는 `CATCH_UP_CAPPED`를 제공한다. 보정은 realm 잠금 아래 마지막 시각과 함께 원자적으로 처리한다. 상한을 넘는 경과분은 버린다. 이번 fixture는 PAUSE이며 운영 정책 확정이 아니다.
- 사건은 생산 효율·지역 수요·경로 차단의 수치 데이터다. 엔진은 부족/과잉/활성 사건 신호를 읽기 전용으로 제공한다. 스토리·퀘스트의 실제 조건 연결은 후속이며 서사를 하드코딩하지 않는다.

## 가격 선택과 한계

단순 현재 재고 비율 가격은 빠르지만 경계에서 흔들리고 수량 전체를 같은 단가로 거래하면 분할 매매로 악용하기 쉽다. 이번 구현은 다음을 분리한다.

1. 생산/운송 공급 능력과 수요 사건을 반영하는 기준 가격에 EMA·변화율 상한을 적용한다. 플레이어가 재고를 낮춘 것만으로 다음 Tick 기준 가격까지 끌어올리지 않는다.
2. 목표 재고 대비 현재 재고의 선형 한계가격에 상·하한을 적용한다. 거래 총액은 재고 구간의 적분으로 계산한다. 수량 반복 대신 최대 세 구간을 계산한다.
3. 매수 가산·매도 할인, 매수 올림·매도 내림을 적용한다. 동일 기준 가격에서 역거래하면 이익이 나지 않는다. 사건·시간·지역 간 정상 차익까지 금지하는 모델은 아니다.
4. 생산은 목표 재고와 기본 수요까지 채우도록 제한한다. 목표 재고의 자동 학습은 구현하지 않는다. 적응형 목표는 수요 관측·검증 비용과 조작 위험을 더하므로 후속 후보로 남긴다.

정수 수량·화폐 최소 단위와 BigDecimal 적분을 사용한다. 임시 수치·화폐 이름·초기 자산·시설·수요·효율·Tick 주기는 `economy-demo.properties`에 둔다. 실제 화폐 형태나 게임 밸런스 승인으로 해석하지 않는다.

## 거래 경계

- 현재 세션·경제 월드·NPC·거리·화면·세대 확인 → 최신 dirty 저장 정리 → 불변 41슬롯 캡처 → 경제 트랜잭션 → owner 스레드 인벤토리 적용 순서다.
- realm 잠금 후 견적 revision·재고·잔액·인벤토리 CAS를 재검사한다. 계정 payload/잔액·시장 재고·요청 기록은 하나의 PostgreSQL 트랜잭션이다. GUI는 서버의 견적을 선택할 뿐 가격이나 소유권을 결정하지 않는다.
- 고유 요청 ID의 재전달은 기존 결과를 조회한다. 같은 ID의 다른 내용/소유자는 거부한다. 일반 저장은 같은 계정 revision을 사용하므로 오래된 payload가 거래를 덮지 못한다.
- 확인 가능한 재고/잔액/견적 거부는 거래를 실행하지 않고 다시 조회할 수 있다. SQL 실패·CAS·commit 불명·늦은 세션 적용은 HOLD 및 원본 보존. 불명 결과는 같은 요청 ID의 영수증을 조회하고 자동 재지급/재차감하지 않는다.
- DB commit과 실제 클라이언트 적용은 원자적이지 않다. commit 뒤 적용 실패는 HOLD와 관리자 수동 대응 대상이다. 강제 종료 무손실, escrow, 아이템 이동별 DB 기록을 약속하지 않는다.

## 운영 적용 전 경계

일반 서버 기본 비활성. 기존 격리 루트·JVM gate·설정이 모두 필요하다. 격리 전용 경제 세션 adapter는 스토리 adapter와 동시에 같은 플레이어 이벤트를 관리하지 않는다. 수도 상인·개발 잔액·계정 생성은 명시적 fixture에서만 준비한다. 일반 최초 접속/계정 생성·스토리↔경제 이전·운영 화폐·오프라인 정책·운영 배포는 이번 결정에 포함하지 않는다.

실제 NPC 클릭/GUI/다인 행동, 운영 규모 Tick·조회 인덱스/정리 주기·백업/롤백·미확정 E1 규칙 검토 뒤에만 운영 적용을 판단한다. WorldGuard 구역 저장은 [공식 스레드 계약](https://worldguard.enginehub.org/en/latest/developer/regions/managers/)에 따라 worker에서 완료를 기다리고 Bukkit 월드 저장/언로드는 기존 안전한 owner 시점에서 수행한다.

## 2026-11-07 후속 구현 — 상점/관리 경계

E002로 거래 기록 조회 인덱스를 추가하고 E001 행·파일을 보존한다. 콘텐츠 취급 상품 목록과 이름, 본인 기록 keyset 조회를 연결한다. commit 불명/롤백 요청의 영수증·DB revision/payload를 확인한 뒤 오프라인·정리 완료 HOLD 임대만 관리자가 폐기할 수 있다. 이전 실패 future·dirty·월드 HOLD는 보존하며 DB 수정/재실행/강제 해제를 하지 않는다. 운영 정책 변경을 뜻하지 않는다. [조건·검증·명령](../economy-desk-verification.md)을 따른다.

## 2026-11-07 후속 구현 — 공개 시장 정보

경제 계산을 재작성하지 않고 상태/효율/수요 계산을 재사용하는 읽기 전용 시장 DTO와 상점 연결을 추가한다. 콘텐츠의 공개 지역·상품·시설·운송로·사건 목록을 적용하며 계정·인벤토리·물리 식별자는 담지 않는다. 화면 조회/새로고침은 경제 상태를 변경하지 않는다. 상세 조건과 [검증](../economy-report-verification.md)을 따르며 운영 공개 정책이나 미확정 게임 규칙의 확정을 뜻하지 않는다.

## 2026-11-08 후속 구현 — 복수 지역 상인

상인 ID별 지역·취급 상품·위치를 콘텐츠에서 연결하고, 같은 경제 realm의 인벤토리/화폐를 재사용해 지역 간 거래를 지원한다. 화면은 선택한 상인·실제 엔티티·월드 세대에 연결한다. 기존 단일 설정·시장/계정/영수증·스키마를 유지하고 NPC는 저장 데이터의 소유권 키로 사용하지 않는다. 수도/광산의 두 배치는 공개 시험 콘텐츠이며 운영 지역·운송비·빠른 이동 정책의 확정이 아니다. [검증](../economy-merchants-verification.md)을 따른다.

## 2026-11-08 후속 구현 — 최근 Tick 실적

최근 완료 Tick의 지역/상품별 생산·제조 투입·소비·미충족 수요·도착·출발·전후 재고를 E003 집계로 저장한다. 기존 Tick/시장/운송 트랜잭션과 같은 경계를 사용하며 CAS 중복 실행과 실패 시 원본 보존을 유지한다. realm의 실적 Tick 표식으로 업그레이드 전 미등록과 기록 후 누락을 구분한다. 최근 집계만 덮어쓰므로 저장 행 수는 지역×상품에 한정되며, 과거 전체 이력이나 고비용 체크포인트를 추가하지 않는다.

공개 DTO는 콘텐츠의 지역/상품 필터를 유지하고 실제 실적과 시설의 현재 재고 단독 생산 가능량을 구분한다. 격리 콘솔의 등록 사건 예약은 기존 요청 ID 멱등성을 재사용한다. 운영 경제 정책이나 새로운 사건/밸런스 확정이 아니다. [검증과 비용](../economy-flow-verification.md)을 따른다.
