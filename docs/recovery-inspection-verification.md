# 관리자 읽기 전용 복구 진단·비교

확인일: 2026-11-09. 기준 `d8e35f5` 이후 코드. 사용자는 현재 실제 접속 불가로 답해 클라이언트 시험을 보류했다. 이번 배치는 [ADR-0003](decisions/0003-inventory-performance-and-recovery.md)의 성능 우선·수동 장애 대응과 [ADR-0016](decisions/0016-s4-personal-features-and-recovery.md)의 원본/HOLD 보존에 필요한 조회 기능을 추가한다. 상세 해시·수치·원시 로그는 [검증 JSON](../verification/recovery-inspection-result.json)에 기록한다.

## 사용 범위

기존 격리 개발 모드의 S4 모듈이 준비된 서버 콘솔에서 사용한다. 일반 서버 자동 활성화나 운영 적용은 수행하지 않았다. `hearth.recovery` 권한이 있어도 플레이어·명령 블록은 실행할 수 없다.

```text
hearthrecovery help
hearthrecovery list [page]
hearthrecovery inspect <story_run_id UUID> <player_uuid UUID>
hearthrecovery compare <report UUID>
```

- `list`는 서버가 이미 검증해 등록한 연결을 페이지당 최대 6개씩 조회한다. 전체 DB 구성원 목록이나 온라인 명단이 아니다. `inspect`의 UUID는 기존 연결을 찾는 키이며, 입력값으로 새 문맥·개인 행·세션을 만들지 않는다. 물리 월드 UUID를 진행 ID로 대체할 수 없다.
- 보고서는 개인/진행 ID·DB 관측 시각·revision·전체 payload SHA-256과 제한된 상태 요약을 출력한다. 진행 본문·원시 인벤토리 NBT·대화 내용·복귀 좌표는 출력하지 않는다. 기존 인벤토리와 개인 기능 기록을 읽고, 별도의 메인 스레드 런타임 관측으로 월드 세대·세션·dirty/저장 중·엔더/장면/전투 HOLD를 표시한다.
- DB의 한 SELECT는 동일 MVCC 관측으로 개인 인벤토리와 엔더 등 기능 행을 읽는다. DB 읽기와 런타임의 전후 관측은 하나의 원자적 상태가 아니다. 읽는 동안 연결·세션·세대·저장 상태가 달라지면 변경 또는 대기 표식을 남긴다. 전투의 `restart_policy=HOLD`는 재시작 정책이며 현재 세션의 HOLD와 구분한다.
- DB 작업 및 해시/엔벌로프 검사는 기존 비동기 작업자에서 실행한다. 메인 스레드는 런타임을 관측하고 보고서를 출력한다. 동시 명령 1개, 쿼리 제한 4초, 개인 기능 64행·획득 payload 4MiB, 캐시 최대 16개·10분을 적용한다. 캐시에는 원시 payload·Player·Session을 넣지 않는다. 연결이 교체되면 과거 보고서로 재조회할 수 없으며 종료 후 늦은 결과는 출력하지 않는다.
- `compare`는 같은 개인/진행의 이전 보고서와 현재 저장 데이터의 revision·길이·해시를 비교한다. 읽기 한도로 보지 못한 행·해시는 미확인으로 남긴다. 변경 없음은 저장 바이트/메타데이터의 비교 결과이며 정상 판정이나 복구 승인으로 쓰지 않는다. 보고서 ID는 재시작 후 유지되지 않는다.

관리자는 `list`/`inspect`로 상태를 확인하고 보고서 ID를 보존한 뒤 `compare`로 저장 원본의 변화 여부를 볼 수 있다. SQL 실패는 성공 보고서로 바꾸지 않고 기존 보고서를 유지한다. 손상·미인식 기록은 해시/문제 표식으로 남긴다. 개인 엔더/스마트폰 발급 행의 부재는 빈 보관함이나 아이템 부재의 증거가 아니다. 엔벌로프 검증은 NBT 아이템의 유효성·소유권 검사가 아니다. 실제 수정은 원본·로그·백업과 결과를 확인하는 별도 수동 대응 절차를 따른다. 이 명령에는 초기화·재확정·지급·복귀 claim·이동·HOLD 해제가 없다.

## 검사 결과

- 관련 단위/회귀 **52개 PASS**: 신규 진단/콘솔 18개와 기존 세션·개인 엔더·장면 34개. 권한·검증 연결/교체·만료/캐시 한도·중복/종료 지연 결과·범위 혼합 거부, DB 실패의 이전 보고서 유지, 해시 미획득의 미확인 비교, 손상/미인식 기록과 NBT 비출력을 검사했다.
- 최종 Gradle JAR의 `--sessions --quests --story-batch --recovery-inspection --accept-eula`는 **세션 assertion 46회(고유 26개), 38.999초 PASS**. 실제 Paper 콘솔 명령 등록, ACTIVE/RETURN_PENDING/RETURNING/잘못된 월드 기록의 조회 불변, 미완료 장면·발급 기록·손상 엔더 보존, 외부 발급 문맥·없는 개인 거부를 확인했다.
- 실제 격리 PostgreSQL에서 8회 연속 41/27슬롯 원자 저장과 12회 조회를 경합시켜 revision 쌍의 일관성을 확인했다. 실제 CAS 실패 후 rollback 원본, 실제 SQL 조회 실패 후 이전 보고서와 복구 후 원본·revision 보존을 검사했다. SQL 실패 유도용 테이블 이름 변경/복원은 새 시험 DB의 fixture에서만 수행했으며 애플리케이션 진단 경로는 SELECT만 실행한다.
- 4MiB 초과·65개 기능 행 fixture의 획득 한도/불완전 표식, 기존 A의 두 개인 및 B의 인벤토리 수량/revision 보존을 확인했다. 잘못된 CLI 조합 **3개**는 작업 경로 접근 전에 거부했다. Python 구문·변경 Markdown 링크/형식·diff도 확인했다.
- 기존 EULA·일반 사용자 소유 새 `/tmp`·localhost·600초/작업 550초·heap 1536MiB/RSS 중단 2560MiB·CPU 2/nice 10 한도를 유지했다. DB 1개/Paper **1 JVM**이 종료했고 모든 소유 프로세스/포트가 정리됐다. 저장·복원 계약을 바꾸지 않아 두 번째 JVM은 생략했다. 초기 새 fixture의 괄호/람다 이름 컴파일 오류는 수정하고 최종 관련 검사와 빌드를 통과했다. 초기 로그도 덮어쓰지 않았다.

## 미검증·후속

실제 인증 클라이언트의 개인/코옵·아이템/시설·팩/HUD·전투/복귀·장애 수용은 사용자 재개 요청 전 보류한다. 운영 장애 복구·데이터 수정·재시작·배포, 실제 강제 종료/파일시스템 실패, 장기 부하/TPS/MSPT는 수행하지 않았다. S4 실제 수용과 S5 필수 로컬 AI·S6 콘텐츠/성능·S7 운영 및 경제 단계의 완료는 별개다. 현재 남은 범위는 [S4 수용 작업](s4-remaining-work.md)을 따른다.
