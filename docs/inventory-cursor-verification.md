# 기본 인벤토리 조작·저장 경계 통합

2026-11-05. 격리 개발 모드 전용이며 S4는 진행 중이다. [이전 조작 기반](player-interactions-verification.md)을 확장했고 [결과 JSON](../verification/inventory-cursor-result.json)에 최종 실행과 최초 실패를 함께 기록했다.

## 구현한 사용자 동작

- 본인 기본 인벤토리의 보관 슬롯 0~35에서 좌/우 클릭 집기·나누기·배치·합치기·교환 및 드래그를 허용한다. 장비/보조 손은 기존 커서 없는 Shift·숫자키 조작을 유지한다.
- 제작 슬롯·외부 컨테이너·개발 GUI 아이템 이동·바깥 클릭 버리기·더블클릭 수집·크리에이티브 조작은 제한한다. 드래그는 변경할 모든 raw 슬롯을 본인 보관 슬롯으로 확인한다. 다른 플러그인의 취소는 해제하지 않는다.
- 커서에 든 아이템은 별도 영속 슬롯을 만들지 않고 기존 41슬롯 스냅샷 사본의 보관 공간에 합친다. 일반 캡처는 실제 커서나 배치를 변경하지 않는다. 메타데이터가 같은 아이템만 최대 수량 안에서 합치며 원본을 보존한다.
- 인벤토리 닫기·개발 GUI/명령 전환·보상 트랜잭션·명시적 저장 장벽·퇴장 전에 커서를 실제 보관 슬롯으로 정리한다. 정리할 공간이 없으면 변경 전에 거부하고 저장 경계는 HOLD로 보존한다. 커서를 들고 있는 동안 바닥 아이템 줍기를 제한해 보관 공간 경합을 줄인다.
- 기존 다음 틱 캡처·dirty·30초 비동기 저장·CAS·세션 교체·진행별 저장 장벽을 재사용한다. 클릭별 DB 저장과 새 스키마는 추가하지 않는다. 보상 등 기존 게임 기능은 같은 저장 경계를 거친다.

이는 개발 모드의 41슬롯 호환 처리이며 커서 자체의 신규 영속 정책이나 컨테이너/제작 지원 확정이 아니다. 일반 서버에 자동 활성화하지 않는다.

## 실제 수행한 검사

- 관련 단위·회귀 **29개 PASS**: 클릭/액션·슬롯·드래그 범위, 비활성/다른 화면 차단, 저장 장벽의 정리 순서, 정리 실패 시 writer 차단/HOLD, 퇴장 저장·빠른 재접속 대기, 기존 저장/전환·보상 관련 회귀.
- 최종 JAR 빌드 PASS. 기존 `--sessions --player-interactions`를 확장한 한 JVM·독립 PostgreSQL 통합 **PASS**, 32.727초. 실제 Paper ItemStack/인벤토리 객체에서 합치기·분리·이름/Lore 보존·왕복·공간 부족 시 원본 보존을 확인했다.
- 서버 내부 제어 세션에서 커서 포함 스냅샷→dirty→DB revision 1 저장→퇴장 정리→새 세션 복원과 같은 진행의 다른 개인·다른 진행 데이터 보존을 확인했다. 실제 인증 플레이어 이벤트 시험은 아니다.
- 별도 저장 시험 인스턴스에 실제 SQL 쓰기 거부를 주입해 기존 DB 값·revision·dirty·HOLD 보존을 확인했다. 정상 세션을 실패 시험 데이터로 대체하지 않았다.
- 최초 실행은 새 실패 시험 명령의 라우터 등록 누락으로 중단됐다. 정상 풀 종료 표식 누락을 포함한 FAIL 원시 결과를 보존했고 프로세스 종료 코드는 모두 0이었다. 등록 수정 후 새 격리 경로에서 통과했다. 사전 소유 표식 누락으로 프로세스 기동 전 거부된 로그도 별도 보존했다.
- 최종 Paper 최대 RSS 1,085,464KiB, 관측 CPU 58.37초, 시작 준비 13.235초. 최소 관측 가용 RAM 11,663,100KiB. 기존 힙/CPU/시간/메모리 한도를 유지했고 정상 종료·프로세스/포트 반환·최종 빌드와 실행 JAR 해시 일치를 확인했다.

## 미검증과 다음 범위

인증 클라이언트 클릭·드래그·화면 닫기·로그아웃 중 실제 PlayerInventory 동작, 다른 플러그인과의 이벤트 경합은 미검증이다. 실제 시험은 사용자 별도 요청 전까지 보류한다. 저장 형식과 복원 계약은 기존 41슬롯 그대로라 이번 두 번째 JVM은 생략했다. 강제 종료의 자동 무손실 복구는 보장하지 않는다.

제작·컨테이너·엔더 상자와 장기 부하는 이번 범위 밖이다. 후속 배치는 기존 전투/퀘스트 기반의 종료 복귀·길목/체크포인트 연결 등 남은 플레이 흐름을 선정하며 동일 저장 시험 확장만 반복하지 않는다.

API 근거는 [Paper InventoryDragEvent](https://jd.papermc.io/paper/26.1.2/org/bukkit/event/inventory/InventoryDragEvent.html)의 raw/변환 슬롯 구분과 [PlayerInventory](https://jd.papermc.io/paper/26.1.2/org/bukkit/inventory/PlayerInventory.html)의 보관·장비 구분을 참고했다. 대상 Paper 26.2 호환성은 현재 고정 의존성의 컴파일과 위 런타임 범위로 확인했다.
