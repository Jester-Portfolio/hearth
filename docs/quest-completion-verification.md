# 개인 퀘스트 실패·보상·장별 따라잡기 통합

2026-10-29 · 격리 개발 모드 · S4 진행 중. **선정한 기능 묶음의 내부 자동 검증 PASS**.

## 구현 범위

| 기능 | 동작·경계 |
| --- | --- |
| 실패·재시작 | 개인 ACTIVE → FAILED → ACTIVE. 진행 유지/제작자 지정 목표 체크포인트/첫 목표를 콘텐츠로 선택. revision은 계속 증가하며 완료·스킵은 재시작하지 않음 |
| 실패 입력 | 콘텐츠에서 허용한 사망/목표 실패/시간 초과만 처리. 사망 이벤트 연결과 서버 내부 목표 실패 경계 제공. 호위·전투 엔진 자체는 만들지 않음 |
| 시간 초과 | 기본 비활성. 합성 정의의 2초는 시험값. 절대 만료 시각을 저장하고 기존 목표·완료 요청에서도 만료를 검사. Paper 주기 작업과 재접속 복원으로 실패 처리. 실콘텐츠의 오프라인 시간 계산 정책은 미정이며 절대시각 방식은 개발 후보 |
| 저장 경합 | 실패가 목표 저장 중 발생하면 해당 저장 뒤 처리하고 같은 진행 저장 장벽에서 대기. 정리/busy 해제까지 단일 완료 future로 연결. stale/DB 오류는 성공으로 표시하지 않음 |
| 아이템 보상 | 외부 데이터의 아이템 종류·수량과 지급 로직 분리. 실제 완료 저장과 PENDING 지급 기록을 같은 트랜잭션에 기록. 기존 완료 데이터에 소급 보상을 만들지 않음 |
| 보상 지급 | 현재 41슬롯의 최신 변경을 기존 저장 경로로 정리한 뒤, 일반 36슬롯만 사용. 지급 기록 GRANTED와 인벤토리 revision/payload를 한 DB 트랜잭션에서 저장. 장비/보조 손·상자·커서는 보상 대상으로 변경하지 않음 |
| 보상 오류 | 중복은 같은 퀘스트 지급 기록으로 확인. 공간 부족은 드롭·부분 지급 없이 PENDING 유지. DB 거부/commit 불명·stale/적용 실패는 HOLD와 원본을 보존. dirty가 없어도 HOLD 저장을 성공 반환하지 않음 |
| 장별 선택 | 공동체가 이미 완료한 등록 단계의 장만 개인 따라잡기 대상으로 제공. 직접 플레이는 기존 NPC/지역·개인 퀘스트로 안내. 스킵은 명시한 메인/필수 길목만 원자적으로 SKIPPED 처리하고 다음 개인 선행 조건 충족에 사용. 일반 서브 퀘스트는 목록 밖에 두어 보존 |
| 스킵 의미 | 실제 COMPLETED·개인 대화/비밀 발견·보상 지급과 구분. 이미 실제 완료한 퀘스트/지급 기록은 보존. 공동체 분기·NPC·세계 상태를 되돌리거나 재적용하지 않음. 스킵 보상은 POLICY_PENDING으로 두며 0개 지급 정책으로 확정하지 않음 |
| 표시·입력 | 목록/상세/NPC/추적 HUD에 FAILED·SKIPPED를 구분. 스마트폰 상세의 재시작·보상 버튼, 퀘스트 목록의 장별 따라잡기 연결. 명령은 본인의 ACTIVE 세션만 사용하고 다른 플레이어/run 인자를 받지 않음 |

개발 명령은 `/hearthquest retry <quest_id>`, `/hearthquest claim <quest_id>`, `/hearthquest chapters`, `/hearthquest chapter-play <chapter_id>`, `/hearthquest chapter-skip <chapter_id>`다. 실제 인증 플레이어의 완료 후 보상 호출도 연결했지만 이번 시험은 내부 서비스·제어 인벤토리 범위다. 플레이어 메모리와 DB는 자동으로 원자적이지 않으며 비정상 종료 무손실을 보장하지 않는다.

## 데이터·활성화

V001~V006 원본·기존 완료/ID/인벤토리를 보존하고 **V007**에서 `deadline_millis`, FAILED/SKIPPED 상태, 지급 기록 `quest_reward`, 개인 `chapter_skip`을 추가한다. 개인 키는 `story_run_id + player_uuid`이며 물리 월드 UUID를 소유권으로 쓰지 않는다.

`quest-rules-demo.yml`의 실패 조건·재시작 방식·목표 인덱스 체크포인트·시간·아이템 보상·장별 필수 퀘스트/공유 단계 연결을 초기 로딩에서 검증한다. 체크포인트는 목표 진행 위치이며 월드/아이템 rollback이나 강제 순간이동을 의미하지 않는다. 기존 파일은 덮어쓰지 않는다. 새 규칙은 `quest-completion-verification-enabled`와 JVM `hearth.verification.questCompletion`을 명시한 기존 격리 세션/퀘스트/스토리 모드에서만 활성화한다.

보상은 새 NPC/퀘스트 플러그인 없이 기존 저장·세션 경계를 재사용한다. 아이템 비교·스택 처리의 API는 [Paper 26.2 공식 ItemStack 문서](https://jd.papermc.io/paper/26.2/org/bukkit/inventory/ItemStack.html)를 확인했다. 외부 경제·화폐 라이브러리는 추가하지 않았다.

## 검사·현재 판정

- 최초 전체 단위 192개 중 1개가 실패했다. 저장 완료와 busy 해제 순서 경합을 수정하고 관련 퀘스트 147개를 재검증했다. 최종 HOLD 수정 후 인벤토리/세션 29개도 PASS. 변경 없는 나머지 결과와 합쳐 중복 제외 **192개 유효 PASS**이며 같은 검사를 관례적으로 반복하지 않았다.
- 첫 Paper/PG 묶음: 첫 JVM PASS, 새 JVM의 내부 온라인 명단 누락으로 `NO_ONLINE_TARGETS` FAIL. 실패와 종료 확인 누락을 보존하고 소유 PID/포트를 확인했다. fixture 명단 준비를 수정한 두 번째 묶음은 두 JVM PASS.
- 세 번째 묶음: 최종 HOLD 경계 변경을 포함해 두 JVM PASS. 세 재시작 정책·실제 타이머·reward CAS/공간 부족/중복/실제 DB 정책 거부·원본/장벽/HOLD·장 스킵/서브 보존/다른 run·새 JVM 복원을 확인했다. 합성 인벤토리의 최신 20개 → 일반 저장 revision 1 → 보상 23개/revision 2를 확인하고 중복 지급/새 JVM에서도 유지했다.
- 세 번째 실행 총 **53.985초**, Paper 최대 관측 RSS 약 **1038MiB**, CPU **62.45초/32.11초**, 최소 가용 RAM 약 **11.3GiB**, 정상 종료·프로세스/포트 반환 PASS.
- 최종 점검에서 시간 제한 퀘스트의 추적 조회가 새 deadline 필드를 포함하지 않던 구형 Saved 매핑과 FAILED 추적 허용 상태를 맞췄다. 기존 상한 뒤 사용자의 재개 지시로 추가 **1묶음**만 수행해 최종 수정본의 시간 제한 추적·실패 후 추적을 실제 PG에서 확인했다. 추가 실행 두 JVM **PASS**, 총 **56.662초**, 최대 Paper RSS 약 **1016MiB**, CPU **65.03초/31.71초**, 최소 가용 RAM 약 **11.4GiB**다. 기존 자원 제한·정상 종료·소유 프로세스/포트 반환을 지켰으며 최종 소스 빌드/설치/실행 JAR 해시가 일치한다. [JSON](../verification/quest-completion-result.json)에 네 시도·기존 단위 결과·해시를 구분했다. 변경 없는 단위 검사는 다시 실행하지 않았다.

## 미정·미구현·실제 사용자 미검증

스킵/재참여 보상 정책과 수치·실제 서사/장 구성·과거 퀘스트용 인스턴스/연출/NPC 재현·오프라인 타이머 운영 정책은 임의 확정하지 않았다. 직접 플레이 안내가 과거 세계 장면 재현 엔진의 완성을 뜻하지 않는다. 장 콘텐츠는 기존 공동체 확정 분기에서 허용된 필수 퀘스트만 지정해야 하며 분기별 과거 콘텐츠 자동 생성/이관은 없다.

실제 클라이언트의 죽음·NPC 보고/자동 완료·자동 보상·GUI/채팅·빠른 재접속·다인 코옵, 호위/전투 엔진의 실패 입력, 강제 종료/commit 응답 소실 복구, 장기 부하·TPS/MSPT는 미검증이다. 실제 클라이언트 시험과 운영 배포는 별도 요청 전 보류한다. 불명 보상은 지급 기록 상태/인벤토리 revision과 로그를 관리자가 대조하고, 임의 새 지급이나 빈 데이터 초기화를 하지 않는다.
