# S4 후속 설계 제안 — 공유 스토리의 월드 효과

후속: Issue #1 승인 범위의 단일 블록 효과를 구현하고 [격리 검증](s4-world-effect-verification.md)을 완료했다. 아래는 당시 제안 이력이다.

당시 상태: **설계 제안 / 미승인·미구현** (2026-10-27). 프로젝트 상태/ADR을 변경하지 않는다. 기준: `d1412a7`의 코드 및 [공유 진행 검증](s4-shared-story-batch-verification.md). 이 문서는 작업 인계 시에만 읽는다.

## 1. 현재 근거·다음 목표
- `SharedStory`는 온라인 조건/투표·V006 CAS/불명 결과를 확정하고 나서야 `Effects.apply(run, request, saved)`를 호출한다. 기본 응답은 `false`(NOT_IMPLEMENTED), 상태는 메모리에만 보관한다.
- 현 `confirm`의 `applied`는 effect 작업 완료 **전**에 증가하며 오류도 `effect` 문자열로만 표시한다. 재시작 시 물리 월드가 결과를 반영했다고 보장할 수 없다.
- `StoryAccess`의 단계 기반 지역 접근은 이미 존재한다. **다음 우선순위는 모든 콘텐츠 확장이 아니라, DB 확정 결과와 물리 월드 상태의 불일치 방지 계약**이다.
- 게임의 실제 장면·건물·비밀 스토리 콘텐츠는 여기서 정하지 않는다.

## 2. 채택 제안 — 상태 수렴형(effect reconciliation) 최소 구현
1. **원칙:** DB가 확정한 공유 단계/분기만 효과의 권위 있는 입력으로 사용한다. 효과 실행 성공을 DB 확정으로 착각하지 않으며 DB commit 불명·HOLD에서는 실행하지 않는다.
2. **멱등성:** 효과를 '한 번 실행'이 아니라 '지정된 안전한 최종 상태인지 확인하고 맞춘다'는 연산으로 정의한다. 동일 `story_run_id + stage/branch + effect_id`가 반복돼도 결과가 같아야 한다. DB–월드 파일 간 원자적 커밋/정확히 한 번 실행을 약속하지 않는다.
3. **최소 첫 효과:** **격리 시험 월드 안의 정해진 1개 블록 상태 변경**만 후보. 관리자/제작자 정의의 허용 목록 위치·기대 기존 블록·목표 블록을 사용하고, 대상 블록이 이미 목표면 성공, 기대 상태 이외이면 `EFFECT_CONFLICT`로 거부한다. 무관한 월드·플레이어가 변경한 지형을 절대 덮지 않는다.
4. **실행 시점:** DB 확정 뒤, 그리고 기존 진행 월드가 로드될 때 동일한 원하는 상태를 재확인한다. 월드 준비/저장·언로드 장벽에서 완료를 기다리며 Bukkit 블록 변경은 메인 스레드에서만 한다. 반복적인 tick/PlayerMoveEvent에서 DB를 조회하거나 효과를 실행하지 않는다.
5. **실패:** effect 실패는 **이미 확정한 DB 진행을 되돌리지 않는다**. 별도 상태(대기·적용·충돌/실패)를 기록/노출하며 효과가 필요한 지역의 플레이어 입장은 해당 효과 확인 전까지 차단한다. 다른 `story_run_id`는 계속 정상 동작한다. DB receipt가 불명인 요청에 임의 새 요청 ID를 발급해 재시도하지 않는다.
6. **콘텐츠 안전:** 실환경 기본 비활성, 기존 별도 검증 설정/JVM 게이트 및 새 사용자 소유 임시 월드에서만 시험한다. WorldGuard는 일반 보호 정본, Hearth effect는 신뢰한 내부 변화이지만 보호 규칙을 자동으로 우회한다고 가정하지 않는다. 콘텐츠 버전/진행 소유권 매핑 불일치면 적용 거부. 보상·인벤토리·NPC·다중 블록 건설/구역 대량 편집·기존 플레이어 월드 업그레이드는 이번 범위에서 제외한다.

## 3. 구현 경계(향후 Codex에게 전달할 작은 한 묶음)
- 기존 `SharedStory.Effects` 연결을 살리고 새 프레임워크·플러그인·일반화된 effect engine을 만들지 않는다.
- 효과 정의(고정 테스트 콘텐츠) → 월드/진행 일치 검사 → 메인 스레드의 조건부 블록 상태 수렴 → 완료/충돌 결과의 분리 순서로 작업한다.
- 로딩 시 재확인 경로를 추가하되 기존 `WorldLifecycle`의 생성/재진입·저장/언로드 순서를 보존한다. 물리 월드 ID로 DB 권한을 선택하지 않는다.
- 기존 `SharedStory`가 effect 비동기 실패를 저장 완료 성공과 혼동하지 않도록 실패 상태 및 barrier/settled 의미를 명확히 한다.
- 첫 배치에서 새로운 DB 마이그레이션/영구 retry queue/outbox는 추가하지 않는다. 단일 블록의 결정적 수렴으로 충분한지 먼저 입증한다. 이후 비멱등 효과(아이템 지급·엔티티 생성 등)는 반드시 별도 설계/중복 방지 검토가 필요하다.

## 4. 수용 기준과 필수 검사(중복 실행 금지)
- 단위: 성공·이미 적용된 대상·예상과 다른 블록 충돌, 잘못된 run/월드/generation 거부, 같은 요청 재전달 멱등성.
- 통합: DB commit 실패/불명 중 물리 효과 없음, A run만 변경·B 불변, effect 실패 후 공유 단계 기록 보존 및 제한 접근 차단.
- 복원 계약이 달라지므로 **신규 격리 Paper 순차 2 JVM + PG 1개 1묶음**에서 재시작 후 동일 상태 수렴과 언로드/프로세스 정리를 확인한다. 소스 변경 뒤 영향받은 검사만 다시 실행한다.
- 실제 인증 클라이언트의 이동·클릭/채팅/연출은 사용자 별도 지시 전 보류. 모든 검증 결과에 '내부 제어/실제 클라이언트' 경계를 표시한다.

## 5. 후속 순서와 보류 결정
1. **이번 문서만 설계**: 기능 구현, 시험 실행, 운영 변경 없음.
2. 사용자에게 초기 1블록 효과 및 접근 차단 범위의 채택 여부를 보고한 후 개발 범위를 확정한다.
3. 그 뒤에 Codex용 간결한 구현 지시서(위 3~4절)를 전달한다. 메모리·토큰 아끼기 위해 장문의 프로젝트 내역을 다시 첨부하지 않는다.
4. 분기별 서로 다른 조건 확대, 다수 블록/엔티티·구조물·컷신/보상, 실제 클라이언트 시험은 **별도 후속**으로 유지한다.
