# 경제 Tick 실적·제조 진단·등록 사건

확인일: 2026-11-08. 기준: `0cae349`. [결과 JSON](../verification/economy-flow-result.json)에 실행·실패 증거·자원·소스/JAR 식별자를 기록한다. 기존 [거래 수량/확정](economy-quote-verification.md)과 소유권/인벤토리 경계를 유지한다.

## 구현과 데이터

- `EconomyEngine.Step`에서 지역/상품별 실제 생산·제조 재료 투입·소비·미충족 수요·도착·출발·전후 재고를 계산한다. 재고 보존식 `이전+생산+도착-투입-소비-출발=종료`를 검사한다. 생산/소비/가격 규칙은 변경하지 않았다.
- E003은 `realm.flow_tick`과 `tick_flow`를 추가한다. 기존 Tick/시장/운송 저장과 같은 트랜잭션에서 실적을 확정한다. 최근 완료 Tick만 덮어쓰고 누적 이력/아이템 원장은 만들지 않는다. E001/E002 체크섬·원본 파일과 기존 데이터는 보존한다.
- 업그레이드 전/첫 Tick 전에는 실적 미등록을 표시한다. 기록 이후 전체/부분 누락·Tick 불일치는 조회와 후속 Tick을 거부하며 빈 실적이나 자동 복구로 처리하지 않는다. 시장 거래 이후의 현재 재고와 직전 Tick 종료 재고는 서로 다를 수 있다.
- 기존 콘텐츠 공개 필터를 거친 `EconomyReport`와 상점 시장 화면에 실제 실적을 연결했다. 시설 화면은 상한·현재 재고 단독 생산 가능량·목표 재고 충족/재료 부족/효율·사건 중단을 구분한다. 단독 참고값은 다음 Tick의 실제 생산 예측이 아니다.
- 기존 생산 효율/수요/레시피/운송량/지연 콘텐츠를 유지한다. 격리 서버 콘솔의 `hearthverify economy-event <event_id> <request_uuid>`는 등록 사건만 다음 Tick에 예약한다. 동일 요청 재전달은 중복 예약하지 않고 다른 사건으로 재사용하면 거부한다. 일반 플레이어·일반 서버에서는 활성화하지 않는다.
- 계정·41슬롯·30초 dirty 저장·경제/스토리 소유권과 기존 bounded worker를 재사용한다. DB 작업은 비동기이며 메인 스레드 대기를 추가하지 않았다. 신규 외부 플러그인/서비스·운영 정책 변경은 없다.

## 실패 보존과 비용

첫 컴파일에서 `java.util.concurrent.Flow`와 실적 타입 이름이 충돌해 명시 import로 수정했다. 첫 런타임 `/tmp/hearth-s4-11.gS1YLkkO`는 수요 증가 직후 생산을 5개로 잘못 기대해 실패했다. 기존 목표 재고 계산은 3개 생산/6개 소비이므로 경제 규칙을 바꾸지 않고 기대값과 관련 단위 사례를 수정했다. 원시 FAIL/풀 종료 확인 누락 기록은 보존했다. 후속 검사에서 소유 PID/DB PID 파일/25585·42495 포트가 없음을 별도로 확인한 뒤 새 경로에서 재시험했다. 총 2묶음을 사용했다.

실적 집계는 기존 계산에 지역×상품 수에 비례하는 공간/계산을 추가한다. DB 행 수는 realm당 해당 시장 수로 제한하고 한 batch로 같은 트랜잭션에 저장한다. 실제 실적의 보존/누락 검사를 위해 Tick마다 읽기·쓰기 비용이 추가되므로 비용이 없다고 보지 않는다. 운영 규모 DB 처리량은 미측정이다.

변경된 계산 경로의 기존 90일 시뮬레이션 2160 Tick도 검사했다. 4시장 0.129초, 512시장 8.125초, 종료 시 사용 힙 135031128바이트였다. 이는 단위 JVM 계산의 관측값이며 Paper TPS·실DB Tick 비용·장기 메모리 누수·개선율 측정이 아니다. 정식 경제 Tick 시간/밸런스를 정한 결과도 아니다.
