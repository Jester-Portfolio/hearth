# 스토리 월드 B안 구현 가능성 검토

> 후속 결정 (2026-10-23): [ADR-0002](decisions/0002-stack-and-world-policies.md)로 Paper 26.2·Java 25·Gradle·PostgreSQL·단일 JAR·Docker Compose 및 월드 정책이 확정됐습니다. 아래 기술 미정·후보 표현과 API 근거는 2026-10-22 당시 검토 기록으로 보존합니다. 현재 결정은 ADR을 따르며 채택 버전에서의 실행·호환성 검증은 여전히 미완료입니다.


상태: B안 채택 후 보존하는 기술 검토. [ADR-0001](decisions/0001-story-world-multiworld.md)에 따라 운영 구조는 확정했으며, 세부 구현 제안과 미검증 항목은 남아 있습니다. 최종 서버 구현체·버전·플러그인·모드와 데이터 저장 기술은 **미정**입니다.
검토일: 2026-10-22.

## 결론과 근거 수준

**Minecraft Java Edition에서 단일 서버의 다중 월드를 이용하는 B안에는 구현 경로가 있습니다. 다만 Hearth가 요구하는 전체 진행 격리와 현재 호스트의 자원 수용량은 미검증입니다.** Paper 계열 API 또는 월드 관리 플러그인을 우선 조사 대상으로 삼을 수 있지만 채택을 확정하지 않습니다.

[AGENTS.md](../AGENTS.md), [독립 진행 구조 비교](story-world-architecture.md), [아키텍처](architecture.md), [스토리 월드 설계](../minecraft/story/README.md)를 기준으로 작성했습니다. 싱글도 하나의 진행으로 취급하며, 코옵은 같은 진행에 참여합니다. 경제 월드와 데이터는 계속 분리합니다. Java Edition을 이번 검토의 범위로 삼는 것이 프로젝트 에디션 확정을 뜻하지는 않습니다.

| 표기 | 의미 |
| --- | --- |
| 문서 확인 | 공식 API·프로젝트 문서에서 기능이나 제약을 확인함. Hearth 실행 검증은 아님 |
| 설계 제안 | 요구사항을 만족시키기 위해 제안하는 처리 방식. 구현하지 않음 |
| 미검증 | 선정 버전에서의 지원 여부·호환성·성능·장애 복구를 실제로 확인해야 함 |

서버 설치·실행, 컨테이너 생성, 운영 설정 변경과 부하 시험은 수행하지 않았습니다. 아래 후속 검증 계획도 실행 승인을 뜻하지 않습니다.

## 1. Java Edition 다중 월드 운영 방법

여기서 월드는 블록·엔티티 공간과 저장 데이터를 가진 단위이고, 진행은 퀘스트·NPC 상태·참가자를 포함하는 게임 단위입니다. 하나의 진행은 필요에 따라 오버월드·네더·엔드 같은 월드 묶음에 대응할 수 있습니다. 마법 없는 세계관에서 필요한 차원과 포털 표현은 별도 게임 설계 사항입니다.

| 방법 | 문서로 확인한 구현 경로 | Hearth 적용 제약 |
| --- | --- | --- |
| Paper 계열 API를 이용한 자체 관리 | `Server.createWorld(WorldCreator)`, `getWorlds()`, `unloadWorld(..., save)` 제공 | 생성·로드·언로드를 진행 ID와 연결하는 자체 관리 기능 필요. API 존재가 전체 데이터 격리를 보장하지 않음 |
| Paper 계열 + Multiverse-Core 같은 월드 관리자 | 생성, 가져오기, 복제, 로드, 언로드 명령 제공 | 파티·퀘스트·AI 권한은 별도 구현. 명령보다 API 연동 가능성과 자동 로드 정책을 후보 버전에서 확인할 필요 |
| 바닐라의 커스텀 차원·데이터팩 | Mojang은 커스텀 월드·차원 도입을 공식 발표함 | 차원 정의와 플레이어별 동적 인스턴스 서비스는 다름. 현재 후보 버전의 런타임 생성·언로드·복구 적합성은 미검증 |
| Fabric·NeoForge 기반 모드 | 모드로 엔티티·저장·네트워크 등 게임 동작 확장 가능 | 동적 차원 관리의 구체 API·지원 모드와 NPC·퀘스트 통합은 미검증. 버전별 개발·호환성 조사 필요 |

Paper API는 동일 이름의 기존 월드를 로드하거나 이미 로드된 월드를 반환할 수 있습니다. 실패 결과와 예외를 처리해야 하며 해당 API 버전은 월드 틱 도중 로드·언로드에 제약을 명시합니다. 무조건 비동기 스레드로 옮기는 방식은 전제하지 않습니다. [Paper Server API 1.21.11](https://jd.papermc.io/paper/1.21.11/org/bukkit/Server.html)

`WorldCreator.copy()`는 생성 **옵션** 복사입니다. 같은 시드·옵션만으로 이미 건설된 마을, 상자 내용과 스토리 변화를 복제하지는 않습니다. 실제 템플릿 복제는 별도 기능입니다. [WorldCreator API](https://jd.papermc.io/paper/1.21.11/org/bukkit/WorldCreator.html)

Multiverse-Core의 복제 기능은 월드 디렉터리와 관련 설정 복사를 제공하지만 외부 퀘스트 DB·NPC 레지스트리까지 함께 복제한다고 해석하지 않습니다. [Multiverse-Core 명령 문서](https://mvplugins.org/core/fundamentals/commands-usage/)

커스텀 차원에 대한 Mojang의 도입 문서는 역사적 근거이며 현재 버전의 동적 관리 API나 안정성 보증이 아닙니다. 이를 근거로 재시작 없이 임의 개수의 진행을 만들 수 있다고 주장하지 않습니다. [Mojang 20w21a 안내](https://www.minecraft.net/en-us/article/minecraft-snapshot-20w21a)

## 2. Paper와 다른 후보 기술의 차이

| 후보 | 장점·적합 가능성 | 기술적 제약·미검증 항목 |
| --- | --- | --- |
| Paper + 필요한 자체 플러그인 | 월드·이벤트·플레이어 API를 조합해 진행 관리 가능. 기존 월드·인벤토리 도구 활용 후보 | 게임 로직의 메인 스레드 부하를 고려해야 함. 다른 월드도 지연·힙·장애를 공유. NPC·퀘스트 도구의 진행 ID 지원은 미검증 |
| Spigot/Bukkit 계열 | 공통 API 기반 플러그인 후보를 검토할 수 있음 | Paper 전용 API를 사용하면 그대로 이전할 수 없음. 선정 버전의 기능·성능·플러그인 요구 API는 미검증 |
| Folia | 영역별 틱 병렬화로 분산된 활동을 처리할 가능성 | Paper 플러그인 호환을 가정할 수 없음. 영역·엔티티 스케줄러 대응 필요. 월드 수명주기 API와 NPC·퀘스트 도구 호환, 6코어 호스트에서의 이득은 미검증 |
| Fabric / NeoForge | 자체 게임 기능이나 클라이언트 UI까지 확장할 후보 | Bukkit 플러그인을 그대로 쓰는 전제가 성립하지 않음. 모드 구성에 따라 클라이언트 설치가 필요할 수 있음. 동적 차원·저장·퀘스트 도구와 유지보수 비용은 미검증 |
| 바닐라 + 데이터팩 | 별도 서버 플러그인 없이 제한된 콘텐츠를 구성할 후보 | 진행 생성·폐기, 인벤토리 전환, 복구와 외부 AI 연동을 묶는 방법은 별도 검증 필요. B안 전체의 준비된 구현으로 보지 않음 |

Paper의 공식 스케줄러 문서는 게임 로직의 메인 스레드와 비동기 작업을 구분하고 월드 상태 API의 비동기 접근 위험을 명시합니다. 파일·DB·AI 통신은 별도 작업으로 처리하되 안전한 스냅샷을 사용하고 게임 상태 반영은 올바른 서버 실행 문맥으로 돌려보내는 설계를 검토합니다. 비동기화도 호스트 CPU·RAM 경쟁을 없애지는 않습니다. [Paper 스케줄링](https://docs.papermc.io/paper/dev/scheduler/)

Folia는 영역 병렬화와 별도 스케줄러를 사용하며 호환 표시만 추가해서 플러그인이 안전해지는 것은 아닙니다. 자동 성능 향상이나 진행 격리를 보장하는 대안으로 선정하지 않습니다. [Paper/Folia 지원 지침](https://docs.papermc.io/paper/dev/folia-support/), [Folia 개요](https://docs.papermc.io/folia/)

모드 후보의 기능 범위는 [Fabric 개발 문서](https://docs.fabricmc.net/develop/), [NeoForge 개발 문서](https://docs.neoforged.net/docs/gettingstarted/)를 참고했습니다. 동적 진행 월드에 대한 구체적인 작동 조합은 확인하지 않았습니다. Minecraft·Java·서버·확장 기능 버전의 교집합은 최종 후보 평가 시 확인하며, 참고 API 버전은 채택 버전이 아닙니다.

## 3. 진행 ID와 월드 수명주기 설계 제안

변경 가능한 파티 명단·월드 이름과 별개인 `story_run_id`를 유지합니다. 물리 월드 이름·UUID·차원 키는 별도 매핑으로 관리합니다. 플레이어가 입력한 월드 이름만으로 접근을 허용하지 않습니다.

| 논리 데이터 | 역할 |
| --- | --- |
| 진행 레코드 | 진행 ID, 템플릿·콘텐츠 버전, 상태·저장 세대, 배치 서버 ID |
| 월드 매핑 | 진행 ID, 논리 월드 역할, 실제 월드 이름·UUID·키 |
| 참가 관계 | 진행 ID, 플레이어 UUID, 역할, 참여·철회 상태 |
| 진행 상태 | 진행 ID별 퀘스트·NPC·월드 이벤트 및 보상 이력 |
| 개인 상태 | 진행 ID + 플레이어 UUID별 인벤토리·위치·체력 등 |

DB나 파일 형식은 미정입니다. 한 플레이어가 여러 진행에 속할 수 있는지와 별개로, 현재 접속 세션이 조작하는 진행은 하나로 지정하는 방향입니다.

진행 수명주기는 다음과 같이 검토합니다. 아래 상태와 절차는 구현 제안이며 **미검증**입니다.

| 단계 | 제안하는 처리 | 실패·경합 시 제약 |
| --- | --- | --- |
| 생성 요청 | 권한·활성 진행 한도 확인 후 진행 ID 예약. 같은 요청의 중복 실행 방지 | 여러 파티원이 동시에 요청해도 진행을 중복 생성하지 않도록 잠금·멱등 처리 필요 |
| 템플릿 복제 | 쓰기 중이 아닌 검증된 원본을 임시 목적지로 복제하고 콘텐츠 버전·완료 여부 확인 | 로드 중인 원본의 단순 파일 복사를 전제하지 않음. 실패본은 접근 차단하고 기존 데이터는 보존 |
| 식별자 재매핑 | 월드 UUID·키, 엔티티 UUID, 포털 연결, NPC ID·좌표, 외부 스크립트 참조를 점검 | 어떤 식별자를 유지·변환할지는 복제 도구와 버전에 따라 미검증. 범용 파일 삭제 규칙으로 해결하지 않음 |
| 로드·초기화 | 올바른 실행 문맥에서 월드 로드, 진행별 NPC·퀘스트 연결, 준비 완료 후 입장 허용 | API 반환값·예외 확인. 로드가 실패한 기존 월드를 빈 새 월드로 대체하지 않음 |
| 활동 | 허용된 참가자만 입장. 저장과 진행 이벤트를 순서대로 처리 | 이동·포털·부활·명령·플러그인 강제 이동도 동일한 경계 검사 필요 |
| 저장 | 플레이어 스냅샷, 퀘스트·NPC 상태와 월드 저장을 조정 | 월드 파일과 DB는 자동 단일 트랜잭션이 아님. 체크포인트·완료 표식·재처리 규칙 필요 |
| 유휴 전환 | 마지막 참가자 이탈 후 대기 시간을 두고 새 입장을 잠시 차단. 참가자·입장 중 요청이 없는지 재확인 | 재접속 요청과 언로드가 교차하면 한쪽을 대기시켜 중복 로드 방지 |
| 언로드 | 저장 완료 후 NPC 작업·틱 작업·강제 청크 티켓·캐시 참조 정리, 월드 언로드 성공 확인 | 실패하면 로드 상태로 유지·재시도 판단. 저장 완료 전 강제 제거하거나 성공으로 기록하지 않음 |
| 재접속 | 참가 권한과 진행 상태 확인 → 단일 로드 요청에 합류 → 개인 상태 복원 → 안전 위치로 이동 | 월드가 준비되기 전 상호작용 차단. 복구 불가 시 안내·입장 대기 또는 거부하고 다른 진행으로 자동 배치하지 않음 |

기본 월드·대기 공간이 필요하다면 진행 월드와 분리하고 전체 비용에 포함합니다. 로드 대기 중 접속을 유지하는 방식이 가능한지, 초기 스폰 전에 경계를 적용할 수 있는지 또는 준비될 때까지 접속을 거부할지는 이벤트 API와 후보 플러그인 조합에서 **미검증**입니다.

주기 저장은 장애 시 유실 범위를 줄이는 수단이며 세 저장 계층의 일관성을 보장하지 않습니다. 플레이어 전환 기록과 체크포인트를 통해 중단된 작업을 식별하고, 복구 때 완료된 세대를 선택하는 방안을 검토합니다. 서버 시작 시 미완료 복제·전환·언로드 기록을 먼저 처리하고 모든 저장 월드를 자동 로드하지 않는 정책이 가능한지 확인해야 합니다.

언로드는 월드 파일 삭제가 아닙니다. 빈 진행 자동 삭제는 제안하지 않습니다. 유휴 월드는 멈춘다는 가정과 작물·NPC·퀘스트 시간의 재접속 시 처리 정책은 별도 결정이 필요합니다.

## 4. NPC·퀘스트·인벤토리·플레이어 데이터 격리

월드 분리는 실제 블록·엔티티 공간을 나누는 기반입니다. 서버 전체 레지스트리나 플레이어 객체에 붙은 상태까지 자동 분리하는 기능은 아닙니다.

| 대상 | 설계 제안 | 제약과 검증 포인트 |
| --- | --- | --- |
| 블록·상자·드롭·유체·레드스톤 | 진행별 물리 월드에서 처리. 월드 객체를 진행 ID로 검증 | 다른 월드를 지정하는 명령·스크립트·좌표 참조 차단. 네더·엔드 연결도 진행 묶음 안으로 제한 |
| NPC | 논리 NPC ID를 `(진행 ID, 콘텐츠 NPC ID)`로 관리하고 실제 엔티티·플러그인 ID와 매핑 | 월드 디렉터리 복사만으로 플러그인의 NPC 정의·상태가 복제된다고 가정하지 않음. 재로드 시 중복 스폰 방지 |
| 퀘스트 | 진행별 공유 단계와 개인별 목표·보상 이력 분리. 모든 이벤트에 진행 컨텍스트 부여 | 플레이어 UUID만으로 저장하는 도구는 다른 진행을 구분하지 못할 수 있음. 파티 기능이 있어도 영속 진행 ID를 지원하는지는 별도 확인 |
| 인벤토리·엔더 상자 | `(진행 ID, 플레이어 UUID)`별 저장·복원. 같은 진행의 차원끼리는 같은 개인 상태 사용 검토 | 월드 이동만으로 분리되지 않음. 장비·보조 손·커서·열린 GUI·아이템 드롭·사망 시점까지 검증 |
| 체력·허기·경험치·효과·게임 모드·부활 위치 | 진행 전환 시 분리할 항목을 명시적으로 저장·복원 | 베드·리스폰 앵커·사망 복귀가 다른 진행으로 연결되지 않도록 확인 |
| 업적·통계·레시피 해금 | 진행별 분리가 필요한 항목과 계정 공통 항목을 결정 | 후보 도구가 모든 상태를 지원하는지 미검증. 필수 격리 항목을 지원하지 않으면 콘텐츠에서 제외하거나 후보 변경 |
| 팀·스코어보드·보스바·명령·타이머·플러그인 캐시 | 진행별 키와 수신자 범위를 지정 | 전역 브로드캐스트나 고정 NPC ID 같은 전역 참조를 감사해야 함 |

Multiverse-Inventories는 월드 그룹별 플레이어 상태 분리·공유 경로를 제공합니다. 진행에 속한 월드들을 한 그룹에 묶는 후보 방식이지만 동적 그룹 생성과 접속·전환 제어의 호환성은 **미검증**입니다. 이는 파티원들이 한 인벤토리를 공유한다는 뜻이 아니며 각자의 상태가 해당 그룹 안에서 유지되는 방식입니다. [그룹 기본 사용법](https://mvplugins.org/inventories/fundamentals/basic-usage/)

지원 목록에는 인벤토리·장비·엔더 상자·경험치 등이 있고 업적·레시피·마지막 위치 등은 선택 설정입니다. `all` 같은 이름만으로 모든 게임·플러그인 데이터가 분리된다고 판단하지 않습니다. 특히 마지막 위치 기능이 이동을 재지정할 수 있어 Hearth의 입장 제어와 충돌 여부를 확인해야 합니다. [공유 항목 목록](https://mvplugins.org/inventories/reference/shares-list/)

자체 저장을 선택한다면 전환 때 상호작용을 잠시 막고 이전 상태 저장 → 목적 진행 상태 복원 → 이동 완료를 관리해야 합니다. 실패 시 이전 상태 복구 또는 안전한 입장 차단을 적용하고 미완료 기록을 남기는 방향입니다. 기존 인벤토리 플러그인과 자체 저장이 같은 데이터를 동시에 덮어쓰지 않도록 항목별 저장 책임자를 하나로 정해야 합니다. 구체적인 이벤트 순서와 장애 복구는 **미검증**입니다.

엔티티·아이템에 진행 ID를 보조 표식으로 남기는 수단으로 Paper PDC를 검토할 수 있습니다. 표식 자체가 접근 통제나 전체 저장소는 아니며, 신뢰할 수 있는 서버 매핑과 대조해야 합니다. [Paper PDC 문서](https://docs.papermc.io/paper/dev/pdc/)

NPC·퀘스트 제품의 이름만으로 호환성을 판단하지 않습니다. 예를 들어 BetonQuest의 파티 문서는 조건·거리 기반 참여 방식을 설명하므로 Hearth의 영속 파티·진행 소유권과 동일하다고 볼 수 없습니다. 실제 후보 버전의 저장 키·월드 조건·NPC 연결 API를 확인해야 합니다. [BetonQuest 2.1 파티 문서](https://betonquest.org/2.1/Documentation/Scripting/Parties/)

## 5. 코옵 파티와 진행 데이터 처리 제안

파티 명단과 진행 소유권을 분리하고 가입·탈퇴만으로 월드나 저장 데이터를 합치거나 복제하지 않는 방향을 검토합니다. 싱글의 독립 진행과 코옵의 진행·월드 공유는 확정했으며, 아래 가입·탈퇴·보상 등 세부 정책은 확정 사항이 아닙니다.

| 상황 | 제안하는 처리 | 결정·검증할 사항 |
| --- | --- | --- |
| 싱글·새 파티 생성 | 새 진행 ID와 참가 관계 생성. 싱글에도 같은 절차 사용 | 진행 생성 한도, 소유자·관리자 권한 |
| 기존 싱글 진행에 친구 초대 | 기존 진행 ID에 참가 권한을 추가하며 새 월드를 만들지 않음 | 초대 승인, 퀘스트 중간 합류, 스포일러·보상 자격 |
| 다른 진행에 있던 플레이어 가입 | 기존 개인 상태 저장 후 대상 진행의 개인 상태를 로드하거나 신규 초기화 | 기존 아이템·퀘스트를 가져오지 않는 방향을 검토. 신규 장비·과거 보상 정책은 미정 |
| 탈퇴·추방 | 접근 권한 철회 후 안전하게 퇴장. 해당 진행의 개인 저장과 공유 진행은 보존 | 탈퇴자의 기여·재가입 보상·소유권 처리. 접속 중 철회와 저장 순서 검증 |
| 마지막 플레이어 로그아웃 | 확정된 저장 후 언로드 방향에 따라 유휴 전환 | 로그아웃은 탈퇴가 아님. 복귀 시 참가 관계 유지 |
| 파티장 변경·부재 | 진행 ID를 유지한 채 역할만 변경 | 단독 탈퇴·장기 부재 시 소유권 정책 |
| 파티 분할·병합 | 초기에는 자동 병합·월드 분기를 제공하지 않는 방향 검토 | 향후 분기는 NPC·보상·개인 상태까지 복제해야 하며 미검증 |

공유 퀘스트의 동시 완료는 진행별 순서 제어·상태 버전 검사로 한 번만 반영하고, 개인 보상에는 진행·퀘스트·플레이어·완료 회차를 식별할 키를 두는 방안을 검토합니다. DB 기록과 아이템 지급의 경계에서 중단되어도 중복·유실이 발생하지 않도록 지급 기록과 재처리 정책이 필요합니다. 단순히 같은 이벤트를 모든 파티원에게 실행하는 것으로 일관성이 보장되지는 않습니다.

## 6. AI 스마트폰 어시스턴트의 접근 경계

AI는 필수 기능이며 공통 로컬 AI 서비스를 사용하되 진행별 정보 접근을 격리하기로 확정했습니다. 아래는 그 요구를 구현하기 위한 세부 설계 제안입니다. 모델·런타임·동시 처리량은 **미검증**입니다.

1. 인증된 플레이어 세션에서 현재 진행 ID·참가 권한을 서버가 결정합니다. 사용자의 질문이나 모델이 제시한 월드 ID를 권한 근거로 쓰지 않습니다.
2. 공통 과학·기술 지식과 콘텐츠 정의는 공유 가능한 정적 자료로 분리하고, NPC 생존·퀘스트 단계·발견 정보는 진행 및 필요 시 개인별 자료로 제한합니다. 공통 콘텐츠라도 미공개 내용의 열람 규칙은 적용합니다.
3. 정보 조회 도구가 권한과 진행 필터를 강제합니다. 검색 인덱스·문서·대화·요약·캐시는 진행 ID와 필요한 플레이어 범위를 포함하고, 필터 실패 시 다른 진행 자료로 대체하지 않습니다.
4. 게임 상태는 올바른 서버 실행 문맥에서 스냅샷으로 수집하고 AI 통신은 비동기로 수행하는 방향입니다. 늦게 도착한 응답은 현재 진행·권한·상태 버전을 다시 확인한 뒤 전달합니다.
5. 월드 언로드 시 스냅샷의 시점을 표시하고 실제 월드를 무조건 다시 로드해 질의하지 않는 방향을 검토합니다. NPC·퀘스트 변경이 있으면 관련 캐시 무효화가 필요합니다.
6. 초기에는 답변용 읽기 권한을 기본 후보로 삼고, 퀘스트 완료·아이템 지급·임의 명령 실행 권한은 별도 검토합니다. 자연어 지시만으로 접근 경계가 유지된다고 보지 않습니다.

개인 대화와 파티 공유 대화의 공개 범위, 탈퇴 뒤 대화 접근과 보존 정책은 미정입니다. 파티 간 동일 문장 질의, 권한 철회 중 요청, 진행 전환 후 응답, 캐시 재사용을 이용한 정보 누출 시험은 **미검증**입니다.

## 7. 동시 접속자·활성 월드에 따른 CPU·RAM 부담

이전 [구조 비교 문서](story-world-architecture.md)에 기록된 환경은 Rocky Linux 9.8, i7-9750H 6코어·12스레드, RAM 15,442MiB(약 15.1GiB)입니다. 이 값은 이전 읽기 전용 확인 기록이며 이번에 다시 측정한 값은 아닙니다. 당시 가용 RAM 수치는 현재 여유량이나 할당 예산으로 재사용하지 않습니다.

등록·저장된 월드 수, 메모리에 로드된 월드 수, 실제 청크가 활동하는 월드 수를 구분해야 합니다. 진행 하나가 세 월드로 구성될 수도 있고 참가자가 없는 월드도 강제 청크 로드나 플러그인 작업 때문에 비용을 발생시킬 수 있습니다.

| 부하 상황 | 예상 특성·추론 | 절약 후보와 제약 |
| --- | --- | --- |
| 같은 장소의 코옵 인원 증가 | 일부 청크는 공유하지만 플레이어 처리·통신·상호작용은 증가 | 파티 규모 제한 후보. 같은 파티여도 멀리 탐험하면 청크 공유 효과 감소 |
| 같은 접속자 수가 여러 진행으로 분산 | 같은 마을도 월드별 청크·NPC·엔티티가 중복 활동 | 동시 활성 진행 한도와 진행별 로드 범위 관리 필요 |
| 월드 생성·복제·로드 동시 발생 | 파일 I/O·청크 생성·초기화·힙 할당이 순간 증가 | 생성·로드 작업의 대기열과 동시 작업 한도 검토 |
| NPC 다수·탐험·저장·AI 질의 중첩 | 경로 탐색·새 청크 생성·저장·AI 추론이 호스트 자원에서 경쟁 | NPC 활동 범위·청크 생성 범위·AI 동시 질의 제한을 측정 후 결정 |
| 유휴 진행 언로드 | 청크·엔티티의 실행 비용을 줄일 가능성 | 플러그인 참조·작업이 남으면 효과 제한. 언로드 직후 RSS가 즉시 감소한다고 가정하지 않음 |
| 저장된 진행만 증가 | 디스크·백업·목록 관리 비용 증가 | 미접속 진행을 모두 로드하지 않는 정책. 데이터 삭제와는 분리 |

자원 예산의 개념식은 `OS·기존 서비스·안전 여유 + Minecraft 프로세스 전체 사용량 + AI 및 데이터 서비스 사용량 ≤ 호스트 RAM`입니다. Minecraft 사용량에는 공유 런타임·플러그인 기본 비용, 로드 청크·엔티티, 플레이어·진행 캐시, 동시 작업의 최대 비용을 포함합니다. JVM 힙 상한은 네이티브 메모리·스레드·프로세스 전체 RSS와 다릅니다. 계수와 실제 최대치는 **미검증**이며 특정 GiB/월드 또는 최대 접속자 수는 제시하지 않습니다.

Paper에서는 여러 월드의 게임 로직이 메인 스레드 처리 시간을 경쟁하므로 12논리 CPU를 12월드의 전용 처리 능력으로 계산하지 않습니다. 20TPS를 목표로 하면 평균 틱 예산은 50ms이지만 평균만으로 순간 정지를 판단할 수 없습니다. Folia 등 다른 스케줄링 모델은 별도 지표와 검증이 필요합니다. 메인 스레드·비동기 작업의 구분은 [Paper 스케줄링 문서](https://docs.papermc.io/paper/dev/scheduler/)를 근거로 합니다.

월드별 NPC·스폰·청크 관련 설정을 조정할 여지는 있으나 콘텐츠 동작도 변할 수 있습니다. 후보 버전에서 지원 항목과 결과를 확인하고, 실제 절감량을 측정해야 합니다. [Paper 월드 설정](https://docs.papermc.io/paper/reference/world-configuration/)

## 8. 현재 서버에서 필요한 후속 검증

아래 시험은 모두 **미검증·미실행**입니다. 운영 환경과 분리된 검증 범위·자원 예산을 정하고 필요한 설치·실행 승인을 별도로 받은 뒤 진행할 계획입니다.

| 검증 항목 | 시험과 판정 방향 |
| --- | --- |
| 버전 조합 | Minecraft·Java·서버·월드 관리자·인벤토리·NPC·퀘스트 기술의 지원 버전과 API·라이선스 조건 확인. 동적 월드 처리 불가 도구는 제외 또는 대체 검토 |
| 템플릿·ID | 두 복사본 동시 로드 후 월드·엔티티·NPC 식별 충돌, 좌표·포털 참조를 확인. 한쪽 다리·상자·NPC 상태 변경이 다른 쪽에 반영되지 않아야 함 |
| 개인 상태 | 같은 플레이어가 두 진행을 오가며 인벤토리·엔더 상자·경험치·사망·부활·재접속 처리 확인. 실패·강제 종료 중 전환의 중복·유실도 점검 |
| 파티 일관성 | 동시 가입·탈퇴·추방·공유 퀘스트 완료·보상 처리 및 마지막 이탈과 재접속 경합 확인 |
| 로드·언로드 반복 | 참가자 없는 진행을 반복 저장·언로드·재로드하고 청크 티켓·NPC 작업·참조 누수와 상태 보존 확인 |
| 접근·AI | 명령·포털·부활·스크립트 이동을 통한 타 진행 접근, 검색·대화·캐시·지연 응답을 통한 정보 누출이 없어야 함 |
| 지속 부하 | 1인·1진행을 기준으로 2인·동일 진행과 2인·서로 다른 진행 비교 후 목표 동시 코옵 규모까지 단계적으로 측정. 탐험·NPC·저장·AI 중첩 포함 |
| 호스트 여유 | 기존 서비스 최대 사용량, CPU 클럭·온도·지속 성능, RAM·Swap·디스크 용량과 I/O, AI 추론의 최대 사용량 확인 |
| 복구·이전 | 월드와 외부 상태를 같은 체크포인트로 복원. 하나의 진행만 별도 서버에 복원하고 다른 진행이 유지되는지 확인 |

측정 항목은 CPU, 프로세스 RSS·힙·GC, 로드 월드·청크·엔티티 수, 디스크 I/O, 틱 지연 분포·TPS, 입장·저장 지연, AI 응답 시간입니다. Paper 후보라면 공식 안내의 프로파일러로 병목을 관찰할 수 있습니다. [Paper 프로파일링](https://docs.papermc.io/paper/profiling/)

허용 지연·안전 메모리 여유·동시 파티 목표는 시험 전에 결정해야 합니다. 상태 누출·진행 유실·중복 보상은 통과로 인정하지 않는 방향입니다. 성능 기준을 넘으면 활성 진행 수나 콘텐츠 부하를 줄여 재평가하며, 누수·호환성 문제가 남으면 B의 전제를 재검토합니다.

## 9. A안 확장 가능성을 유지하는 방향

진행 ID와 물리 월드·서버 배치의 분리는 확정했습니다. 콘텐츠 버전·참가 관계·개인 상태·퀘스트·NPC 상태를 진행 단위로 내보내는 방식은 세부 설계 제안입니다. 저장 형식과 이전 도구는 미정입니다.

- 논리 NPC·퀘스트 ID와 실제 플러그인·엔티티 ID를 분리합니다. 위치는 진행 ID와 논리 월드 역할로 표현하고 로컬 월드 이름만 영구 식별자로 쓰지 않습니다.
- 월드 파일만으로 이전이 끝나지 않습니다. 인벤토리 도구 데이터, 외부 NPC·퀘스트 저장, 보상·참가 관계, AI 자료와 캐시 정책까지 이전 범위에 포함합니다.
- 이전 시 신규 변경·입장을 막고 저장 체크포인트를 만든 뒤, 대상에서 버전·식별자 매핑·복원을 검증하고 배치를 전환하는 절차를 검토합니다. 무중단 자동 이전은 약속하지 않습니다.
- 같은 진행을 두 서버가 동시에 쓰지 않도록 배치 소유권·잠금을 검토합니다. 실패 시 원본 보존과 쓰기 권한을 조정한 롤백이 필요하며 양쪽 변경을 자동 병합하지 않습니다.
- A로 이동하더라도 AI·DB 접근 경계는 계속 필요합니다. 공통 서버 하나를 전제로 한 API 호출과 게임 로직을 분리하는 방향이 이식성에 유리하다는 설계 추론입니다.

이식성과 복구는 **미검증**입니다. B안은 ADR-0001로 채택했으며 NPC·퀘스트 격리 또는 자원 기준을 만족하지 못하면 대체 구현과 A안 확장 비용도 재검토합니다. 구조 변경이 필요하면 시험 결과를 근거로 후속 [의사결정 기록](decisions/README.md)을 남깁니다. B안 채택이 본문의 기술적 검증 완료를 뜻하지는 않습니다.
