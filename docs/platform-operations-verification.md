# 공통 플랫폼 운영 수명주기 일괄 검증

2026-11-21. 잔여 시스템 일괄 구현 요청에 따라 설정 I/O·이력/과거 세대 보관·공통 진입 조건·상태 관측·배포 후보를 연결했다. [ADR-0035](decisions/0035-platform-operations-and-retention.md), [운영 가이드](../infrastructure/network/platform-operations.md), [구조화 증거](../verification/platform-operations-result.json)를 따른다. 플레이 콘텐츠/밸런스와 운영 활성화는 이번 구현에 포함하지 않는다.

## 구현

- **설정 파일 작업:** bounded 단일 worker/대기32개에서 전체 이력 검증·후보 읽기/보존·상세 조회·원자 공개/보관을 수행한다. 검증할 바이트를 고정해 owner의 Paper 검증 후 다시 비교하고, 중간 외부 수정은 거부한다. Paper/API 검증과 제한된 live reload는 owner에서 실행한다. 조회 결과는 해당 요청의 불변 값으로 판단하며 종료 drain은 파일 작업을 기다린다.
- **이력:** E014는 config/job의 archived 표식을 추가한다. 원본 행과 안정 ID·해시/입력·영수증을 남기고 현재 목록의 4,096개 상한만 분리한다. UUID 상세 조회/작업 replay는 보관 뒤에도 유지한다. 보관한 설정은 재적용을 거부하고 새 후보를 요구한다. 부분 보관은 같은 ID로 재개하고 증거를 덮어쓰지 않는다. 과거 offline 정책 기록은 live 후보 목록과 구별한다.
- **월드:** RETIRED 생성 세대의 미로드/비참조·metadata UUID·전체 파일 seal을 검사한 뒤 cold 영역으로 원자 이동/복원한다. E014 상태/revision과 파일 이동 사이의 중단은 보류로 남고 새 JVM에서도 유지된다. 현재/준비 세대, 원래 바인딩과 거주, 미확정 작업은 대상이 아니다. 복원은 파일 위치만 되돌리고 활성 역할을 바꾸지 않는다. 보관 상태의 세대는 hot 자원 목록 상한에서 분리한다.
- **진입 조건:** 일반 작업/예약과 관리 복구의 준비 조건을 구분한다. 설정 변경 중 기존 상점/native 거래·인챈트 작업·RPG 능력의 공통 신규 진입을 막고 확정 후 다시 연다. 기존 권한·접속 토큰·설정 세대·입장/ACL·NativeTransactions/CAS를 유지한다. 보관/없는 후보의 단순 적용 거부는 정상 플랫폼을 유지보수로 바꾸지 않는다. 실제 쓰기/증거 불명 오류와 다른 모듈 HOLD는 계속 보존한다.
- **진단:** format2 RuntimeReport/기존 Python 판독기에 플랫폼 보류·파일 큐·작업/자원/설정 카운터를 연결한다. 단순 프로세스 생존/READY만으로 controller_ready를 표시하지 않는다. 지속 관측 도구는 현재 nonce·나이·한도/TPS/MSPT/힙을 검사하고 실제 집계만 JSONL로 기록한다.
- **운영 준비:** 네트워크 4서비스의 준비된 경로·동일 JAR/인증 전달·고정 이미지/입력 해시·예산/포트·백업 정책과 수용 미완료를 묶은 후보를 생성한다. 생성한 Compose/기동 파일도 seal로 검사한다. JDK25/비root·준비된 EULA·입력/검토 해시·수용/별도 승인 조건을 검사하고 기동 nonce를 만든다. 미선정 예산/보존 값은 빈 검토 양식으로 남긴다.

이력 보관은 원본을 삭제하거나 DB/디스크 사용량을 줄이는 purge가 아니다. 삭제·자동 보존 기간·스케줄 설치·운영 전환은 적용하지 않았다. 원자 이동은 같은 파일시스템에서만 사용하고, DB+월드 전체의 정전 무손실 복구를 약속하지 않는다. 보관 파일도 기존 전체 Paper+PG 일관 백업에 포함한다.

전체 저장 형식/DB 코드는 PG 통과 JAR과 최종 JAR의 관련48개 엔트리가 동일함을 비교했다. 이후 bounded 순회/기동 검사/요청 거부/공통 진입 변경은 영향받은 단위와 최종 Paper 경계로 검사했다. 이미 통과한 PG·자원 교체 전체 행렬을 다시 실행하지 않았다. 중간 최종 후보의 추가 한 JVM 증거도 원본으로 보존한다. 원래 realm의 기존 열 값과 스토리 데이터 보존을 확인했으며 E014의 새 archived 기본 열을 원래 데이터 변경으로 오인하지 않도록 비교에서 분리했다.

## 성능·자원과 한계

4,096개 초과 cold config 이력을 둔 격리 DB에서 8개 동시·총128개 읽기는 637ms, p95 40.235ms/최대48.073ms였다. 실제 Paper에서 8개 동시·총32개 설정 조회는 399ms, p95 99.934ms였고 그동안8tick이 진행됐다. 파일 검증은 전용 worker를 사용한다. 이 값은 짧은 무접속 관리/복구 검사이며 4명/실동접 채집·전투·거래나 장기 용량 기준이 아니다.

기존 CPU2/nice10·Paper heap1536MiB/RSS2560MiB·합산RSS6144MiB·600초/작업550초·실행별 최대2Paper/1PG·localhost/정품 인증·소유 격리 경계를 유지했다. 전체 배치의 최초 두 JVM 실행은55.379초였고 합산 RSS 최대 표본은 약1,606MiB였다. 최종 시간/RSS/TPS/MSPT/힙·모든 원시 증거 경로/해시는 구조화 증거에 기록한다. 관측 도구의 시험 기준은 기술 한도 확인용이며 운영 수용 기준으로 채택하지 않는다.

## 별도 수용

실제 정품 클라이언트 클릭·접속자 포함 상점/인챈트/이동/권한 변경의 행동, 실제 동접/장기 부하·물리 정전·운영 이미지 빌드/기동·백업 스케줄/오프사이트·Zabbix 수집/전환은 미검증이다. Player를 합성하지 않았다. 관측/배포 도구 구현을 이 수용의 완료로 세지 않는다. 기존 서비스를 중단/재시작하거나 운영 DB/월드·Docker 서비스·Zabbix·SSH/방화벽·시스템 패키지를 바꾸지 않았다. 추가 개발은 확인된 결함/새 플랫폼 기능 요청을 대상으로 하고, 보류한 콘텐츠/수치 선택을 반복해서 시스템 미구현으로 세지 않는다.
